# 1. Назначение

Настоящее архитектурное решение определяет принцип организации поиска, фильтрации и SEO каталога в проекте **Smart Electric (SmEl)**.

Решение фиксирует эти функции как отдельную подсистему, работающую поверх данных каталога и не изменяющую исходные бизнес-данные.

# 2. Область применения

Решение применяется к:

- полнотекстовому поиску;
    
- поиску по артикулу;
    
- поиску по SKU;
    
- поиску по характеристикам;
    
- поиску по брендам и сериям;
    
- фильтрации товаров;
    
- сортировке результатов;
    
- фасетной навигации;
    
- поисковым подсказкам;
    
- SEO-страницам;
    
- URL и каноническим адресам;
    
- хлебным крошкам;
    
- sitemap;
    
- структурированным данным Schema.org.
    

# 3. Основная часть

## 3.1. Поиск, фильтрация и SEO как отдельный слой

В SmEl поиск, фильтрация и SEO строятся как единая подсистема, расположенная над каталогом товаров.

Подсистема использует данные:

- классификации каталога;
    
- характеристик товаров;
    
- коммерческих условий;
    
- медиа-контента.
    

Исходные данные при этом не изменяются.

```
Catalog
     │
     ├── Classification
     ├── Characteristics
     ├── Commercial Data
     ├── Media
     │
     ▼
 Search Engine
     │
     ├── Full-text Search
     ├── Filters
     ├── Sorting
     ├── Facets
     └── Suggestions
     │
     ▼
 SEO
     ├── URL
     ├── Meta Tags
     ├── Canonical URL
     ├── Breadcrumbs
     ├── Sitemap
     └── Structured Data
```

## 3.2. Назначение подсистемы

Подсистема обеспечивает:

- полнотекстовый поиск;
    
- поиск по артикулу;
    
- поиск по SKU;
    
- поиск по характеристикам;
    
- поиск по сериям и брендам;
    
- фильтрацию товаров;
    
- сортировку результатов;
    
- построение SEO-страниц;
    
- генерацию хлебных крошек;
    
- формирование sitemap;
    
- генерацию структурированных данных Schema.org.
    

# 4. Правила

1. Поиск не изменяет данные каталога.
    
2. Поиск и фильтрация работают только с опубликованными данными.
    
3. Фильтры формируются автоматически на основе доступных характеристик товаров.
    
4. Генерация фильтров является централизованной.
    
5. Единые правила фильтрации используются всеми клиентами системы.
    
6. SEO-страницы строятся на основе структуры и опубликованных данных каталога.
    
7. Навигация и хлебные крошки строятся по иерархии каталога.
    
8. URL должны быть человеко-понятными (`Human Readable URL`) и стабильными.
    
9. Каждая индексируемая страница должна иметь единственный канонический адрес (`canonical URL`).
    
10. Изменение внутренних идентификаторов (`SKU`) не должно автоматически изменять пользовательский URL.
    
11. SEO-данные не должны дублировать бизнес-логику каталога.
    
12. Изменение структуры каталога требует проверки URL, хлебных крошек и правил генерации SEO.
    
13. Поисковая подсистема должна предоставлять единые правила поиска и фильтрации для Web, REST API и будущих клиентских приложений.
    

## 4.1. Правила формирования URL

URL должны отражать структуру каталога и оставаться стабильными.

Примеры:

```
/showcase/category/group/type/configuration/execution/
/brand/series/
/product/{slug}/
```

Пользовательские URL не должны зависеть непосредственно от внутренних идентификаторов товара.

## 4.2. SEO-данные

Для каждой индексируемой страницы могут формироваться:

- `Title`;
    
- `Description`;
    
- `Keywords` — при необходимости;
    
- `Open Graph`;
    
- `BreadcrumbList`;
    
- `Product Schema`;
    
- `Canonical URL`;
    
- `Robots`;
    
- `Sitemap`.
    

SEO-данные могут задаваться вручную либо генерироваться автоматически на основании шаблонов.

# 5. Обоснование

Выделение поиска, фильтрации и SEO в отдельный слой выбрано по следующим причинам:

- разделение каталога и механизмов поиска;
    
- масштабируемость поисковой подсистемы;
    
- единый механизм фильтрации;
    
- оптимизация индексации поисковыми системами;
    
- поддержка больших каталогов товаров;
    
- независимое развитие SEO;
    
- возможность замены поискового механизма без изменения основных моделей каталога.
    

# 6. Последствия

## 6.1. Преимущества

- высокая производительность поиска;
    
- автоматическое построение фильтров;
    
- единообразная навигация по каталогу;
    
- улучшенная индексация поисковыми системами;
    
- готовность к подключению специализированных поисковых систем;
    
- возможность использования Elasticsearch, OpenSearch или другого поискового движка;
    
- независимое развитие поисковой и SEO-подсистем.
    

## 6.2. Ограничения

- поиск и фильтрация должны использовать только опубликованные данные;
    
- SEO-данные не должны дублировать бизнес-логику каталога;
    
- изменение структуры каталога требует проверки связанных URL и SEO-правил;
    
- генерация фильтров должна быть централизованной;
    
- единые правила поиска и фильтрации должны использоваться Web, REST API и будущими клиентскими приложениями;
    
- конкретный поисковый движок данным решением не определяется.

# 8. Заключительные положения

Настоящее решение определяет поиск, фильтрацию и SEO как **отдельный слой**, расположенный над каталогом товаров.

Такое разделение позволяет:

- развивать поисковый механизм независимо от структуры каталога;
    
- подключать специализированные поисковые движки без изменения основных бизнес-моделей;
    
- автоматически формировать фильтры и SEO-страницы на основе существующих данных;
    
- обеспечивать единые правила поиска и навигации для веб-интерфейса, REST API и будущих клиентских приложений.
    

Подсистема сохраняет минимальную связанность с источниками данных и не изменяет исходные данные каталога.
