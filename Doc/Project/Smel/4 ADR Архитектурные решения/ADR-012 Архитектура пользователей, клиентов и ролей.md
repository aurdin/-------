# 1. Назначение

Настоящее архитектурное решение определяет принцип организации пользователей, клиентов и ролей в проекте **Smart Electric (SmEl)**.

Решение фиксирует разделение трех независимых понятий:

- **User** — учетная запись, используемая для аутентификации и авторизации;
    
- **Customer** — физическое или юридическое лицо, участвующее в коммерческих операциях;
    
- **Role** — набор прав доступа к функциям системы.
    

# 2. Область применения

Решение применяется к подсистеме управления:

- пользователями;
    
- клиентами;
    
- ролями;
    
- правами доступа;
    
- профилями;
    
- коммерческими связями клиента;
    
- аутентификацией и авторизацией.
    

Подсистема является самостоятельной и не должна смешивать учетные записи пользователей с коммерческими сущностями клиентов.

# 3. Основная часть

## 3.1. Разделение User, Customer и Role

В SmEl пользователь, клиент и роль являются различными сущностями с разными зонами ответственности.

```
User
   │
   ├── Authentication
   ├── Profile
   ├── Roles
   └── Permissions

            │

Customer
   ├── Individual
   ├── Company
   ├── Addresses
   ├── Contacts
   ├── Price Group
   └── Orders

            │

Role
   ├── Permissions
   ├── Access Rules
   └── System Functions
```

## 3.2. Пользователь

`User` представляет учетную запись, посредством которой субъект взаимодействует с системой.

Пользователь используется для:

- аутентификации;
    
- авторизации;
    
- хранения профиля;
    
- назначения ролей;
    
- проверки прав доступа.
    

## 3.3. Клиент

`Customer` представляет физическое или юридическое лицо, являющееся участником коммерческих отношений.

Клиент может иметь:

- тип клиента;
    
- адреса;
    
- контактные данные;
    
- коммерческую группу;
    
- коммерческие условия;
    
- связанные заказы.
    

## 3.4. Роль

`Role` определяет набор прав доступа к функциям системы.

Ролевая модель основана на принципе **RBAC (Role-Based Access Control)**.

# 4. Правила

1. `User` и `Customer` являются разными сущностями.
    
2. Один `User` может быть связан с одним или несколькими `Customer`.
    
3. Один `Customer` может иметь нескольких связанных `User`.
    
4. Такая модель поддерживает сценарии работы нескольких сотрудников от имени одной организации.
    
5. Права доступа определяются ролями, а не типом клиента.
    
6. Коммерческие условия назначаются клиенту, а не пользователю.
    
7. Роли не должны использоваться для определения коммерческих условий.
    
8. Все проверки доступа выполняются через централизованный механизм авторизации.
    
9. Аутентификация и авторизация реализуются средствами Django и Django REST Framework.
    
10. Перечень ролей может расширяться без изменения базовой архитектуры.
    
11. Связи между `User` и `Customer` должны сохранять целостность данных.
    
12. Архитектура должна поддерживать сценарии **«один пользователь — несколько клиентов»** и **«один клиент — несколько пользователей»**.
    

## 4.1. Системные роли

Архитектура предусматривает следующие примеры ролей:

```
Administrator
Manager
Sales Manager
Content Manager
Warehouse Manager
Customer
Guest
API Client
```

Перечень ролей не является закрытым и может расширяться без изменения архитектурного принципа RBAC.

# 5. Обоснование

Разделение пользователей, клиентов и ролей выбрано по следующим причинам:

- разделение учетных записей и коммерческих сущностей;
    
- поддержка B2C- и B2B-сценариев;
    
- возможность работы нескольких сотрудников от имени одной компании;
    
- гибкое управление правами доступа;
    
- независимое развитие подсистем безопасности и коммерции;
    
- подготовка к интеграции с внешними системами авторизации.
    

# 6. Последствия

## 6.1. Преимущества

- независимое развитие подсистем безопасности и коммерции;
    
- поддержка различных моделей клиентов: частные лица, организации, партнеры;
    
- централизованное управление правами доступа;
    
- возможность назначения персональных коммерческих условий клиентам;
    
- масштабирование при добавлении новых ролей и типов клиентов;
    
- возможность использования одной учетной записи в различных коммерческих контекстах.
    

## 6.2. Ограничения

- бизнес-логика не должна использовать роли для определения коммерческих условий;
    
- проверки доступа должны выполняться через централизованный механизм авторизации;
    
- связи между `User` и `Customer` должны сохранять целостность;
    
- конкретная модель коммерческих групп, лимитов и персональных условий определяется отдельными архитектурными решениями;
    
- конкретные механизмы интеграции с внешними системами авторизации определяются отдельными решениями.

# 8. Заключительные положения

Настоящее решение фиксирует архитектурное разделение между:

- **User** — субъектом, выполняющим вход и взаимодействующим с системой;
    
- **Customer** — участником коммерческих отношений;
    
- **Role** — механизмом управления доступом.
    

Такое разделение обеспечивает поддержку B2C- и B2B-моделей, позволяет нескольким пользователям работать с одним клиентом и соответствует принципам **Separation of Concerns** и **RBAC**.

Конкретная реализация коммерческих условий, механизмов авторизации, клиентских групп и интеграции с внешними системами определяется отдельными архитектурными решениями.
