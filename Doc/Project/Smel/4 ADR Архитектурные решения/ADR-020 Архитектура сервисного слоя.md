# 1. Назначение

Настоящее архитектурное решение определяет принципы построения сервисного слоя проекта **Smart Electric (SmEl)**.

Сервисный слой является центральным уровнем реализации бизнес-логики и обеспечивает взаимодействие между REST API, доменной моделью, моделями Django ORM и внешними интеграциями.

# 2. Область применения

Решение применяется ко всем бизнес-операциям проекта **Smart Electric (SmEl)**, выполняемым через Backend.

В область применения входят:

- реализация бизнес-процессов;
    
- выполнение бизнес-правил;
    
- взаимодействие между доменными областями;
    
- управление транзакциями;
    
- работа с моделями Django ORM;
    
- использование SQL-представлений;
    
- взаимодействие с внешними системами;
    
- подготовка результатов для REST API.
    

# 3. Основная часть

## 3.1. Контекст

В предыдущих архитектурных решениях определены:

- трехуровневая архитектура системы — ADR-001;
    
- структура Django-приложений — ADR-002;
    
- организация базы данных PostgreSQL — ADR-003;
    
- архитектура API — ADR-017;
    
- доменная модель данных — ADR-018;
    
- физическая модель данных PostgreSQL и Django ORM — ADR-019.
    

Настоящее решение определяет место бизнес-логики в архитектуре проекта.

## 3.2. Архитектурное решение

Вся бизнес-логика проекта реализуется в сервисном слое.

Сервисный слой располагается между REST API и моделями Django ORM и является единственной точкой выполнения бизнес-операций.

Общая структура взаимодействия:

```
Frontend (Vue 3)
        │
        ▼
REST API (DRF)
        │
        ▼
Service Layer
        │
 ┌──────┼──────┐
 ▼      ▼      ▼
ORM   dbview  External Services
        │
        ▼
 PostgreSQL
```

Сервисный слой не зависит от пользовательского интерфейса и не должен содержать код представления данных.

# 4. Правила

## 4.1. Ответственность сервисного слоя

Сервисный слой отвечает за:

- реализацию бизнес-процессов;
    
- проверку бизнес-правил;
    
- управление транзакциями;
    
- взаимодействие между доменами;
    
- объединение технических и коммерческих данных;
    
- подготовку данных для REST API;
    
- интеграцию с внешними системами.
    

## 4.2. Принципы построения

При разработке сервисного слоя необходимо соблюдать следующие принципы:

- одна бизнес-операция — один сервис;
    
- один сервис — одна ответственность;
    
- сервисы не зависят от пользовательского интерфейса;
    
- сервисы не содержат код представления данных;
    
- сервисы не обращаются напрямую к HTTP-запросам и HTTP-ответам;
    
- сервисы используют модели Django ORM, SQL-представления и другие сервисы через определённые интерфейсы;
    
- бизнес-логика не должна дублироваться в различных слоях системы.
    

## 4.3. Взаимодействие компонентов

REST API вызывает сервисный слой.

Сервисный слой:

- получает данные из моделей Django ORM;
    
- использует SQL-представления `dbview` для операций чтения;
    
- объединяет данные различных доменов;
    
- управляет транзакциями;
    
- выполняет бизнес-правила;
    
- возвращает результат вызывающему уровню API.
    

Модели Django ORM не должны содержать сложной бизнес-логики.

## 4.4. Структура сервисов

Каждая предметная область реализуется собственным набором сервисов.

Примеры:

- Catalog Service;
    
- Product Service;
    
- Price Service;
    
- Stock Service;
    
- Customer Service;
    
- Cart Service;
    
- Order Service;
    
- Media Service;
    
- Search Service;
    
- Import Service.
    

Конкретная структура и состав сервисов могут уточняться на этапе реализации при сохранении установленных архитектурных границ.

## 4.5. Управление транзакциями

Все операции, изменяющие данные нескольких сущностей, должны выполняться в рамках транзакций.

Границы транзакций определяются сервисным слоем.

Сервис отвечает за целостность бизнес-операции и корректное завершение либо откат соответствующей транзакции.

## 4.6. Обработка ошибок

Сервисный слой отвечает за:

- обработку бизнес-исключений;
    
- преобразование внутренних ошибок в понятные сообщения для API;
    
- ведение журналов ошибок;
    
- сохранение целостности данных при возникновении исключений.
    

# 5. Ограничения

Запрещается:

- размещать сложную бизнес-логику в моделях Django;
    
- реализовывать бизнес-логику непосредственно в представлениях DRF;
    
- обращаться к базе данных напрямую из Frontend;
    
- смешивать бизнес-логику и код пользовательского интерфейса;
    
- обходить сервисный слой при выполнении бизнес-операций изменения данных;
    
- дублировать одну и ту же бизнес-логику в нескольких слоях системы.
    

# 6. Причины выбора

Выбранная архитектура обеспечивает:

- разделение ответственности;
    
- независимость пользовательского интерфейса;
    
- повторное использование бизнес-логики;
    
- упрощение тестирования;
    
- централизованное управление бизнес-процессами;
    
- снижение связанности компонентов;
    
- единый механизм взаимодействия между доменными областями.
    

# 7. Последствия

## 7.1. Преимущества

- единая точка реализации бизнес-логики;
    
- простота сопровождения;
    
- высокая тестируемость;
    
- возможность повторного использования сервисов;
    
- готовность к интеграции с внешними системами;
    
- независимость бизнес-логики от конкретного API или пользовательского интерфейса.
    

## 7.2. Ограничения

- все бизнес-операции должны реализовываться через сервисный слой;
    
- обход сервисного слоя при изменении данных не допускается;
    
- изменение бизнес-правил должно выполняться исключительно в соответствующих сервисах;
    
- добавление новых сервисов должно соответствовать установленным доменным границам.
