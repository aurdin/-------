# 1. Назначение

Настоящее архитектурное решение определяет общую архитектуру доставки в проекте SmEl.

Документ устанавливает границы подсистемы доставки, её связь с заказом, клиентом, адресом, способом доставки и внешними службами доставки.

Конкретные службы доставки, провайдеры, протоколы интеграции и физическая реализация подсистемы настоящим решением не фиксируются.

# 2. Область применения

Решение применяется к операциям доставки, связанным с оформлением и исполнением заказа.

В область входят:

- выбор способа доставки;
    
- определение адреса доставки;
    
- расчёт или получение стоимости доставки;
    
- фиксация выбранного способа доставки в заказе;
    
- передача данных внешнему провайдеру доставки;
    
- получение статуса доставки;
    
- отслеживание доставки;
    
- изменение статуса доставки;
    
- завершение доставки.
    

Решение распространяется на взаимодействие Frontend, Backend, Service Layer, Order и внешних служб доставки.

# 3. Основная часть

## 3.1. Общие принципы

Доставка является отдельной предметной областью и не должна смешиваться с каталогом, корзиной, оплатой или складским учётом.

Заказ и доставка являются связанными, но самостоятельными сущностями.

Заказ фиксирует выбранные условия доставки, а подсистема доставки отвечает за выполнение и сопровождение процесса доставки.

Backend является источником истины для внутреннего состояния доставки.

## 3.2. Архитектурная структура

Общий поток доставки:

```
Frontend (Vue 3)
        │
        ▼
REST API
        │
        ▼
Service Layer
        │
   ┌────┴─────┐
   ▼          ▼
 Order     Delivery
 Service    Service
              │
              ▼
      Delivery Integration
              │
              ▼
    External Delivery Provider
```

Frontend взаимодействует с доставкой только через REST API.

Доступ к данным доставки и изменение её состояния выполняются через Backend и Service Layer.

Прямое взаимодействие Frontend с внешними службами доставки не допускается.

## 3.3. Способ доставки

Способ доставки является отдельным объектом коммерческой и операционной информации.

Способ доставки может определять:

- тип доставки;
    
- доступность для определённых регионов;
    
- сроки;
    
- стоимость;
    
- ограничения;
    
- требования к адресу или получателю;
    
- необходимость интеграции с внешним оператором.
    

Конкретный набор параметров определяется последующими архитектурными и предметными решениями.

## 3.4. Адрес доставки

Адрес доставки является отдельной сущностью и не должен дублироваться в каждом связанном объекте без необходимости.

При оформлении заказа выбранный адрес должен быть зафиксирован в составе данных заказа или связанной с ним записи доставки таким образом, чтобы последующее изменение адреса клиента не изменяло исторические данные уже оформленного заказа.

## 3.5. Стоимость доставки

Стоимость доставки относится к коммерческим условиям оформления заказа.

Она может зависеть от:

- способа доставки;
    
- региона;
    
- адреса;
    
- веса или объёма заказа;
    
- стоимости заказа;
    
- условий клиента;
    
- действующих коммерческих правил;
    
- внешнего тарифа службы доставки.
    

Актуальная стоимость должна определяться Backend.

После оформления заказа стоимость доставки должна быть зафиксирована и не должна произвольно изменяться вследствие последующих изменений тарифов.

## 3.6. Жизненный цикл доставки

Доставка имеет собственный жизненный цикл.

Обобщённая последовательность:

```
Created
   ↓
Planned / Selected
   ↓
Prepared
   ↓
Handed Over
   ↓
In Transit
   ↓
Delivered
```

Дополнительные состояния, включая отмену, возврат или ошибку доставки, определяются отдельным решением.

Состояние доставки не должно определяться только состоянием Frontend.

## 3.7. Интеграция с внешними службами

При использовании внешнего оператора доставки взаимодействие осуществляется через отдельный Integration Layer.

```
Delivery Service
       │
       ▼
Integration Layer
       │
       ▼
External Delivery Provider
```

Внешняя система может предоставлять:

- тариф;
    
- доступные способы доставки;
    
- идентификатор отправления;
    
- статус отправления;
    
- информацию об отслеживании;
    
- подтверждение доставки.
    

Данные внешнего провайдера не должны напрямую изменять внутренние сущности SmEl.

Полученные данные проходят через Backend и соответствующие сервисы.

## 3.8. Источник истины

Для внутренних бизнес-операций SmEl источником истины является Backend.

Внешний провайдер является источником результата своей внешней операции, но не внутренней бизнес-модели SmEl.

Backend должен проверять полученные от внешней системы данные перед изменением внутреннего состояния доставки.

## 3.9. Связь с заказом

После оформления заказа выбранные условия доставки становятся частью зафиксированного результата заказа.

Последующие изменения:

- каталога;
    
- цен;
    
- скидок;
    
- акций;
    
- способов доставки;
    
- тарифов;
    
- профиля клиента
    

не должны изменять исторические данные уже оформленного заказа.

Изменения, относящиеся непосредственно к исполнению доставки, должны отражаться в сущности доставки и её истории.

# 4. Правила

1. Доставка является самостоятельной предметной областью.
    
2. Заказ и доставка являются разными сущностями.
    
3. Frontend не взаимодействует с внешними службами доставки напрямую.
    
4. Все бизнес-операции доставки выполняются через Service Layer.
    
5. Backend является источником истины для внутреннего состояния доставки.
    
6. Внешний провайдер не получает прямого доступа к базе данных SmEl.
    
7. Полученные от провайдера данные проходят через Integration Layer и Backend.
    
8. Выбранный способ доставки фиксируется при оформлении заказа.
    
9. Стоимость доставки должна быть определена и зафиксирована в составе результата оформления заказа.
    
10. Исторические данные оформленного заказа не должны зависеть от последующих изменений актуальных тарифов.
    
11. Адрес оформленного заказа должен сохраняться независимо от последующих изменений адресных данных клиента.
    
12. Состояние доставки должно иметь собственный жизненный цикл.
    
13. Изменение состояния доставки должно выполняться контролируемым Backend процессом.
    
14. Повторная обработка внешних событий доставки не должна приводить к некорректному повторному выполнению бизнес-операций.
    
15. Конкретный провайдер доставки, протокол интеграции и технический механизм обмена определяются отдельными решениями.

# 6. Заключительные положения

Настоящее решение фиксирует архитектурную модель доставки SmEl на уровне границ, ответственности, жизненного цикла и интеграции.

Конкретные службы доставки, тарифные алгоритмы, форматы интеграции, правила выбора провайдера, механизмы расчёта сроков и техническая реализация отслеживания доставки остаются предметом последующих архитектурных решений.
