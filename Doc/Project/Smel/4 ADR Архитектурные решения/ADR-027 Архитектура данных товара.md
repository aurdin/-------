# 1. Назначение

Настоящее архитектурное решение определяет принципы организации, хранения и использования данных товара в проекте SmEl.

Документ устанавливает границы товарных данных, разделение технических, классификационных, коммерческих и медийных данных, а также правила идентификации и актуализации товара.

# 2. Область применения

Решение применяется к данным товарных позиций, используемым:

- каталогом;
    
- поиском и фильтрацией;
    
- корзиной;
    
- оформлением заказа;
    
- ценообразованием;
    
- складским учетом;
    
- импортом и синхронизацией;
    
- медиа-контентом;
    
- SEO;
    
- административными функциями.
    

Решение не определяет физическую структуру всех таблиц PostgreSQL и конкретную реализацию Django-моделей.

# 3. Основная часть

## 3.1. Основные принципы

Данные товара должны быть отделены от коммерческих и операционных данных.

Товарная сущность содержит сведения, характеризующие сам товар, но не должна непосредственно хранить изменяемые:

- цены;
    
- скидки;
    
- акции;
    
- остатки;
    
- резервы;
    
- заказы;
    
- платежи;
    
- доставки.
    

Коммерческие данные определяются архитектурой ценообразования, складские — архитектурой запасов.

## 3.2. Структура товарных данных

Основная модель:

```
Product / SKU
    │
    ├── Classification
    │     ├── Category
    │     ├── Group
    │     ├── Type
    │     ├── Configuration
    │     └── Execution
    │
    ├── Characteristics
    │
    ├── Brand
    │     └── Series
    │
    ├── Media
    │
    └── SEO
```

SKU является стабильным внутренним идентификатором товарной позиции.

Артикул производителя является внешним коммерческим идентификатором и не используется как основной внутренний ключ.

## 3.3. Классификационные данные

Товарная позиция должна быть связана с классификационной иерархией:

**Category → Group → Type → Configuration → Execution → SKU**

Каждая позиция должна находиться в соответствующей части иерархии согласно правилам каталога.

Brand и Series являются отдельными классификационными признаками и не заменяют основную иерархию.

## 3.4. Характеристики товара

Характеристики товара реализуются независимо от основной сущности Product/SKU.

Используется универсальная модель:

```
Characteristic Group
        │
        ▼
Characteristic
        │
        ▼
Characteristic Value
        │
        ▼
Product / SKU
```

Такой подход позволяет добавлять новые технические характеристики без изменения базовой структуры товара.

Для характеристик с фиксированным набором значений могут использоваться общие справочники.

Характеристики должны поддерживать использование в:

- карточке товара;
    
- фильтрации;
    
- поиске;
    
- сравнении;
    
- техническом описании.
    

## 3.5. Идентификация товара

Для товарной позиции используются отдельные идентификаторы:

- внутренний SKU;
    
- артикул производителя;
    
- EAN/GTIN при наличии.
    

SKU должен быть стабильным и уникальным в пределах SmEl.

Артикул может использоваться для обмена с производителем или поставщиком и не должен использоваться как основной идентификатор внутренних связей.

EAN/GTIN хранится отдельно от SKU и артикула.

## 3.6. Локализация

Товарные данные, предназначенные для отображения пользователю, должны поддерживать обязательные языки:

- украинский (`uk`);
    
- русский (`ru`);
    
- английский (`en`).
    

Локализуются, в частности:

- название;
    
- описание;
    
- маркетинговые тексты;
    
- названия характеристик;
    
- значения характеристик;
    
- элементы классификации, если они отображаются пользователю.
    

Backend отвечает за выбор и предоставление локализованного значения.

Frontend не должен самостоятельно выбирать поле `name_uk`, `name_ru` или `name_en` при наличии централизованного механизма локализации API.

## 3.7. Актуальность данных

Товарные данные должны иметь управляемое состояние актуальности.

Изменения данных товара могут поступать:

- вручную через административный интерфейс;
    
- через импорт;
    
- через интеграцию с внешними источниками;
    
- посредством внутренних сервисов.
    

Изменение данных должно проходить через установленные бизнес-правила.

История изменений должна сохраняться там, где это необходимо для аудита, синхронизации или восстановления состояния.

## 3.8. Разделение товарных и коммерческих данных

Следующие данные не являются частью основной товарной сущности:

- текущая стоимость;
    
- скидка;
    
- акция;
    
- итоговая коммерческая стоимость;
    
- остаток;
    
- резерв;
    
- доступное количество;
    
- склад.
    

Они предоставляются соответствующими доменами.

Таким образом, карточка товара может объединять данные нескольких доменов при чтении, но это не означает объединения их ответственности.

## 3.9. Формирование товарной карточки

Товарная карточка является представлением, формируемым Backend из нескольких источников данных.

Обобщённо:

```
Product / SKU
    │
    ├── Catalog Data
    ├── Characteristics
    ├── Commercial Data
    ├── Stock Data
    ├── Media
    └── SEO
            │
            ▼
      Product View / API
            │
            ▼
       Frontend
```

Frontend получает готовое представление через REST API и не должен самостоятельно объединять первичные источники бизнес-данных.

## 3.10. Импорт данных товара

Импорт товарных данных выполняется через отдельный интеграционный контур.

Поступающие данные должны проходить:

**Validation → Mapping → Transformation → Synchronization**

Импорт не должен напрямую изменять произвольные внутренние сущности в обход бизнес-правил.

Идентификация импортируемой позиции выполняется согласно правилам SKU, Article и EAN/GTIN.

# 4. Правила

1. Product/SKU является основной сущностью товарной позиции.
    
2. SKU является стабильным внутренним идентификатором.
    
3. Article является внешним идентификатором производителя и не заменяет SKU.
    
4. EAN/GTIN хранится отдельно от SKU и Article.
    
5. Основная иерархия товара: Category → Group → Type → Configuration → Execution → SKU.
    
6. Brand и Series не заменяют основную иерархию каталога.
    
7. Технические данные товара отделяются от коммерческих условий.
    
8. Цена, скидка и акция относятся к pricing block и не должны храниться как текущие значения непосредственно в Product/SKU.
    
9. Остатки и резервы не являются частью основной товарной сущности.
    
10. Характеристики должны быть реализованы независимо от основной структуры Product/SKU.
    
11. Добавление новой характеристики не должно требовать изменения базовой структуры товара.
    
12. Локализованные данные должны поддерживать `uk`, `ru`, `en`.
    
13. Backend отвечает за предоставление локализованных данных.
    
14. Frontend не является источником товарных данных.
    
15. Товарные данные изменяются только через контролируемые Backend-механизмы.
    
16. Импорт товарных данных выполняется через Integration Layer.
    
17. Товарная карточка может объединять данные нескольких доменов только на уровне представления.
    
18. Объединение данных в API не должно объединять ответственность соответствующих доменов.
    
19. Исторические данные, необходимые для аудита и бизнес-процессов, должны сохраняться независимо от текущего состояния товара.
    
20. Конкретная физическая реализация моделей и таблиц определяется ADR-019 и последующими техническими решениями.

# 6. Заключительные положения

Настоящее решение фиксирует архитектурные принципы организации данных товара SmEl и границы между товарными, коммерческими, складскими, медийными и SEO-данными.

Конкретные физические модели, поля, индексы, механизмы версионирования и реализации хранения локализованных данных определяются отдельными техническими решениями.
