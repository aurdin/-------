# 1. Назначение

Настоящее архитектурное решение определяет общие принципы организации оплаты заказов в проекте **Smart Electric (SmEl)**.

Решение устанавливает архитектурные границы между заказом, платежом, Backend и внешними платёжными системами.

# 2. Область применения

Решение применяется к:

- заказам;
    
- платежам;
    
- способам оплаты;
    
- состояниям платежа;
    
- взаимодействию Backend с платёжными системами;
    
- обработке результатов оплаты;
    
- возвратам денежных средств в части их архитектурной связи с платежом.
    

Конкретный платёжный провайдер и используемый платёжный протокол настоящим ADR не фиксируются.

# 3. Основная часть

## 3.1. Архитектурное разделение

Заказ и платёж являются различными сущностями.

`Order` фиксирует результат оформления покупки.

`Payment` отражает финансовую операцию, связанную с заказом.

Общая архитектурная цепочка:

```
Customer
    │
    ▼
  Order
    │
    ▼
 Payment
    │
    ▼
Payment Service
    │
    ▼
External Payment Provider
```

Платёж не должен изменять исходные данные заказа.

## 3.2. Payment

`Payment` является самостоятельной сущностью домена продаж.

Платёж должен иметь собственный идентификатор и состояние.

К платежу могут относиться:

- Order;
    
- сумма;
    
- валюта;
    
- способ оплаты;
    
- статус;
    
- внешний идентификатор платёжной операции;
    
- дата создания;
    
- дата изменения;
    
- информация о результате операции.
    

Конкретный состав физических полей определяется на этапе реализации.

## 3.3. Связь Order и Payment

Один `Order` может иметь связанные платёжные операции в зависимости от сценария оплаты.

Например, это может потребоваться при:

- повторной попытке оплаты;
    
- отменённой операции;
    
- неуспешной операции;
    
- возврате;
    
- частичной оплате, если такой сценарий будет принят.
    

Поэтому `Payment` не должен использоваться как простое поле `paid = true/false` внутри `Order`.

## 3.4. Состояние платежа

Платёж проходит управляемый жизненный цикл.

Логически могут использоваться состояния:

```
Created
   │
   ▼
Pending
   │
 ┌─┴─────────────┐
 ▼               ▼
Paid           Failed
 │               │
 ▼               ▼
Refunded       Cancelled
```

Фактический набор состояний и переходов уточняется при проектировании платёжного процесса.

Состояние платежа должно изменяться контролируемым Backend-механизмом.

## 3.5. Источник истины

Backend SmEl является источником истины для внутреннего состояния заказа и платежа.

Внешний платёжный провайдер является источником результата внешней платёжной операции.

Полученный от провайдера результат должен быть проверен Backend перед изменением состояния внутреннего `Payment`.

Frontend не должен самостоятельно устанавливать успешность оплаты.

## 3.6. Взаимодействие с платёжным провайдером

Внешняя платёжная система взаимодействует с SmEl через Backend.

Frontend не должен обращаться непосредственно к внутренним бизнес-сервисам или базе данных.

Архитектурная схема:

```
Vue 3
  │
  ▼
REST API
  │
  ▼
Payment Service
  │
  ▼
Payment Integration
  │
  ▼
External Payment Provider
```

Для получения результата операции может использоваться возврат пользователя, серверное уведомление провайдера или иной предусмотренный механизм.

Окончательное состояние платежа должно определяться Backend.

## 3.7. Безопасность платежных данных

SmEl не должен хранить платёжные данные, которые не требуются для выполнения бизнес-операций и которые должны обрабатываться непосредственно платёжным провайдером.

Чувствительные платёжные данные должны обрабатываться в соответствии с требованиями выбранного платёжного решения.

Внутренняя система должна хранить только необходимые для учёта платежа сведения.

## 3.8. Идемпотентность

Операции создания и обработки платежей должны быть устойчивы к повторной доставке запросов и уведомлений.

Повторное получение одного и того же внешнего события не должно приводить к повторному выполнению финансовой операции или некорректному изменению состояния заказа.

Конкретный механизм идемпотентности определяется при реализации интеграции.

## 3.9. Возврат денежных средств

Возврат денежных средств рассматривается как отдельная операция, связанная с исходным платежом.

Возврат не должен изменять исторические данные исходной платёжной операции.

Результат возврата должен фиксироваться отдельно.

Правила и сценарии возвратов могут быть уточнены отдельным архитектурным решением.

# 4. Правила

1. `Order` и `Payment` являются различными сущностями.
    
2. Платёж имеет собственный идентификатор и жизненный цикл.
    
3. Состояние платежа изменяется только контролируемыми Backend-операциями.
    
4. Frontend не является источником истины для состояния платежа.
    
5. Backend проверяет результаты внешних платёжных операций.
    
6. Прямое взаимодействие Frontend с внутренней платёжной бизнес-логикой не допускается.
    
7. Платёжные операции выполняются через соответствующий сервисный слой.
    
8. Внешний платёжный провайдер взаимодействует со SmEl через Backend.
    
9. Повторная обработка одного внешнего события не должна приводить к повторной финансовой операции.
    
10. История платёжных операций должна сохраняться.
    
11. Возврат является отдельной операцией и не должен уничтожать данные исходного платежа.
    
12. Чувствительные платёжные данные не должны храниться в SmEl без архитектурной необходимости.
    
13. Внутреннее состояние `Order` не должно изменяться только на основании недоверенного клиентского сообщения.
    
14. Конкретный платёжный провайдер выбирается отдельным архитектурным решением.
    
15. Конкретный протокол, формат уведомлений и механизм проверки подписи провайдера определяются отдельным решением.
    
16. Правила возвратов и частичных оплат могут определяться отдельными архитектурными решениями.

# 6. Заключительные положения

В SmEl оплата является самостоятельной частью домена продаж и отделена от сущности `Order`.

Backend является источником истины для внутреннего состояния заказа и платежа, а взаимодействие с внешними платёжными системами осуществляется через интеграционный и сервисный уровни.

Платёжные операции должны быть контролируемыми, идемпотентными и иметь сохраняемую историю.

Конкретный платёжный провайдер, протокол взаимодействия и детальные правила обработки платежей определяются последующими архитектурными решениями.
