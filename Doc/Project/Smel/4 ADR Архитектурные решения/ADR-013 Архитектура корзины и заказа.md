# 1. Назначение

Настоящее архитектурное решение определяет принцип организации корзины (`Cart`) и заказа (`Order`) в проекте **Smart Electric (SmEl)**.

Решение фиксирует их как самостоятельные сущности с различными жизненными циклами и определяет переход от выбранных товаров к оформленному заказу.

# 2. Область применения

Решение применяется к процессам:

- формирования корзины;
    
- изменения содержимого корзины;
    
- расчета стоимости;
    
- проверки доступности товаров;
    
- оформления покупки;
    
- создания заказа;
    
- изменения статусов заказа;
    
- хранения истории заказов.
    

Решение распространяется на гостевых и авторизованных покупателей.

# 3. Основная часть

## 3.1. Разделение Cart и Order

В SmEl `Cart` и `Order` являются самостоятельными сущностями.

**Cart** представляет временное состояние выбора покупателя и может изменяться пользователем.

**Order** представляет зафиксированный результат оформления покупки и является частью коммерческой истории системы.

Создание заказа осуществляется путем формирования нового объекта `Order` на основании содержимого корзины.

## 3.2. Жизненный цикл

```
Guest / User
      │
      ▼
   Cart
      │
      ├── Добавление товара
      ├── Изменение количества
      ├── Удаление товара
      ├── Расчет стоимости
      └── Проверка доступности
              │
              ▼
        Checkout
              │
              ▼
      Order
              │
              ├── New
              ├── Confirmed
              ├── Paid
              ├── Processing
              ├── Shipped
              ├── Delivered
              ├── Cancelled
              └── Returned
```

## 3.3. Жизненный цикл корзины

Корзина может существовать без авторизации пользователя.

Для авторизованного клиента корзина сохраняется между сеансами.

Для гостя корзина существует только в рамках текущей сессии.

Корзина создается автоматически при первом добавлении товара.

Один пользователь может иметь только одну активную корзину.

## 3.4. Состав корзины

Корзина содержит:

- товары (`SKU`);
    
- количество;
    
- рассчитанную стоимость;
    
- примененные скидки;
    
- выбранную валюту;
    
- временные коммерческие условия.
    

Данные корзины не являются финансовым документом и не заменяют данные заказа.

## 3.5. Формирование заказа

При оформлении покупки содержимое корзины проходит этап `Checkout`, после чего на его основании создается новый `Order`.

Заказ фиксирует состояние покупки на момент оформления.

После создания заказа его данные не зависят от последующих изменений:

- каталога;
    
- характеристик товара;
    
- актуальных цен;
    
- скидок;
    
- акций;
    
- складских остатков.
    

## 3.6. Состав заказа

Заказ фиксирует:

- перечень товаров;
    
- количество;
    
- цену каждой позиции;
    
- скидки;
    
- итоговую стоимость;
    
- данные клиента;
    
- адреса доставки и оплаты;
    
- выбранный способ доставки;
    
- выбранный способ оплаты;
    
- историю изменения статусов.
    

# 4. Правила

1. `Cart` и `Order` являются различными сущностями.
    
2. Корзина может существовать без авторизации пользователя.
    
3. Корзина создается автоматически при первом добавлении товара.
    
4. Один пользователь может иметь только одну активную корзину.
    
5. Корзина авторизованного клиента сохраняется между сеансами.
    
6. Гостевая корзина существует только в рамках текущей сессии.
    
7. Содержимое корзины может изменяться до начала оформления заказа.
    
8. Перед созданием заказа выполняется проверка актуальности коммерческих условий и доступности товаров.
    
9. Создание `Order` выполняется на основании состояния корзины и результата `Checkout`.
    
10. После создания заказа его зафиксированные коммерческие данные не изменяются вследствие изменений каталога, цен или остатков.
    
11. Корзина не является финансовым документом.
    
12. Изменения заказа выполняются только в рамках определенных бизнес-процессов.
    
13. Изменения статусов заказа выполняются через централизованный механизм.
    
14. История изменения статусов заказа должна сохраняться.
    
15. Конкретные правила резервирования, оплаты, доставки, возврата и отмены определяются отдельными архитектурными решениями.
    

# 5. Обоснование

Разделение `Cart` и `Order` выбрано по следующим причинам:

- разделение временных и постоянных данных;
    
- сохранение истории покупок;
    
- независимость заказов от последующих изменений каталога и цен;
    
- поддержка гостевых заказов;
    
- поддержка сохранения корзины авторизованного клиента;
    
- подготовка к интеграции с CRM, ERP и платежными системами;
    
- четкое разделение процессов выбора товара и совершения покупки.
    

# 6. Последствия

## 6.1. Преимущества

- четкое разделение процессов выбора и покупки;
    
- сохранение зафиксированной истории заказов;
    
- возможность восстановления брошенных корзин;
    
- поддержка различных способов оплаты и доставки;
    
- упрощение интеграции с внешними сервисами;
    
- возможность расширения жизненного цикла заказа без изменения базовой архитектуры;
    
- независимость заказа от последующих изменений каталога и коммерческих данных.
    

## 6.2. Ограничения

- после создания заказа изменения каталога, цен, характеристик и остатков не должны изменять зафиксированные данные заказа;
    
- корзина не используется для финансового учета;
    
- актуальность коммерческих условий и доступность товаров должны проверяться перед созданием заказа;
    
- изменения статусов заказа должны выполняться централизованно с фиксацией истории;
    
- конкретные сроки хранения и правила очистки корзины определяются отдельным архитектурным решением.

# 8. Заключительные положения

Настоящее решение фиксирует жизненный цикл покупки:

**SKU → Cart → Checkout → Order → Выполнение заказа.**

При этом:

- **каталог** отвечает за описание товаров;
    
- **коммерческий блок** — за актуальные цены и условия продажи;
    
- **складской блок** — за доступность товаров;
    
- **корзина** — за временный выбор покупателя;
    
- **Checkout** — за проверку и подготовку оформления;
    
- **заказ** — за фиксацию коммерческой операции и ее дальнейшее выполнение.
    

Такое разделение обеспечивает независимое развитие подсистем, надежное хранение истории заказов и готовность SmEl к интеграции с платежными, логистическими и учетными системами.
