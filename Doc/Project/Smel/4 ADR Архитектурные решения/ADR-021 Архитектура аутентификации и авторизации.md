# 1. Назначение

Настоящее архитектурное решение определяет общие принципы аутентификации и авторизации пользователей проекта **Smart Electric (SmEl)**.

Решение устанавливает архитектурные границы управления идентификацией пользователей, проверкой их полномочий и предоставлением доступа к ресурсам и операциям системы.

# 2. Область применения

Решение применяется ко всем компонентам SmEl, которые требуют идентификации пользователя или контроля доступа.

В область применения входят:

- Web-интерфейс Vue 3;
    
- REST API Django REST Framework;
    
- пользователи и клиенты;
    
- административные функции;
    
- роли и разрешения;
    
- защищённые бизнес-операции;
    
- внутренние и внешние API-клиенты.
    

Конкретные механизмы хранения учётных данных, формат токенов и внешние провайдеры идентификации настоящим решением не фиксируются.

# 3. Основная часть

## 3.1. Архитектурное разделение

В SmEl аутентификация и авторизация рассматриваются как два различных процесса.

**Аутентификация** определяет, кто выполняет запрос.

**Авторизация** определяет, имеет ли идентифицированный субъект право выполнить соответствующую операцию.

Общая архитектурная цепочка:

```
User / API Client
        │
        ▼
Authentication
        │
        ▼
Identity
        │
        ▼
Authorization
        │
        ▼
REST API
        │
        ▼
Service Layer
        │
        ▼
Business Operation
```

Проверка полномочий должна выполняться до выполнения защищённой бизнес-операции.

## 3.2. Пользователь и клиент

В соответствии с ADR-012 сущности **User** и **Customer** не объединяются.

**User** представляет учётную запись, используемую для аутентификации и доступа к системе.

**Customer** представляет физическое или юридическое лицо, участвующее в коммерческих операциях.

Авторизация пользователя определяется его полномочиями, а коммерческие условия определяются связанным с ним Customer.

## 3.3. Роли и разрешения

SmEl использует ролевую модель управления доступом.

Роль определяет набор разрешений, предоставляемых субъекту.

Примерные роли:

- Administrator;
    
- Manager;
    
- Sales Manager;
    
- Content Manager;
    
- Warehouse Manager;
    
- Customer;
    
- Guest;
    
- API Client.
    

Конкретный набор ролей может расширяться без изменения общей архитектуры авторизации.

Разрешения должны определяться исходя из выполняемых операций и ресурсов, а не только из интерфейсных элементов.

## 3.4. Уровни доступа

Архитектура предусматривает несколько категорий субъектов:

**Гость**

- не проходит аутентификацию;
    
- имеет доступ только к публичным ресурсам;
    
- может выполнять разрешённые операции гостевой корзины;
    
- не имеет доступа к защищённым данным пользователя.
    

**Аутентифицированный пользователь**

- имеет подтверждённую идентичность;
    
- получает доступ в соответствии со своими ролями и разрешениями;
    
- может выполнять доступные ему операции Customer.
    

**Административный или служебный пользователь**

- получает дополнительные права в соответствии с назначенной ролью;
    
- имеет доступ к административным и служебным операциям только в пределах предоставленных разрешений.
    

**API Client**

- является отдельным субъектом доступа;
    
- используется для взаимодействия внешних или внутренних систем с API;
    
- не должен автоматически получать права обычного пользователя.
    

## 3.5. Граница авторизации

REST API является контролируемой границей доступа к бизнес-функциям SmEl.

Frontend не должен самостоятельно определять, обладает ли пользователь правом выполнения бизнес-операции.

Frontend может скрывать или отображать элементы интерфейса в соответствии с известными ему правами, однако окончательное решение о доступе принимает Backend.

## 3.6. Авторизация бизнес-операций

Проверка прав должна выполняться на Backend до выполнения соответствующей бизнес-операции.

Service Layer является уровнем выполнения бизнес-операций в соответствии с ADR-020.

Авторизация не должна зависеть исключительно от проверки на уровне пользовательского интерфейса или URL.

Доступ к данным и операциям должен контролироваться независимо от конкретного клиента API.

# 4. Правила

1. Аутентификация и авторизация являются различными архитектурными функциями.
    
2. Backend является источником истины для идентификации и проверки прав доступа.
    
3. Frontend не является доверенной стороной при принятии решений об авторизации.
    
4. Все защищённые API-операции должны проходить проверку доступа.
    
5. Права доступа определяются ролями и разрешениями.
    
6. User и Customer остаются различными сущностями.
    
7. Коммерческие условия Customer не должны использоваться как механизм авторизации.
    
8. Гость имеет только публичные и явно разрешённые гостевые права.
    
9. API Client рассматривается как отдельный субъект доступа.
    
10. Авторизация должна применяться независимо от используемого клиентского интерфейса.
    
11. Обход механизмов авторизации при выполнении защищённых бизнес-операций не допускается.
    
12. Конкретный механизм аутентификации должен быть выбран отдельным архитектурным решением.
    
13. Конкретные механизмы хранения секретов, токенов и ключей безопасности не определяются настоящим ADR.
    
14. Расширение ролей и разрешений не должно нарушать установленные архитектурные границы.

# 6. Заключительные положения

В SmEl принимается архитектура, в которой аутентификация и авторизация являются централизованными функциями Backend.

REST API является контролируемой границей доступа, а Backend принимает окончательное решение о предоставлении доступа к защищённым ресурсам и бизнес-операциям.

Ролевая модель обеспечивает разделение полномочий между гостями, клиентами, административными пользователями и API-клиентами.

Конкретные технологии и механизмы реализации аутентификации, управления токенами, сессиями и секретами определяются последующими архитектурными решениями.
