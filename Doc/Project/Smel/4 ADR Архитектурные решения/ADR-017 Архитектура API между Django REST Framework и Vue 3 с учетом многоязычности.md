# 1. Назначение

Настоящее архитектурное решение определяет принципы построения API между Frontend на **Vue 3** и Backend на **Django REST Framework (DRF)** в проекте **Smart Electric (SmEl)**.

Решение устанавливает REST API как единый публичный интерфейс доступа к бизнес-логике и данным системы, а также закрепляет обязательную поддержку многоязычности.

# 2. Область применения

Решение распространяется на:

- Web-приложение Vue 3;
    
- будущие мобильные приложения;
    
- B2B-клиенты;
    
- административные интерфейсы;
    
- внешние API-интеграции;
    
- Backend на Django REST Framework;
    
- данные, передаваемые через API;
    
- локализацию данных и сообщений;
    
- импорт и экспорт данных;
    
- документацию API.
    

Поддержка украинского (`uk`), русского (`ru`) и английского (`en`) языков является обязательным архитектурным требованием для проекта SmEl.

# 3. Основная часть

## 3.1. Архитектура взаимодействия

Взаимодействие между клиентами и Backend осуществляется исключительно через REST API.

API является единственным публичным интерфейсом доступа к бизнес-логике и данным системы.

Логическая схема:

```
Vue 3 (Web)
Mobile App
B2B Client
Admin UI
External API
        │
        ▼
 REST API (JSON)
        │
        ▼
Django REST Framework
        │
        ▼
Business Services
        │
        ▼
PostgreSQL
```

API не зависит от конкретного клиентского приложения и проектируется по принципу **API First**.

## 3.2. Основные принципы API

- Frontend не обращается напрямую к базе данных.
    
- Вся бизнес-логика реализуется на Backend.
    
- Все данные передаются через REST API.
    
- Форматом обмена является JSON.
    
- API является версионируемым.
    
- Клиенты не должны зависеть от внутренней структуры базы данных.
    
- API должно быть единым для Web, мобильных приложений и внешних интеграций.
    
- Backend является единственным источником бизнес-данных и бизнес-логики.
    

# 4. Правила

## 4.1. Версионирование API

Все конечные точки API публикуются с указанием версии.

Пример:

```
/api/v1/
```

Изменения, нарушающие обратную совместимость, публикуются только в новой версии API.

Изменения, совместимые с существующими клиентами, могут выполняться в пределах текущей версии в соответствии с принятой политикой совместимости.

## 4.2. Структура API

API организуется по ресурсам предметной области.

Пример:

```
/api/v1/

catalog/
categories/
groups/
types/
configurations/
executions/
products/

prices/
stocks/

cart/
orders/

customers/
users/

search/
seo/
```

Конкретный состав конечных точек может расширяться без нарушения установленной архитектуры.

## 4.3. Формат успешных ответов

API использует единый формат успешных ответов.

Пример:

```
{
  "data": {
    ...
  },
  "meta": {
    ...
  }
}
```

Структура `meta` используется для дополнительной служебной информации, включая сведения о пагинации и другие метаданные ответа.

## 4.4. Формат ошибок

API использует единый формат сообщений об ошибках.

Пример:

```
{
  "error": {
    "code": "...",
    "message": "...",
    "details": []
  }
}
```

Формат ошибки должен обеспечивать однозначную идентификацию типа ошибки и возможность передачи дополнительных сведений.

## 4.5. Обязательная многоязычность

Проект поддерживает три языка:

- украинский (`uk`) — основной язык системы;
    
- русский (`ru`);
    
- английский (`en`).
    

Поддержка этих языков является обязательным архитектурным требованием для всего проекта SmEl.

Требование распространяется на:

- модели Django;
    
- справочники (`lists`);
    
- классификацию каталога;
    
- характеристики товаров;
    
- категории;
    
- группы;
    
- типы;
    
- конфигурации;
    
- исполнения;
    
- бренды и серии, где требуется локализация;
    
- SEO-данные;
    
- сообщения API;
    
- пользовательский интерфейс Vue;
    
- административную панель;
    
- импорт и экспорт данных;
    
- документацию API.
    

## 4.6. Определение языка

Язык ответа API определяется в следующем порядке:

1. параметр запроса API, если такой механизм используется;
    
2. пользовательские настройки для авторизованного пользователя;
    
3. HTTP-заголовок `Accept-Language`;
    
4. язык по умолчанию — `uk`.
    

Конкретный механизм передачи языка должен обеспечивать единообразное определение локали для всех API-операций.

## 4.7. Представление локализованных данных

Backend возвращает текстовые данные на языке текущего запроса.

Например:

```
{
  "id": 123,
  "name": "Розетка із заземленням"
}
```

Клиент не выбирает языковое поле самостоятельно.

Frontend не должен напрямую работать с внутренними полями хранения переводов, например:

```
name_ru
name_uk
name_en
```

Выбор локализованного значения полностью выполняется на Backend.

## 4.8. Локализация справочников и данных

Справочники (`lists`), классификаторы, характеристики и SEO-данные должны поддерживать локализованные значения.

Для реализации локализации используется единый механизм проекта.

В качестве возможного механизма может применяться `django-modeltranslation` либо другой согласованный инструмент, обеспечивающий единый принцип локализации.

Конкретная технология не фиксируется настоящим решением.

## 4.9. Принцип совместимости

Все новые архитектурные решения, модели данных, API и компоненты пользовательского интерфейса должны проектироваться с учетом поддержки многоязычности.

Если новая сущность содержит пользовательские текстовые данные, возможность их локализации должна предусматриваться на этапе проектирования.

Локализация не рассматривается как последующее необязательное расширение.

## 4.10. Граница ответственности Frontend и Backend

Frontend отвечает за:

- представление данных;
    
- пользовательское взаимодействие;
    
- выбор языка интерфейса;
    
- отображение локализованных данных.
    

Backend отвечает за:

- бизнес-логику;
    
- получение и изменение данных;
    
- правила локализации;
    
- выбор локализованных значений;
    
- формирование API-ответов;
    
- контроль целостности и бизнес-правил.
    

Frontend не должен дублировать бизнес-логику Backend.

# 5. Причины выбора

Выбранная архитектура обеспечивает:

- единый API для всех клиентов;
    
- централизованную бизнес-логику;
    
- отсутствие прямого доступа клиентов к базе данных;
    
- независимость клиентов от структуры хранения данных;
    
- централизованную обработку локализации;
    
- отсутствие дублирования логики выбора переводов на Frontend;
    
- стабильный и версионируемый API;
    
- возможность добавления новых клиентов;
    
- возможность расширения набора поддерживаемых языков.
    

# 6. Последствия

## 6.1. Преимущества

- единая бизнес-логика для всех клиентов;
    
- единый интерфейс доступа к данным;
    
- централизованная обработка локализации;
    
- упрощение разработки Frontend;
    
- независимость API от структуры базы данных;
    
- стабильность существующих клиентов при корректном версионировании;
    
- готовность к мобильным приложениям и внешним интеграциям;
    
- возможность дальнейшего расширения языковой поддержки.
    

## 6.2. Ограничения

- Frontend не должен использовать внутренние языковые поля моделей;
    
- переводы и выбор локализованных значений формируются на Backend;
    
- новые текстовые поля должны проектироваться с учетом многоязычности;
    
- изменение структуры API должно выполняться с соблюдением политики версионирования;
    
- изменение языка хранения данных не должно требовать изменения клиентского API.
    

# 7. Архитектурные принципы

- **API First** — API является основным публичным интерфейсом системы.
    
- **Single Source of Truth** — Backend является единственным источником бизнес-данных и бизнес-логики.
    
- **Separation of Concerns** — Frontend и Backend имеют четко разделенные зоны ответственности.
    
- **Internationalization (i18n)** — многоязычность является обязательной частью архитектуры.
    
- **Backward Compatibility** — изменения API не должны нарушать работу существующих клиентов в пределах поддерживаемой версии.
    
- **Client Independence** — клиенты не должны зависеть от внутренней структуры хранения данных.
    
- **Centralized Localization** — правила выбора и формирования локализованных данных централизованы на Backend.

# 9. Заключительные положения

ADR-017 устанавливает REST API как единый публичный интерфейс взаимодействия между клиентами и Backend SmEl.

Backend остается единственным источником бизнес-логики и данных, а Frontend и другие клиенты взаимодействуют с системой исключительно через API.

Поддержка языков **uk / ru / en** является сквозным архитектурным требованием проекта и должна учитываться при проектировании всех новых подсистем, моделей данных, API и пользовательских интерфейсов.

Настоящее решение распространяется на все последующие архитектурные решения и реализации SmEl.
