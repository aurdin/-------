# 1. Назначение

ADR-037 определяет конкретную архитектуру аутентификации пользователей SmEl.

Документ детализирует решения ADR-021 и ADR-022 в части:

- механизма аутентификации;
    
- токенов;
    
- жизненного цикла токенов;
    
- обновления аутентификации;
    
- завершения аутентифицированного доступа;
    
- взаимодействия Frontend и Backend.
    

Цель решения — обеспечить безопасную и управляемую идентификацию пользователя при работе через REST API.

# 2. Область применения

Решение распространяется на:

- User;
    
- Customer;
    
- Authentication;
    
- Session;
    
- Access Token;
    
- Refresh Token;
    
- REST API;
    
- Vue 3 Frontend;
    
- Django REST Framework;
    
- Service Layer;
    
- защищённые ресурсы SmEl.
    

ADR-037 не определяет:

- бизнес-роли и их полномочия;
    
- структуру Customer;
    
- конкретные права RBAC;
    
- MFA;
    
- внешние Identity Provider;
    
- OAuth2/OpenID Connect как внешний механизм федерации;
    
- конкретную инфраструктуру хранения секретов.
    

# 3. Основная часть

## 3.1. Выбор механизма аутентификации

Для основной аутентификации Frontend SmEl используется схема:

**JWT Access Token + Refresh Token.**

Access Token используется для обращения к защищённым REST API.

Refresh Token используется для получения нового Access Token без повторного ввода учётных данных.

Архитектура:

```
Vue 3
  │
  │ credentials
  ▼
REST API
  │
  ▼
Authentication Service
  │
  ├── User
  └── Token Management
        │
        ├── Access Token
        └── Refresh Token
```

## 3.2. Разделение Authentication и Authorization

Authentication отвечает на вопрос:

**«Кто выполняет запрос?»**

Authorization отвечает на вопрос:

**«Имеет ли этот субъект право выполнить операцию?»**

JWT подтверждает аутентифицированный контекст, но не заменяет RBAC и проверки полномочий.

Правила authorization определяются ADR-021 и ADR-023.

## 3.3. Access Token

Access Token предназначен для краткосрочного доступа к защищённым REST API.

Он должен:

- иметь ограниченный срок действия;
    
- идентифицировать аутентифицированный субъект;
    
- содержать только необходимые claims;
    
- не содержать секретных или избыточных данных;
    
- проверяться Backend;
    
- быть недействительным после истечения срока.
    

Access Token не используется как постоянное хранилище состояния пользователя.

## 3.4. Refresh Token

Refresh Token предназначен для получения нового Access Token.

Он должен иметь:

- собственный срок действия;
    
- отдельный жизненный цикл;
    
- контролируемое хранение;
    
- возможность отзыва;
    
- связь с аутентификационным контекстом пользователя.
    

Refresh Token не должен использоваться для обычного доступа к бизнес-ресурсам API.

## 3.5. Жизненный цикл токенов

Общий жизненный цикл:

```
Authentication
     │
     ▼
Access Token + Refresh Token
     │
     ├───────────────┐
     ▼               ▼
Access Token     Refresh Token
     │               │
     ▼               ▼
Expired          Refresh
                     │
                     ▼
              New Access Token
```

Refresh Token также может истечь или быть отозван.

После невозможности обновления пользователь должен пройти повторную аутентификацию.

## 3.6. Срок действия токенов

Access Token должен иметь короткий срок действия.

Refresh Token имеет более длительный срок действия.

Конкретные значения сроков устанавливаются конфигурацией окружения и требованиями безопасности.

Продолжительность действия токенов не должна быть зашита во Frontend.

## 3.7. Refresh Token Rotation

При обновлении Access Token рекомендуется использовать ротацию Refresh Token.

При успешном обновлении:

```
Old Refresh Token
       │
       ▼
   Validation
       │
       ▼
New Access Token
       +
New Refresh Token
```

Предыдущий Refresh Token становится недействительным согласно политике ротации.

Это позволяет обнаруживать повторное использование ранее выданного Refresh Token.

## 3.8. Хранение токенов

Access Token и Refresh Token должны храниться с учётом требований безопасности.

Предпочтительный архитектурный вариант для браузерного клиента:

- Refresh Token — в защищённой `HttpOnly` cookie;
    
- cookie должна использовать `Secure`;
    
- политика `SameSite` определяется архитектурой развёртывания;
    
- Access Token не должен помещаться в небезопасное постоянное клиентское хранилище.
    

Frontend не должен получать серверные секреты, ключи подписи JWT или другие credentials Backend.

## 3.9. Проверка Access Token

Каждый защищённый API-запрос проходит проверку:

```
HTTP Request
     │
     ▼
Access Token
     │
     ▼
Signature / Validity
     │
     ▼
Authenticated User
     │
     ▼
Authorization
     │
     ▼
Service Layer
```

При недействительном или истёкшем Access Token защищённая операция не выполняется.

## 3.10. Обновление Access Token

Если Access Token истёк, Frontend может выполнить операцию refresh.

Refresh выполняется через Backend.

Backend:

1. принимает Refresh Token;
    
2. проверяет его действительность;
    
3. проверяет срок действия;
    
4. проверяет статус аутентификационного контекста;
    
5. выполняет необходимые проверки;
    
6. выдаёт новый Access Token;
    
7. при ротации выдаёт новый Refresh Token.
    

Frontend не генерирует токены самостоятельно.

## 3.11. Завершение аутентификации

Logout должен завершать текущий аутентификационный контекст.

При logout:

- Refresh Token отзывается или становится недействительным;
    
- соответствующая cookie удаляется;
    
- текущий Access Token перестаёт использоваться;
    
- Frontend удаляет своё локальное состояние аутентификации.
    

Поскольку Access Token является краткоживущим, его немедленная серверная инвалидизация не является обязательным механизмом.

Для критичных сценариев может использоваться дополнительный механизм отзыва.

## 3.12. Связь с Session

Аутентификация и Session являются различными понятиями.

```
User
 │
 ▼
Authentication
 │
 ▼
Authenticated Session
 │
 ▼
Access Token
```

Завершение одной Session не означает удаление User или Customer.

Customer Cart продолжает существовать независимо от отдельной Session согласно ADR-036.

## 3.13. Guest → Authenticated

До аутентификации клиент может работать как Guest.

После успешной аутентификации Backend создаёт аутентифицированный контекст.

```
Guest
 │
 ▼
Authentication
 │
 ▼
Authenticated User
 │
 ▼
Customer Context
```

Объединение Guest Cart с Customer Cart выполняется согласно отдельному бизнес-правилу ADR-036.

## 3.14. Безопасность токенов

Запрещается:

- передавать JWT по незащищённому HTTP в Production;
    
- помещать ключи подписи в Frontend;
    
- включать Refresh Token в обычные API-ответы бизнес-операций;
    
- записывать токены в логи;
    
- передавать токены третьим лицам;
    
- использовать Access Token после истечения срока действия.
    

Production API должен использовать HTTPS согласно ADR-023 и ADR-031.

## 3.15. API Client

API Client является отдельным субъектом доступа согласно ADR-021.

Механизм пользовательской JWT-аутентификации не должен автоматически применяться к серверным интеграциям.

Для API Client может использоваться отдельный механизм credentials или machine-to-machine authentication.

Конкретный механизм определяется архитектурой интеграции.

## 3.16. Управление ключами подписи

Ключи, используемые для подписи и проверки JWT, относятся к секретам системы.

Они:

- не находятся в исходном коде;
    
- не находятся во Frontend;
    
- не включаются в Docker image;
    
- предоставляются Backend через защищённую конфигурацию;
    
- управляются согласно ADR-029.
    

Ротация ключей должна выполняться контролируемо.

Конкретная схема ротации ключей определяется при реализации.

# 4. Правила

1. Основной механизм пользовательской аутентификации SmEl — JWT Access Token + Refresh Token.
    
2. Authentication и Authorization являются различными механизмами.
    
3. Access Token используется для краткосрочного доступа к защищённому API.
    
4. Refresh Token используется только для обновления аутентификации.
    
5. Access Token имеет ограниченный срок действия.
    
6. Refresh Token имеет собственный жизненный цикл и срок действия.
    
7. Refresh Token должен поддерживать отзыв.
    
8. Для Refresh Token применяется ротация.
    
9. Backend является единственным источником истины для состояния аутентификации.
    
10. Frontend не генерирует и не подписывает JWT.
    
11. Ключи подписи JWT никогда не передаются Frontend.
    
12. Токены не должны попадать в логи.
    
13. Защищённые API-запросы выполняются только после проверки Access Token.
    
14. После истечения Access Token выполняется контролируемое обновление через Backend.
    
15. При недействительном Refresh Token требуется повторная аутентификация.
    
16. Logout завершает соответствующий аутентификационный контекст.
    
17. Customer Cart не зависит от срока действия отдельного Access Token.
    
18. Authentication не заменяет RBAC.
    
19. API Client рассматривается отдельно от пользовательской JWT-аутентификации.
    
20. Ключи и другие authentication secrets управляются согласно ADR-029.
    
21. В Production аутентификация передаётся только по HTTPS.
    
22. Все бизнес-операции после аутентификации выполняются через Service Layer.

# 6. Заключительные положения

ADR-037 фиксирует конкретный механизм пользовательской аутентификации SmEl на основе JWT Access Token и Refresh Token.

Архитектура обеспечивает разделение Authentication и Authorization, краткоживущий доступ, обновление аутентификации, контролируемое завершение доступа и защиту ключей подписи.

Конкретные значения TTL токенов, параметры cookie, алгоритм подписи JWT, механизм хранения Refresh Token и детальная политика ротации ключей определяются на этапе реализации с учётом требований безопасности конкретного Production-окружения.
