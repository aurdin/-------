# 1. Назначение

Настоящее архитектурное решение определяет принципы контейнеризации компонентов SmEl и организации основных программных окружений.

Решение обеспечивает единообразное формирование окружений, изоляцию компонентов, воспроизводимость запуска и подготовку системы к развёртыванию в production.

# 2. Область применения

Решение распространяется на:

- Frontend SmEl;
    
- Backend SmEl;
    
- PostgreSQL;
    
- фоновые процессы и workers;
    
- Integration Layer;
    
- вспомогательные инфраструктурные компоненты;
    
- Development, Test и Production окружения;
    
- конфигурацию и взаимодействие контейнеризированных компонентов.
    

Решение не определяет конкретного облачного провайдера, оркестратор контейнеров или физическую инфраструктуру.

# 3. Основная часть

## 3.1. Контейнеризация

SmEl использует контейнеризацию как базовый механизм формирования воспроизводимых программных окружений.

Основной технологией контейнеризации является **Docker**.

Каждый компонент, имеющий самостоятельный жизненный цикл, зависимости или требования к окружению, может выполняться в отдельном контейнере.

Контейнеризация не изменяет логические границы компонентов, определённые архитектурой SmEl.

## 3.2. Основные контейнеризированные компоненты

Архитектура предусматривает возможность выделения следующих компонентов:

```
                    SmEl
                      │
        ┌─────────────┼─────────────┐
        │             │             │
    Frontend       Backend       Workers
        │             │             │
        │             ├──────┐      │
        │             │      │      │
        │          Service  Integration
        │           Layer      Layer
        │             │          │
        └─────────────┼──────────┘
                      │
                  PostgreSQL
```

Frontend, Backend, workers, Integration Layer и PostgreSQL рассматриваются как логически независимые компоненты.

Фактическое количество контейнеров может отличаться от логического количества компонентов.

Один логический компонент может использовать несколько экземпляров одного контейнерного образа.

## 3.3. Frontend

Frontend SmEl контейнеризируется независимо от Backend.

Frontend не получает прямого доступа к PostgreSQL.

Frontend взаимодействует с Backend только через REST API в соответствии с ADR-017.

Секреты Backend, базы данных и внешних интеграций не передаются во Frontend.

## 3.4. Backend

Backend является основным серверным приложением SmEl.

Backend выполняется в отдельном контейнеризированном окружении.

Backend предоставляет REST API, реализует Service Layer и взаимодействует с PostgreSQL и внешними системами через определённые архитектурные границы.

Backend не должен зависеть от локального состояния контейнера как от единственного источника бизнес-данных.

## 3.5. PostgreSQL

PostgreSQL является отдельным инфраструктурным компонентом.

В Development и Test окружениях PostgreSQL может запускаться в Docker-контейнере.

В Production PostgreSQL может находиться:

- в отдельном Docker-контейнере;
    
- во внешнем управляемом сервисе;
    
- на отдельном сервере.
    

Конкретный вариант production-размещения PostgreSQL определяется инфраструктурным решением и не фиксируется настоящим ADR.

Независимо от способа размещения PostgreSQL не должен предоставляться прямому доступу из Frontend или внешних систем.

## 3.6. Workers и фоновые процессы

Фоновые процессы рассматриваются как отдельные исполняемые компоненты и могут выполняться в отдельных контейнерах.

Архитектура контейнеризации должна позволять независимо масштабировать Backend и workers.

Конкретная архитектура асинхронной обработки, очередей и Message Broker определяется отдельным решением ADR-033.

## 3.7. Integration Layer

Integration Layer выполняется отдельно от основного Backend на логическом уровне.

Он обеспечивает контролируемое взаимодействие SmEl с внешними системами.

Внешние системы не получают прямого доступа к PostgreSQL.

При необходимости Integration Layer может быть размещён в одном или нескольких отдельных контейнерах.

## 3.8. Docker Compose

Для Development и локального Test окружения допускается и рекомендуется использование **Docker Compose** для согласованного запуска взаимосвязанных компонентов SmEl.

Docker Compose может использоваться для:

- запуска Frontend;
    
- запуска Backend;
    
- запуска PostgreSQL;
    
- запуска workers;
    
- запуска вспомогательных сервисов;
    
- настройки внутренних сетей;
    
- подключения volumes;
    
- передачи конфигурации окружения.
    

Docker Compose является средством организации окружения и не является обязательным механизмом production-оркестрации.

## 3.9. Окружения

SmEl разделяется минимум на следующие логические окружения:

```
Development
     │
     ▼
   Test
     │
     ▼
 Production
```

Каждое окружение имеет собственные:

- конфигурацию;
    
- секреты;
    
- базы данных;
    
- учётные данные внешних систем;
    
- сетевые параметры;
    
- допустимые интеграции.
    

Данные Production не должны использоваться в Development без специально предусмотренного механизма обезличивания и защиты.

## 3.10. Конфигурация

Конфигурация приложения отделяется от контейнерного образа.

Изменяемые параметры передаются через конфигурацию окружения.

Секреты не включаются в Docker-образы и не хранятся в исходном коде.

Правила управления секретами определяются ADR-029.

## 3.11. Docker-образы

Для каждого контейнеризированного компонента формируется воспроизводимый образ.

Образ должен содержать необходимые программные зависимости и не должен содержать:

- пароли;
    
- токены;
    
- ключи;
    
- production-секреты;
    
- изменяемые бизнес-данные.
    

Версии базовых образов и зависимостей должны быть контролируемыми.

## 3.12. Сети контейнеров

Взаимодействие контейнеров осуществляется через внутренние сети.

Публичный доступ предоставляется только компонентам, которым он необходим.

PostgreSQL не публикуется непосредственно во внешнюю сеть.

Внутренние сервисы не должны становиться публичными только вследствие контейнеризации.

## 3.13. Хранение данных

Контейнер рассматривается как заменяемый экземпляр выполнения.

Бизнес-данные не должны зависеть от файловой системы конкретного контейнера.

Для данных, которые должны переживать пересоздание контейнера, используются внешнее или постоянное хранилище.

Резервное копирование PostgreSQL определяется ADR-030 и будущим ADR-043.

## 3.14. Production

Production должен обеспечивать:

- изоляцию компонентов;
    
- защищённый внешний доступ;
    
- HTTPS;
    
- отсутствие прямого доступа Frontend к PostgreSQL;
    
- отсутствие прямого доступа внешних систем к PostgreSQL;
    
- управление секретами;
    
- резервное копирование;
    
- мониторинг и журналирование;
    
- возможность восстановления компонентов;
    
- возможность независимого масштабирования при необходимости.
    

Конкретная production-инфраструктура определяется настоящим решением только на уровне принципов.

# 4. Правила

1. Docker является базовой технологией контейнеризации SmEl.
    
2. Контейнеризация не изменяет логические границы архитектурных компонентов.
    
3. Frontend не имеет прямого доступа к PostgreSQL.
    
4. Внешние системы не имеют прямого доступа к PostgreSQL.
    
5. Backend остаётся центральной серверной точкой бизнес-логики.
    
6. Service Layer не предоставляется как публичный интерфейс.
    
7. Секреты не включаются в контейнерные образы.
    
8. Бизнес-данные не должны зависеть от жизненного цикла контейнера.
    
9. Development, Test и Production разделяются.
    
10. Конфигурация окружения отделяется от контейнерного образа.
    
11. Docker Compose используется как средство локальной организации окружения и не определяет production-оркестрацию.
    
12. Message Broker и Kubernetes не вводятся автоматически настоящим решением.
    
13. Асинхронная обработка определяется отдельным ADR-033.
    
14. Конкретная production-инфраструктура уточняется отдельными архитектурными решениями при необходимости.
    
15. Любое расширение состава контейнеризированных компонентов не должно нарушать установленные архитектурные границы.

# 6. Заключительные положения

Docker принимается как базовый механизм контейнеризации SmEl.

Docker Compose используется для организации локальных и тестовых окружений.

Контейнеризация обеспечивает воспроизводимость и изоляцию окружений, но не заменяет архитектурные границы Backend, Service Layer, Integration Layer и PostgreSQL.

Конкретные механизмы асинхронной обработки, production-оркестрации, масштабирования и инфраструктурного размещения могут быть определены отдельными архитектурными решениями.
