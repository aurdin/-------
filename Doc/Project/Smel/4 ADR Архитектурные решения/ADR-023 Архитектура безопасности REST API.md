# 1. Назначение

Настоящее архитектурное решение определяет общие принципы обеспечения безопасности REST API проекта **Smart Electric (SmEl)**.

Решение устанавливает архитектурные правила защиты API от несанкционированного доступа, некорректного использования и нарушения целостности бизнес-операций.

# 2. Область применения

Решение применяется ко всем REST API проекта SmEl и определяет требования к:

- идентификации клиентов API;
    
- аутентификации;
    
- авторизации;
    
- защите передаваемых данных;
    
- контролю доступа к ресурсам и операциям;
    
- обработке ошибок безопасности;
    
- защите бизнес-операций;
    
- взаимодействию с внешними API-клиентами.
    

Конкретные технологии и библиотеки реализации безопасности настоящим ADR не фиксируются.

# 3. Основная часть

## 3.1. Архитектурная граница

REST API является внешней границей Backend и контролируемой точкой доступа к бизнес-функциям SmEl.

Общая архитектурная цепочка:

```
Client
   │
   ▼
HTTPS
   │
   ▼
REST API
   │
   ├── Authentication
   │
   ├── Authorization
   │
   ├── Input Validation
   │
   ▼
Service Layer
   │
   ▼
Domain / ORM
   │
   ▼
PostgreSQL
```

Все внешние запросы должны проходить через установленные механизмы контроля доступа и проверки входных данных.

## 3.2. Аутентификация

Для защищённых операций API должна выполняться аутентификация субъекта запроса.

Аутентификация определяет User или иной субъект, от имени которого выполняется запрос.

Архитектурные принципы аутентификации определены ADR-021.

Конкретный механизм аутентификации и формат учётных данных определяется отдельным решением.

## 3.3. Авторизация

После успешной аутентификации API должен определить, имеет ли субъект право выполнить запрошенную операцию.

Авторизация основывается на ролях и разрешениях в соответствии с ADR-021.

Проверка авторизации должна учитывать:

- субъект запроса;
    
- требуемую операцию;
    
- ресурс;
    
- контекст операции;
    
- установленные бизнес-ограничения.
    

Проверка только факта аутентификации недостаточна для защищённых операций.

## 3.4. Защита данных при передаче

Взаимодействие с API должно осуществляться по защищённому транспортному соединению.

Передача учётных данных, токенов, сессионных идентификаторов и другой чувствительной информации по незащищённому соединению не допускается.

API не должен передавать клиенту секретные данные, не предназначенные для его использования.

## 3.5. Проверка входных данных

Все данные, поступающие через API, должны рассматриваться как недоверенные.

Backend должен выполнять:

- проверку структуры входных данных;
    
- проверку типов и форматов;
    
- проверку допустимых значений;
    
- проверку бизнес-ограничений;
    
- проверку прав доступа к изменяемым ресурсам.
    

Валидация Frontend не заменяет серверную валидацию.

## 3.6. Защита бизнес-операций

Защищённые бизнес-операции выполняются через Service Layer в соответствии с ADR-020.

REST API не должен самостоятельно реализовывать бизнес-правила.

Это обеспечивает единый механизм выполнения бизнес-операций независимо от типа клиента.

## 3.7. Защита ресурсов

Доступ к ресурсу должен проверяться не только на уровне endpoint, но и на уровне самой операции.

Пользователь не должен получать доступ к объекту только потому, что знает его идентификатор.

Backend должен проверять принадлежность ресурса субъекту или наличие соответствующего разрешения.

Особенно это относится к:

- Customer;
    
- Cart;
    
- Order;
    
- Payment;
    
- Delivery;
    
- административным ресурсам.
    

## 3.8. Ошибки безопасности

API не должно раскрывать клиенту внутреннюю техническую информацию, которая может использоваться для анализа системы.

Сообщения об ошибках должны быть понятными для клиента, но не должны раскрывать:

- внутреннюю структуру базы данных;
    
- SQL-запросы;
    
- внутренние пути файловой системы;
    
- секреты;
    
- конфигурационные значения;
    
- внутренние трассировки исключений.
    

Подробная диагностическая информация должна сохраняться на стороне Backend в соответствии с установленной политикой журналирования.

# 4. Правила

1. REST API является контролируемой границей доступа к Backend.
    
2. Все входные данные API считаются недоверенными.
    
3. Защищённые операции должны проходить аутентификацию и авторизацию.
    
4. Авторизация выполняется на Backend.
    
5. Frontend не является доверенной стороной при принятии решений о доступе.
    
6. Проверка прав должна выполняться независимо от пользовательского интерфейса.
    
7. Серверная валидация обязательна независимо от наличия клиентской валидации.
    
8. Бизнес-операции выполняются через Service Layer.
    
9. Прямой доступ Frontend к PostgreSQL запрещён.
    
10. Доступ к ресурсам должен проверяться с учётом субъекта и контекста операции.
    
11. Передача чувствительных данных должна выполняться по защищённому соединению.
    
12. Секреты и внутренние технические данные не должны передаваться клиенту.
    
13. Внутренние ошибки Backend не должны непосредственно передаваться клиенту.
    
14. Механизм аутентификации, формат токенов и конкретные средства защиты API определяются отдельными решениями.
    
15. Механизмы защиты от автоматизированного злоупотребления, ограничения частоты запросов и другие специализированные средства могут быть определены отдельными решениями.

# 6. Заключительные положения

REST API SmEl рассматривается как защищаемая внешняя граница Backend.

Аутентификация и авторизация выполняются на стороне Backend, входные данные проходят серверную валидацию, а бизнес-операции выполняются через Service Layer.

Доступ к ресурсам определяется субъектом запроса, его полномочиями и контекстом операции.

Конкретные механизмы аутентификации, управления токенами, ограничения частоты запросов и специализированной защиты API определяются последующими архитектурными решениями.
