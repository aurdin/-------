## 1. Контекст

SmEl является многоязычным интернет-магазином электротехнических товаров.

Система должна поддерживать следующие языки:

|Код|Язык|Назначение|
|---|---|---|
|`en`|English|базовый язык данных|
|`ru`|Русский|локализация|
|`uk`|Українська|локализация|

Локализуемыми являются прежде всего пользовательские текстовые данные каталога и справочников:

- название;
    
- описание;
    
- другие текстовые поля, для которых локализация определена соответствующей моделью.
    

При этом данные могут поступать из различных источников:

- ручной ввод через Admin;
    
- импорт CSV/XLSX;
    
- автоматический перевод;
    
- последующее ручное редактирование.
    

Необходимо исключить ситуацию, когда автоматический перевод без ведома пользователя перезаписывает ранее введённый или исправленный человеком текст.

---

## 2. Проблема

Необходимо определить:

1. как хранить локализованные значения;
    
2. какой язык может быть исходным для перевода;
    
3. когда разрешён автоматический перевод;
    
4. как обрабатывать уже заполненные переводы;
    
5. как отличать ручной текст от автоматически созданного;
    
6. как должен работать перевод после импорта;
    
7. как локализация должна участвовать в экспорте данных.
    

---

## 3. Рассмотренные варианты

### Вариант A — автоматический перевод при сохранении

При сохранении записи система автоматически переводит отсутствующие языковые варианты.

**Недостатки:**

- перевод запускается без явного действия пользователя;
    
- увеличивается количество внешних запросов;
    
- возможна генерация нежелательного текста;
    
- сложнее контролировать перезапись ручного перевода.
    

**Решение:** не использовать.

### Вариант B — только ручной перевод

Все языковые варианты вводятся пользователем вручную.

**Недостатки:**

- высокая трудоёмкость;
    
- большое количество повторяющейся работы;
    
- особенно неудобно для большого каталога.
    

**Решение:** не использовать как единственный механизм.

### Вариант C — автоматический перевод только по команде пользователя

Пользователь явно запускает перевод кнопкой **«Перевести»**.

Система определяет исходный язык, два целевых языка и состояние каждого локализованного поля.

**Решение:** принять.

---

## 4. Решение

SmEl использует **управляемый пользователем автоматический перевод**.

Автоматический перевод **никогда не запускается автоматически** при:

- создании записи;
    
- изменении записи;
    
- сохранении записи;
    
- импорте;
    
- экспорте.
    

Перевод выполняется только после явного действия пользователя:

> **«Перевести»**

Исходным может быть **любой из трёх поддерживаемых языков**:

- `en`;
    
- `ru`;
    
- `uk`.
    

Таким образом, поддерживаются все направления:

```text
EN → RU + UK
RU → EN + UK
UK → EN + RU
```

---

## 5. Определение исходного языка

Перед запуском перевода пользователь указывает или подтверждает исходный язык.

Система определяет два остальных языка как целевые.

Например:

```text
Исходный язык: RU

RU ───────→ EN
  └───────→ UK
```

или:

```text
Исходный язык: UK

UK ───────→ EN
  └───────→ RU
```

Автоматическое определение языка текста может использоваться как вспомогательный механизм, но не должно заменять возможность явного выбора пользователем.

---

## 6. Правило обработки каждого локализованного поля

Проверка выполняется **для каждого локализованного поля отдельно**.

Например, для Category:

```text
name_en
name_ru
name_uk

description_en
description_ru
description_uk
```

Если пользователь переводит из `ru`, система отдельно проверяет:

- `name_en`;
    
- `name_uk`;
    
- `description_en`;
    
- `description_uk`.
    

### 6.1. Целевое поле пустое

Если целевое поле пустое:

```text
name_en = ""
```

перевод может быть выполнен автоматически без дополнительного подтверждения.

### 6.2. Целевое поле заполнено

Если целевое поле содержит значение:

```text
name_en = "Switch"
```

система должна предупредить пользователя:

> Поле `name_en` уже заполнено. Выполнить перевод с заменой существующего значения?

Доступны действия:

- **Продолжить**;
    
- **Отмена**.
    

До подтверждения существующее значение не изменяется.

---

## 7. Ручной и автоматический источник значения

Для локализованных данных вводится понятие источника значения:

|Значение|Назначение|
|---|---|
|`MANUAL`|значение введено или изменено пользователем|
|`AUTO`|значение создано автоматическим переводом|

Приоритет имеет ручное значение:

```text
MANUAL > AUTO
```

Однако наличие `AUTO` также означает, что поле **уже заполнено**.

Поэтому повторный автоматический перевод существующего `AUTO`-значения также требует предупреждения и подтверждения пользователя.

---

## 8. Повторный перевод

Повторный перевод не выполняется автоматически.

Например:

```text
name_ru = "Выключатель"
name_en = "Switch"
name_uk = "Вимикач"
```

Если пользователь снова запускает перевод из `ru`, система обнаруживает заполненные целевые поля.

Она должна сообщить:

> Целевые поля уже содержат значения. Их текущие значения будут заменены результатами нового перевода.

Только после подтверждения пользователя существующие значения могут быть заменены.

При отмене операции:

```text
изменений нет
```

---

## 9. Импорт данных

Импорт CSV/XLSX является **источником данных**, но не является командой перевода.

Импорт:

- не запускает автоматический перевод;
    
- сохраняет предоставленные языковые значения;
    
- не заменяет отсутствующие языки автоматически;
    
- не вызывает Translation Service.
    

Например, импорт может содержать:

```text
code,name_en,name_ru,name_uk
SW-001,Switch,Выключатель,
```

После импорта:

```text
name_en = "Switch"
name_ru = "Выключатель"
name_uk = ""
```

Поле `name_uk` остаётся пустым.

Пользователь может после этого выполнить:

> **«Перевести»**

и получить украинское значение.

---

## 10. Экспорт данных

Экспорт должен включать локализованные поля явно.

Например:

```text
code
name_en
name_ru
name_uk
description_en
description_ru
description_uk
status
```

Экспорт:

- не выполняет перевод;
    
- не изменяет данные;
    
- сохраняет существующие языковые значения;
    
- должен позволять повторно импортировать данные.
    

---

## 11. Стабильный идентификатор при импорте и экспорте

Для обмена данными между средами используется стабильный бизнес-идентификатор `code`.

Импорт не должен зависеть от внутреннего Django `id`.

Правило:

```text
code существует → UPDATE
code отсутствует → CREATE
```

Для связанных объектов используются коды соответствующих справочников.

Например:

```text
category_code
group_code
brand_code
series_code
type_code
model_code
execution_code
```

Таким образом, импорт/экспорт не зависит от совпадения внутренних идентификаторов баз данных.

## 12. Архитектура Translation Service

Логика автоматического перевода реализуется отдельным сервисом:

```text
Admin / Import
      │
      ▼
Localized Model
      │
      │ пользователь нажал «Перевести»
      ▼
Translation Service
      │
      ▼
Translation Provider
      │
      ▼
Translated Values
```

### Translation Service отвечает за:

- определение исходного языка;
    
- определение целевых языков;
    
- проверку локализованных полей;
    
- определение пустых и заполненных полей;
    
- формирование предупреждений;
    
- получение подтверждения пользователя;
    
- выполнение перевода;
    
- фиксацию источника значения (`MANUAL` / `AUTO`);
    
- сохранение результата.
    

### Translation Provider отвечает только за перевод текста.

Конкретный внешний сервис автоматического перевода не является частью модели каталога.

Это позволяет заменить поставщика перевода без изменения моделей каталога и бизнес-логики.

## 13. Взаимодействие с django-modeltranslation

Для хранения локализованных полей используется `django-modeltranslation`.

Например:

```python
name
name_en
name_ru
name_uk
```

и:

```python
description
description_en
description_ru
description_uk
```

Поле без языкового суффикса (`name`, `description`) является динамическим представлением значения для текущего языка и **не является четвёртым языком**.

`django-modeltranslation` отвечает за:

- хранение локализованных значений;
    
- получение значения текущего языка;
    
- интеграцию с Django Admin;
    
- языковые fallback-механизмы.
    

`django-modeltranslation` **не отвечает** за:

- запуск автоматического перевода;
    
- определение источника значения `MANUAL/AUTO`;
    
- подтверждение перезаписи;
    
- взаимодействие с внешним Translation Provider.
    

Эта логика является частью SmEl.

---

## 14. Область применения

Локализация применяется только к тем моделям и полям, для которых она архитектурно необходима.

Пример:

| Поле                    | Перевод |
| ----------------------- | ------- |
| `name`                  | Да      |
| `description`           | Да      |
| `article`               | Нет     |
| `barcode`               | Нет     |
| `status`                | Нет     |
| `code`                  | Нет     |
| числовые характеристики | Нет     |
| текстовое поле          | Да      |

Для каждой модели перечень переводимых полей определяется отдельно.

На первом этапе локализация применяется, в частности, к:

- Category;
    
- Group;
    
- Product;
    
- другим текстовым сущностям каталога по мере их реализации.
    

---

## 15. Принцип приоритета данных

Источники локализованного значения имеют следующий приоритет:

```text
MANUAL
   ↓
AUTO
```

Ручное значение пользователя является окончательным до тех пор, пока пользователь явно не разрешит его замену.

Автоматический перевод является вспомогательным механизмом заполнения каталога и не должен самостоятельно изменять пользовательские данные.
