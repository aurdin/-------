# 1. Назначение

Настоящее архитектурное решение определяет принцип разделения товарных данных и коммерческих условий в проекте **Smart Electric (SmEl)**.

Решение фиксирует независимость коммерческих данных от структуры каталога и обеспечивает возможность их изменения без изменения технической и классификационной информации о товаре.

# 2. Область применения

Решение применяется к данным, связанным с коммерческим использованием товаров:

- ценами;
    
- прайс-листами;
    
- скидками;
    
- акциями;
    
- валютами;
    
- наличием;
    
- складами;
    
- группами клиентов;
    
- периодами действия;
    
- коммерческими ограничениями.
    

Каталог товара содержит техническую и классификационную информацию и не является местом хранения коммерческих условий.

# 3. Основная часть

## 3.1. Разделение товарных и коммерческих данных

В SmEl данные о товарах и коммерческие условия хранятся раздельно.

Каталог содержит техническую и классификационную информацию, а коммерческие данные находятся в отдельном функциональном блоке.

```
Product (SKU)
      │
      └───────────────┐
                      │
              Commercial Data
                      │
        ├── Price
        ├── Discount
        ├── Currency
        ├── Availability
        ├── Warehouse
        ├── Promotion
        ├── Customer Group
        ├── Price List
        └── Validity Period
```

## 3.2. Назначение коммерческого блока

Коммерческий блок отвечает за:

- базовые цены товаров;
    
- цены различных прайс-листов;
    
- индивидуальные цены клиентов;
    
- скидки;
    
- акции;
    
- наличие;
    
- склады;
    
- валюты;
    
- периоды действия цен;
    
- коммерческие ограничения.
    

При этом **Стоимость, Скидки и Акции являются составными частями блока ценообразования**.

# 4. Правила

1. Каждый товар (`SKU`) может иметь множество коммерческих записей.
    
2. Цены не хранятся непосредственно в основной сущности товара.
    
3. Изменение цены не требует изменения карточки товара.
    
4. Коммерческие данные имеют собственный жизненный цикл.
    
5. История изменения цен должна сохраняться.
    
6. Для одного товара одновременно могут существовать несколько прайс-листов.
    
7. Расчёт стоимости выполняется на основании коммерческих данных.
    
8. Логика выбора актуальной цены должна быть централизованной.
    
9. Единая логика определения актуальной цены используется каталогом, корзиной, оформлением заказа и API.
    
10. Конкретные механизмы применения скидок, акций и коммерческих условий определяются отдельными архитектурными решениями.
    

## 4.1. Логическая модель

```
Product (SKU)
        │
        └──────────────< ProductPrice
                               │
                               ├── Price List
                               ├── Currency
                               ├── Price
                               ├── Discount
                               ├── Availability
                               ├── Warehouse
                               ├── Valid From
                               ├── Valid To
                               └── Status
```

# 5. Обоснование

Разделение каталога и коммерческих данных выбрано по следующим причинам:

- разделение технических и коммерческих данных;
    
- возможность частого обновления цен без изменения каталога;
    
- поддержка нескольких прайс-листов;
    
- возможность реализации B2B-цен и персональных условий;
    
- поддержка историчности цен;
    
- подготовка к интеграции с ERP и учетными системами;
    
- независимый жизненный цикл коммерческой информации.
    

# 6. Последствия

## 6.1. Преимущества

- независимое управление каталогом и коммерческими данными;
    
- поддержка нескольких валют;
    
- возможность реализации различных типов цен: розничной, дилерской, оптовой, проектной и других;
    
- простая реализация акций и временных предложений;
    
- масштабирование при увеличении количества товаров и прайс-листов;
    
- снижение нагрузки на основной каталог при обновлении коммерческой информации.
    

## 6.2. Ограничения

- расчёты стоимости выполняются на основе коммерческих данных, а не данных каталога;
    
- при отсутствии действующей коммерческой записи товар считается недоступным для продажи либо отображается без цены — в зависимости от установленных бизнес-правил;
    
- логика определения актуальной цены должна быть централизована;
    
- изменение коммерческих условий может влиять на доступность товара для покупки без изменения самого товара.

# 8. Заключительные положения

Настоящее решение фиксирует архитектурный принцип **разделения каталога и коммерческих данных**.

Техническая и классификационная информация о товаре отделяется от изменяемых коммерческих условий, что обеспечивает независимое управление и жизненный цикл этих данных.

Конкретная реализация `PriceList`, `ProductPrice`, `Warehouse`, `Promotion`, `CustomerGroup`, механизмов расчёта итоговой стоимости, применения скидок и акций определяется отдельными архитектурными решениями подсистемы ценообразования и оформления заказа.
