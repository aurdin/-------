# 1. Назначение

Настоящее архитектурное решение определяет архитектуру импорта и синхронизации данных каталога в проекте **Smart Electric (SmEl)**.

Решение устанавливает единый механизм получения, проверки, преобразования и загрузки данных от производителей, поставщиков, ERP-систем и других внешних источников.

Подсистема импорта рассматривается как самостоятельный **ETL-слой (Extract → Transform → Load)** между внешними источниками данных и внутренними бизнес-модулями SmEl.

# 2. Область применения

Решение распространяется на процессы:

- импорта каталога товаров;
    
- импорта характеристик;
    
- импорта справочников;
    
- импорта цен;
    
- импорта складских остатков;
    
- импорта изображений и документов;
    
- синхронизации данных с ERP;
    
- синхронизации данных с поставщиками;
    
- контроля качества импортируемых данных.
    

Подсистема импорта является независимой от пользовательского интерфейса и не изменяет архитектуру бизнес-моделей внутренних подсистем.

# 3. Основная часть

## 3.1. Архитектурное решение

Импорт и синхронизация данных реализуются как самостоятельная подсистема, расположенная между внешними источниками и внутренними бизнес-модулями SmEl.

Подсистема отвечает за:

- получение данных;
    
- проверку формата;
    
- преобразование данных;
    
- сопоставление данных;
    
- валидацию;
    
- синхронизацию;
    
- загрузку данных;
    
- журналирование операций;
    
- обработку ошибок.
    

Логическая модель:

```
External Sources
        │
        ├── Manufacturer
        ├── Supplier
        ├── ERP
        ├── Excel
        ├── CSV
        ├── XML
        ├── JSON
        └── API
                │
                ▼
      Import Pipeline
                │
        ├── Validation
        ├── Mapping
        ├── Transformation
        ├── Synchronization
        ├── Logging
        └── Error Handling
                │
                ▼
        Business Modules
                │
        ├── Catalog
        ├── Characteristics
        ├── Prices
        ├── Stock
        ├── Media
        └── SEO
```

## 3.2. Этапы обработки

Обработка импортируемых данных выполняется последовательно:

```
Источник
      │
      ▼
Получение данных
      │
      ▼
Проверка формата
      │
      ▼
Преобразование
      │
      ▼
Сопоставление
      │
      ▼
Валидация
      │
      ▼
Обновление данных
      │
      ▼
Журналирование
```

## 3.3. Независимость подсистемы

Подсистема импорта не содержит бизнес-логики каталога, цен, складского учета или других бизнес-модулей.

Она обеспечивает контролируемую доставку данных в соответствующие подсистемы.

Все изменения бизнес-данных должны выполняться через специализированные сервисы соответствующих подсистем и не должны обходить установленные бизнес-правила.

# 4. Правила

## 4.1. Общие правила

- импорт не изменяет архитектуру бизнес-моделей;
    
- каждый тип данных импортируется своим специализированным процессом;
    
- загрузка выполняется поэтапно;
    
- ошибки одной записи не должны останавливать обработку остальных данных;
    
- импорт поддерживает полную и инкрементальную синхронизацию;
    
- каждая операция импорта журналируется.
    

## 4.2. Организация источников

Каждый источник имеет собственную конфигурацию.

Подсистема должна обеспечивать возможность подключения новых источников и форматов без изменения существующих процессов импорта.

Поддерживаются источники и форматы, включая:

- производители;
    
- поставщики;
    
- ERP;
    
- Excel;
    
- CSV;
    
- XML;
    
- JSON;
    
- API.
    

## 4.3. Идентификация товаров

Идентификация товарных позиций при импорте выполняется по правилам, установленным **ADR-008 — Архитектура идентификации товарных позиций**.

Внешние идентификаторы не должны нарушать правила внутренней идентификации SmEl.

## 4.4. Порядок импорта данных

Для зависимых данных должен соблюдаться установленный порядок:

```
Справочники
     ↓
Каталог
     ↓
Характеристики
     ↓
Цены
     ↓
Остатки
     ↓
Медиа
```

При этом:

- справочники синхронизируются до импорта товаров;
    
- характеристики импортируются после создания товаров;
    
- цены импортируются независимо от каталога;
    
- остатки импортируются независимо от цен;
    
- медиафайлы импортируются отдельным процессом.
    

## 4.5. Режимы запуска

Импорт может выполняться:

- вручную;
    
- по расписанию.
    

Архитектура должна поддерживать повторную обработку данных.

## 4.6. Идемпотентность

Каждая операция импорта должна быть идемпотентной.

Повторный импорт одного и того же набора данных не должен приводить к дублированию или неконтролируемому изменению данных.

## 4.7. Транзакционность

Изменения в пределах одной логической операции должны сохранять целостность данных.

Транзакционные границы и конкретные механизмы отката определяются на уровне реализации соответствующих подсистем.

## 4.8. Журналирование и обработка ошибок

Все операции импорта, их результаты и ошибки должны фиксироваться в журнале.

Ошибки отдельных записей не должны останавливать обработку остальных корректных записей.

Журналирование должно обеспечивать возможность анализа результатов и повторной обработки ошибочных данных.

# 5. Причины выбора

Выбранная архитектура обеспечивает:

- независимость бизнес-модулей от форматов внешних данных;
    
- подключение новых источников без изменения архитектуры бизнес-модулей;
    
- устойчивость к ошибкам отдельных записей;
    
- поддержку больших объемов данных;
    
- повторную обработку данных;
    
- централизованное журналирование;
    
- подготовку к автоматической синхронизации с ERP и поставщиками;
    
- масштабируемость подсистемы импорта.
    

# 6. Последствия

## 6.1. Преимущества

- единый механизм импорта для различных источников;
    
- возможность повторной обработки данных;
    
- возможность подключения новых форматов;
    
- централизованное журналирование;
    
- высокая масштабируемость;
    
- минимальное влияние ошибок отдельных записей на общий процесс;
    
- независимое развитие интеграций.
    

## 6.2. Ограничения

- импорт не должен обходить бизнес-правила системы;
    
- изменения данных выполняются через специализированные сервисы соответствующих подсистем;
    
- должен соблюдаться порядок импорта зависимых сущностей;
    
- операции импорта должны быть идемпотентными;
    
- конкретные технологии реализации ETL-слоя не фиксируются настоящим решением.
    

# 7. Архитектурные принципы

Подсистема импорта должна соответствовать следующим принципам:

- **Идемпотентность** — повторная обработка одного и того же набора данных не должна приводить к дублированию или неконтролируемому изменению результата.
    
- **Транзакционность** — изменения в пределах одной логической операции должны сохранять целостность данных.
    
- **Расширяемость** — добавление нового источника или формата не должно требовать изменения существующих процессов.
    
- **Наблюдаемость** — операции, ошибки и результаты импорта должны фиксироваться в журнале.
    
- **Изоляция** — форматы и особенности внешних источников не должны проникать в бизнес-модели внутренних подсистем.

ADR-016 определяет единый архитектурный механизм импорта и синхронизации данных между внешними источниками и внутренними бизнес-модулями SmEl.

Подсистема импорта реализуется как самостоятельный ETL-слой и обеспечивает безопасную, контролируемую и наблюдаемую доставку данных.

Решение завершает базовую архитектуру управления данными каталога и создает основу для последующего подключения производителей, поставщиков и ERP-систем без нарушения архитектурных границ проекта.
