# 1. Назначение

Документ фиксирует архитектурное решение по организации Backend проекта **Smart Electric (SmEl)** на основе модульной структуры Django-приложений.

Решение определяет принцип разделения функциональности Backend на отдельные приложения и устанавливает основные правила их организации.

# 2. Область применения

Решение распространяется на Backend проекта SmEl.

Каждая крупная функциональная область Backend должна реализовываться как отдельное Django-приложение (**app**) при наличии самостоятельной предметной ответственности.

Приложения размещаются в каталоге:

**backend/apps/**

# 3. Основная часть

Backend проекта SmEl строится по модульному принципу.

Каждое Django-приложение отвечает за определённую функциональную или предметную область и должно иметь чётко определённую ответственность.

Пример логической структуры:

```
backend/
└── apps/
    ├── lists/          # Общие справочники
    ├── catalog/        # Каталог товаров
    ├── cart/           # Корзина
    ├── orders/         # Заказы
    ├── users/          # Пользователи
    ├── prices/         # Цены
    ├── dbview/         # SQL VIEW и модели представлений
    ├── plugs/          # Плагины и интеграции
    ├── forks/          # Вспомогательные модули
    ├── seo/            # SEO
    └── ...
```

Конкретный состав приложений может изменяться по мере развития проекта.

Django-приложение может содержать следующие элементы:

- `models`;
    
- `serializers`;
    
- `views`;
    
- `urls`;
    
- `admin`;
    
- `services`;
    
- `permissions`;
    
- `tests`;
    
- `migrations`.
    

Наличие каждого элемента определяется ответственностью конкретного приложения.

# 4. Правила

В рамках данного архитектурного решения устанавливаются следующие правила:

1. Каждое приложение отвечает за определённую предметную или функциональную область.
    
2. Границы ответственности приложений должны быть явно определены.
    
3. Связность между приложениями должна быть минимальной и управляемой.
    
4. Общая бизнес-логика не должна дублироваться между приложениями.
    
5. Взаимодействие между приложениями осуществляется через определённые архитектурные интерфейсы, модели или сервисы в соответствии с характером взаимодействия.
    
6. Общие справочники размещаются в приложении `lists`.
    
7. SQL-представления и связанные с ними модели размещаются в приложении `dbview`.
    
8. Одинаковые предметные сущности не должны независимо реализовываться в нескольких приложениях.
    
9. Изменения общих компонентов должны учитывать влияние на зависимые приложения.
    
10. При выделении новой функциональной области необходимо определить её ответственность и границы взаимодействия с существующими приложениями.
    

# 5. Последствия

## 5.1. Преимущества

Модульная организация Backend обеспечивает:

- масштабируемость структуры проекта;
    
- удобство сопровождения;
    
- упрощение тестирования;
    
- возможность независимой разработки функциональных областей;
    
- понятную навигацию по исходному коду;
    
- снижение количества конфликтов при совместной разработке;
    
- возможность дальнейшего архитектурного выделения отдельных функциональных областей при необходимости.
    

## 5.2. Ограничения

Решение требует:

- соблюдения границ ответственности приложений;
    
- контроля зависимостей между приложениями;
    
- предотвращения дублирования предметных сущностей;
    
- анализа влияния изменений общих компонентов на зависимые приложения.

# 7. Заключительные положения

Модульная организация Backend на основе Django-приложений является базовым принципом структурирования серверной части SmEl.

Дальнейшее разделение Backend на приложения должно выполняться исходя из предметной ответственности, границ функциональности и управляемости зависимостей.

Конкретная реализация отдельных приложений не является предметом данного ADR и определяется соответствующими архитектурными документами и реализацией проекта.
