# 1. Назначение

Документ определяет архитектуру синхронизации складских остатков SmEl с внешними системами учета, а также правила обработки расхождений между внутренними и внешними данными.

Цель решения — обеспечить предсказуемое получение и использование актуальной информации о наличии товара без нарушения границ между каталогом, запасами, резервированием, заказами и внешними системами.

# 2. Область применения

Решение распространяется на:

- синхронизацию складских остатков;
    
- ERP/WMS-интеграции;
    
- получение количества доступного товара;
    
- получение резервов и других складских показателей;
    
- полную и инкрементальную синхронизацию;
    
- обработку изменений;
    
- обнаружение конфликтов;
    
- разрешение расхождений;
    
- повторную обработку сообщений;
    
- идемпотентность;
    
- актуализацию данных Stock;
    
- использование Stock в Cart, Checkout и Order.
    

Решение не определяет:

- конкретную ERP/WMS;
    
- конкретный протокол интеграции;
    
- конкретный брокер сообщений;
    
- физическую структуру внешней системы;
    
- архитектуру резервирования как таковую;
    
- правила ценообразования;
    
- физическую реализацию складской инфраструктуры.
    

# 3. Основная часть

## 3.1. Источник истины

Для складских данных внешняя ERP/WMS может являться **фактическим источником данных о физическом остатке**.

SmEl является источником истины для собственного состояния домена Stock, включая:

- полученное и сохраненное значение;
    
- время последнего обновления;
    
- статус синхронизации;
    
- историю изменений;
    
- внутренние резервы;
    
- связь с заказами и бизнес-операциями.
    

Таким образом, источники имеют разные зоны ответственности.

```
ERP / WMS
   │
   │ фактический складской остаток
   ▼
Integration Layer
   │
   ▼
Stock Service
   │
   ├──► Stock
   │
   └──► Reservation
```

ERP/WMS не получает прямого доступа к PostgreSQL SmEl.

## 3.2. Разделение физического остатка и доступности

Физический остаток и доступное для продажи количество не являются одним показателем.

Архитектура различает:

- физический остаток;
    
- зарезервированное количество;
    
- доступное количество;
    
- ожидаемое поступление;
    
- количество в заказах;
    
- статус доступности.
    

Упрощенная модель:

```
Available
   =
Physical Stock
   − Active Reservations
   − Other Business Holds
```

Конкретная формула может уточняться бизнес-правилами, но физический остаток не должен автоматически трактоваться как доступное для продажи количество.

## 3.3. Поток синхронизации

Основной поток:

```
ERP / WMS
    │
    ▼
Integration Layer
    │
    ▼
Validation
    │
    ▼
Mapping / Transformation
    │
    ▼
Stock Service
    │
    ▼
Stock
```

Integration Layer отвечает за адаптацию внешнего формата.

Stock Service отвечает за применение данных к внутренней модели.

Бизнес-логика Stock не должна дублироваться в интеграционном адаптере.

## 3.4. Полная синхронизация

Полная синхронизация используется для:

- первоначального заполнения;
    
- восстановления;
    
- сверки;
    
- устранения накопленных расхождений;
    
- контролируемой реконструкции Stock.
    

Полная синхронизация должна быть повторяемой и идемпотентной.

Она не должна удалять внутренние бизнес-сущности, такие как Order или Reservation.

## 3.5. Инкрементальная синхронизация

Инкрементальная синхронизация применяется для регулярного обновления изменений.

Изменение может поступать:

- через API;
    
- через webhook/event;
    
- через очередь;
    
- через периодический опрос;
    
- другим механизмом, определенным Integration Layer.
    

Конкретный транспорт не фиксируется настоящим ADR.

## 3.6. Идентификация товара

Внешний товар должен однозначно сопоставляться с внутренним SKU.

Для сопоставления могут использоваться:

- SKU;
    
- Article;
    
- EAN/GTIN;
    
- внешний идентификатор;
    
- таблица соответствий.
    

Внутренний SKU остается стабильным идентификатором товара в SmEl.

Нельзя создавать новую складскую сущность только вследствие изменения внешнего идентификатора, если это не подтверждено правилами сопоставления.

## 3.7. Валидация входных данных

До изменения Stock внешние данные проходят проверку.

Проверяются как минимум:

- идентификатор товара;
    
- существование соответствующего SKU;
    
- тип значения;
    
- допустимость количества;
    
- идентификатор склада;
    
- временная метка;
    
- источник данных;
    
- версия или последовательность изменения, если предоставляется;
    
- полнота обязательных данных.
    

Некорректные данные не должны изменять актуальное состояние Stock.

Ошибка должна быть зарегистрирована для последующего анализа.

# 4. Правила

## 4.1. Основное правило синхронизации

Если внешняя ERP/WMS определена как источник фактического складского остатка, SmEl принимает подтвержденное значение из внешней системы как новое фактическое значение.

При этом SmEl сохраняет:

- предыдущее значение;
    
- новое значение;
    
- источник;
    
- время получения;
    
- время применения;
    
- результат обработки.
    

## 4.2. Конфликт данных

Конфликт возникает, когда внутреннее состояние SmEl и поступившее внешнее состояние относятся к одному SKU/складу, но содержат различные значения или несовместимые версии состояния.

Само наличие различия не означает ошибку.

Необходимо определить, является ли внешнее значение:

- более новым;
    
- более старым;
    
- дублирующим;
    
- неполным;
    
- недействительным.
    

## 4.3. Приоритет внешнего источника

Для физического складского остатка при подтвержденной синхронизации приоритет имеет ERP/WMS.

SmEl не должен самостоятельно изменять физический остаток только потому, что его внутреннее значение отличается от внешнего.

Однако внутренние показатели, которые являются собственностью SmEl, например Reservation, изменяются только соответствующими бизнес-операциями SmEl.

## 4.4. Защита от устаревших сообщений

Устаревшее сообщение не должно перезаписывать более новое состояние.

Если внешний источник предоставляет:

- sequence number;
    
- version;
    
- event timestamp;
    
- revision ID,
    

оно используется для определения порядка изменений.

Если надежный порядок определить невозможно, SmEl использует контролируемую стратегию защиты от очевидно устаревших данных и фиксирует неопределенность.

## 4.5. Дублирование событий

Повторное получение одного и того же события не должно приводить к повторному бизнес-эффекту.

Интеграционный контур должен поддерживать идемпотентность операций синхронизации.

Для события рекомендуется сохранять:

- Event ID;
    
- внешний идентификатор;
    
- источник;
    
- время получения;
    
- результат обработки.
    

## 4.6. Конфликт с резервированием

ERP/WMS может сообщать физический остаток, который изменился независимо от внутренних Reservation.

SmEl не должен изменять Reservation для устранения такого расхождения.

Вместо этого Stock Service пересчитывает доступность с учетом актуального физического остатка и существующих внутренних резервов.

Если доступного количества стало недостаточно, система должна перевести ситуацию в контролируемое состояние и не допускать новых резервирований сверх доступного количества.

## 4.7. Конфликт во время Checkout

Checkout обязан повторно проверить актуальность Stock.

Если после добавления товара в Cart внешний остаток уменьшился, Checkout не должен использовать старое значение корзины.

Возможные результаты:

- количество доступно полностью;
    
- доступно меньше запрошенного;
    
- товар больше недоступен.
    

Checkout должен завершиться только после успешной актуализации соответствующих складских условий.

## 4.8. Конфликт после создания Reservation

Если после создания Reservation внешний остаток изменился таким образом, что физического товара недостаточно для выполнения всех обязательств, SmEl фиксирует нарушение доступности.

Reservation не должна автоматически считаться подтвержденной только потому, что ранее была создана.

Дальнейшее разрешение ситуации выполняется через Stock/Reservation Service и бизнес-процесс обработки исключения.

## 4.9. Отрицательные значения

Физический остаток не должен принимать отрицательное значение без явно определенной внешней бизнес-семантики.

Неожиданное отрицательное значение рассматривается как ошибка или исключительная ситуация.

Оно не должно автоматически приводить к неконтролируемой продаже товара.

## 4.10. Недоступность ERP/WMS

При временной недоступности внешней системы SmEl может продолжать работу на основании последнего успешно синхронизированного состояния, если это разрешено бизнес-правилами.

При этом система должна знать возраст данных.

Для устаревшего состояния может применяться признак:

**Stock Data Stale**.

Поведение Checkout при слишком старых данных должно определяться политикой актуальности.

Конкретный допустимый интервал устаревания пока не фиксируется.

## 4.11. Массовая синхронизация

Массовая синхронизация должна выполняться асинхронно.

Используются механизмы ADR-033:

```
Sync Request
     │
     ▼
Task Queue
     │
     ▼
Worker
     │
     ▼
Integration Layer
     │
     ▼
Stock Service
```

Frontend не должен ожидать завершения крупной синхронизации через длительный HTTP-запрос.

## 4.12. Повторная обработка

Временные ошибки интеграции допускают повторную попытку.

Retry должен быть:

- ограниченным;
    
- контролируемым;
    
- наблюдаемым;
    
- совместимым с идемпотентностью.
    

Бесконечные автоматические повторы запрещены.

## 4.13. Ошибочные данные

Если данные не прошли валидацию:

- Stock не изменяется;
    
- ошибка регистрируется;
    
- исходное сообщение сохраняется в необходимом объеме для диагностики;
    
- возможна повторная обработка после исправления причины.
    

## 4.14. Расхождение после полной сверки

Если полная синхронизация обнаружила расхождение между SmEl и ERP/WMS, приоритет имеет подтвержденное актуальное значение ERP/WMS для физического остатка.

Изменение фиксируется в истории.

Если расхождение указывает на возможную ошибку интеграции, оно дополнительно регистрируется как Integration/Stock Conflict.

## 4.15. Аудит

Для значимых изменений Stock рекомендуется сохранять:

- SKU;
    
- склад;
    
- старое значение;
    
- новое значение;
    
- источник;
    
- идентификатор события;
    
- время события;
    
- время обработки;
    
- результат;
    
- признак конфликта.
    

История должна позволять установить причину изменения остатка.

## 4.16. Безопасность

Внешняя система не получает прямого доступа к бизнес-таблицам SmEl.

Все изменения проходят через Integration Layer и внутренние сервисы.

Учетные данные интеграции хранятся согласно ADR-029.

Минимально необходимые права должны применяться к интеграционным учетным данным.

# 6. Заключительные положения

Фактический физический остаток может поступать из ERP/WMS, если такая система определена как внешний источник складских данных.

SmEl сохраняет собственное внутреннее состояние Stock и отвечает за его использование в бизнес-процессах.

Внешние данные не изменяют напрямую Reservation, Order или другие бизнес-сущности.

Основные принципы решения:

- ERP/WMS — источник фактического физического остатка;
    
- SmEl — источник истины для собственного состояния и бизнес-операций;
    
- Integration Layer — единственная граница внешней интеграции;
    
- Stock Service — единственная точка применения складских изменений;
    
- устаревшие и дублирующие сообщения не должны разрушать актуальное состояние;
    
- синхронизация должна быть идемпотентной;
    
- массовая синхронизация выполняется асинхронно;
    
- Checkout повторно проверяет актуальность Stock;
    
- Reservation не является заменой физическому остатку.
    

Конкретные ERP/WMS, протокол, период синхронизации, допустимый возраст данных и технический механизм упорядочивания событий уточняются при реализации.

```
Stock Service
  = точка применения складских изменений
```
