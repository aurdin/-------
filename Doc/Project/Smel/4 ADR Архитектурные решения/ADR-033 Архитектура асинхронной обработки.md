# 1. Назначение

Настоящее архитектурное решение определяет принципы выполнения длительных, ресурсоёмких, фоновых и событийно-зависимых операций в SmEl.

Решение отделяет синхронную обработку пользовательских запросов от операций, которые не требуют непосредственного выполнения в рамках HTTP-запроса.

# 2. Область применения

Решение распространяется на:

- импорт и синхронизацию данных;
    
- синхронизацию остатков;
    
- обработку внешних событий;
    
- отправку уведомлений;
    
- фоновые операции;
    
- длительные и ресурсоёмкие задачи;
    
- периодические задачи;
    
- задачи, выполняемые после завершения пользовательской операции.
    

Решение не определяет конкретный Message Broker, библиотеку очередей или планировщик задач.

# 3. Основная часть

## 3.1. Принцип асинхронной обработки

Операции, длительность или характер которых не требуют синхронного ответа пользователю, могут выполняться асинхронно.

Синхронный REST API не должен удерживать пользовательский HTTP-запрос во время длительной фоновой операции без архитектурной необходимости.

Асинхронная обработка не должна изменять установленные границы бизнес-доменов.

## 3.2. Архитектура

Общая архитектура:

```
Frontend
    │
    ▼
REST API
    │
    ▼
Service Layer
    │
    ├──────────────► Синхронная операция
    │
    └──────────────► Async Task
                         │
                         ▼
                    Task Queue
                         │
                         ▼
                       Worker
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       PostgreSQL    Integration     External
                       Layer          Systems
```

REST API инициирует асинхронную операцию через Service Layer.

Worker выполняет задачу независимо от HTTP-запроса.

## 3.3. Service Layer

Service Layer является точкой принятия решения о необходимости асинхронного выполнения бизнес-операции.

Frontend не определяет внутренний способ выполнения операции.

REST API не содержит самостоятельной реализации фоновой бизнес-логики.

Бизнес-правила остаются в Service Layer независимо от способа выполнения операции.

## 3.4. Worker

Worker является исполняющим компонентом фоновых задач.

Worker:

- получает задачу;
    
- выполняет соответствующую операцию;
    
- использует Service Layer;
    
- взаимодействует с доменными сервисами;
    
- взаимодействует с Integration Layer;
    
- фиксирует результат;
    
- обрабатывает ошибки;
    
- обеспечивает контролируемое повторное выполнение.
    

Worker не должен содержать дублирующую бизнес-логику, существующую в Service Layer.

## 3.5. Очередь задач

Для передачи фоновых задач между инициатором и Worker используется абстракция очереди задач.

Очередь обеспечивает:

- передачу задачи;
    
- временное хранение задачи до выполнения;
    
- контроль состояния обработки;
    
- возможность повторного выполнения;
    
- разделение инициатора и исполнителя.
    

Конкретная технология очереди не фиксируется настоящим ADR.

## 3.6. Типы асинхронных операций

Архитектура предусматривает следующие типы:

### 3.6.1. Отложенные задачи

Операция запускается после завершения инициирующего действия.

Примеры:

- отправка уведомления;
    
- обновление производных данных;
    
- запуск дополнительной обработки.
    

### 3.6.2. Длительные задачи

Операции, которые могут выполняться значительное время.

Примеры:

- импорт каталога;
    
- массовая синхронизация;
    
- обработка большого объёма данных.
    

### 3.6.3. Периодические задачи

Операции, выполняемые по расписанию.

Примеры:

- синхронизация остатков;
    
- контроль актуальности данных;
    
- очистка временных данных;
    
- технические операции.
    

### 3.6.4. Событийные задачи

Операции, инициированные внешним или внутренним событием.

Примеры:

- получение события от платёжного провайдера;
    
- изменение статуса доставки;
    
- получение результата внешней синхронизации.
    

## 3.7. Идемпотентность

Асинхронные операции, повторное выполнение которых возможно, должны быть идемпотентными либо иметь механизм защиты от повторного применения результата.

Повторная доставка одной задачи не должна приводить к неконтролируемому повторению бизнес-операции.

Особое значение это имеет для:

- платежей;
    
- возвратов;
    
- резервирования;
    
- изменения остатков;
    
- внешних интеграций;
    
- обработки webhook/event.
    

## 3.8. Ошибки и повторное выполнение

Ошибка выполнения задачи должна фиксироваться независимо от пользовательского HTTP-запроса.

Для временных ошибок допускается повторное выполнение.

Количество и стратегия повторов должны определяться типом операции.

Ошибки, которые невозможно устранить повтором, должны переводить задачу в контролируемое состояние ошибки и фиксироваться для последующего анализа.

Бесконечное автоматическое повторение не допускается.

## 3.9. Транзакционность

Изменение бизнес-данных выполняется через Service Layer с соблюдением правил транзакционности, определённых архитектурой SmEl.

Постановка задачи в очередь и изменение бизнес-данных должны проектироваться таким образом, чтобы избежать ситуации, когда бизнес-операция считается выполненной, но соответствующая задача потеряна.

Конкретный механизм гарантированной публикации задач определяется при технической детализации архитектуры.

## 3.10. Импорт

Импорт данных может выполняться асинхронно.

Типовой процесс:

```
Источник
   │
   ▼
Integration Layer
   │
   ▼
Создание задачи
   │
   ▼
Queue
   │
   ▼
Worker
   │
   ▼
Validation
   │
   ▼
Mapping
   │
   ▼
Transformation
   │
   ▼
Synchronization
   │
   ▼
Business Domain
```

Ошибки отдельных записей не должны без необходимости останавливать обработку всего задания.

## 3.11. Синхронизация остатков

Синхронизация остатков может выполняться асинхронно.

Worker получает данные через Integration Layer и передаёт их в Stock Synchronization Service.

Архитектура должна поддерживать:

- полную синхронизацию;
    
- инкрементальную синхронизацию;
    
- повторную обработку;
    
- контроль результата;
    
- журналирование ошибок.
    

Конкретные правила синхронизации определяются ADR-042.

## 3.12. Внешние события

Внешние системы не должны напрямую изменять доменные данные SmEl.

Событие поступает через Integration Layer, после чего:

```
External System
       │
       ▼
Integration Layer
       │
       ▼
Validation
       │
       ▼
Task / Event Processing
       │
       ▼
Service Layer
       │
       ▼
Domain Data
```

Такой подход применяется, в частности, к платёжным и транспортным интеграциям.

## 3.13. Контейнеризация

Workers рассматриваются как отдельные исполняемые компоненты и могут выполняться в отдельных Docker-контейнерах в соответствии с ADR-032.

Количество экземпляров Worker может изменяться независимо от Backend при необходимости.

Асинхронная обработка не должна требовать изменения архитектурных границ контейнеризации.

## 3.14. Наблюдаемость

Асинхронные задачи должны иметь возможность контролироваться по меньшей мере на уровне:

- идентификатора задачи;
    
- типа операции;
    
- времени создания;
    
- времени начала;
    
- времени завершения;
    
- текущего состояния;
    
- результата;
    
- ошибки;
    
- количества повторных попыток.
    

Логи не должны содержать секреты и чувствительные данные.

## 3.15. Безопасность

Фоновая задача выполняется с минимально необходимыми правами.

Worker не получает автоматически все права Backend.

Доступ к данным и операциям определяется архитектурными правами соответствующего процесса.

Секреты передаются Worker через механизм конфигурации и секретов окружения в соответствии с ADR-029.

# 4. Правила

1. Длительные и ресурсоёмкие операции не должны без необходимости выполняться внутри пользовательского HTTP-запроса.
    
2. Асинхронные операции инициируются через Service Layer.
    
3. Worker не содержит дублирующую бизнес-логику.
    
4. Очередь отделяет инициатора задачи от её исполнителя.
    
5. Повторяемые задачи должны быть идемпотентными либо защищёнными от повторного применения.
    
6. Бесконечные автоматические повторы запрещены.
    
7. Ошибки фоновых задач должны быть контролируемыми и наблюдаемыми.
    
8. Внешние события проходят через Integration Layer.
    
9. Внешние системы не получают прямого доступа к PostgreSQL.
    
10. Workers могут независимо масштабироваться относительно Backend.
    
11. Workers могут контейнеризироваться согласно ADR-032.
    
12. Конкретный Message Broker не фиксируется настоящим ADR.
    
13. Выбор конкретного механизма очередей выполняется только при наличии соответствующей архитектурной необходимости.
    
14. Бизнес-операции выполняются через Service Layer.
    
15. Асинхронность не должна нарушать границы доменов и источника истины SmEl.

# 6. Заключительные положения

Асинхронная обработка является самостоятельным архитектурным механизмом SmEl для длительных, фоновых и событийно-зависимых операций.

Архитектура отделяет инициирование операции от её выполнения и обеспечивает возможность масштабирования и повторной обработки.

Конкретная технология очередей и Message Broker не определяется настоящим ADR и может быть выбрана отдельным решением при возникновении необходимости.
