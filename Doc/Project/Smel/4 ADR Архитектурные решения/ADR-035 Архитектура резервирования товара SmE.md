# 1. Назначение

ADR-035 определяет архитектурные принципы резервирования товарных позиций SmEl.

Документ устанавливает границы между остатками, резервированием, корзиной, Checkout, заказом, оплатой и доставкой.

Цель решения — обеспечить управляемое резервирование доступного товара при подготовке и оформлении заказа, исключить неконтролируемое уменьшение остатков и обеспечить корректное освобождение резерва.

# 2. Область применения

Решение распространяется на:

- SKU и товарные остатки;
    
- доступное количество товара;
    
- резерв товара;
    
- Cart и Cart Item;
    
- Checkout;
    
- Order и Order Item;
    
- Payment;
    
- Delivery;
    
- Service Layer;
    
- синхронизацию остатков с внешними ERP/WMS;
    
- асинхронные операции, связанные с резервированием.
    

ADR-035 не определяет:

- конкретную ERP/WMS;
    
- конкретную платёжную систему;
    
- конкретного провайдера доставки;
    
- конкретную технологию блокировок;
    
- конкретную очередь сообщений;
    
- конкретный срок действия резерва;
    
- конкретные значения бизнес-таймаутов.
    

# 3. Основная часть

## 3.1. Назначение резерва

Резерв представляет собой временное выделение определённого количества SKU для конкретной бизнес-операции.

Резерв не является физическим уменьшением складского остатка.

Резерв должен учитываться отдельно от:

- физического количества;
    
- доступного количества;
    
- поступающего количества;
    
- количества в заказе;
    
- фактически списанного товара.
    

Резервирование не изменяет Product/SKU как объект каталога.

## 3.2. Граница ответственности

Остатки определяют наличие товара.

Резервирование определяет временно выделенное количество товара.

Cart показывает намерение клиента приобрести товар и сам по себе не создаёт резерв.

Checkout проверяет возможность резервирования и инициирует соответствующую бизнес-операцию.

Order фиксирует результат оформления заказа.

Payment определяет финансовое состояние операции и не заменяет механизм резервирования.

Delivery использует результат оформленного заказа и не управляет складским резервом как самостоятельной бизнес-функцией.

## 3.3. Архитектурная схема

```
Cart
  │
  ▼
Checkout
  │
  ▼
Stock / Reservation Service
  │
  ├──► Stock
  │
  └──► Reservation
          │
          ▼
        Order
          │
     ┌────┴────┐
     ▼         ▼
 Payment    Delivery
```

Все операции выполняются через Service Layer.

Frontend не создаёт, изменяет и не снимает резерв самостоятельно.

## 3.4. Создание резерва

Создание резерва должно происходить только после проверки:

- существования SKU;
    
- возможности продажи SKU;
    
- необходимого количества;
    
- актуального доступного остатка;
    
- допустимости операции для клиента;
    
- актуальных коммерческих условий;
    
- состояния Checkout.
    

Наличие товара в Cart не означает наличие резерва.

Создание резерва должно быть атомарной бизнес-операцией.

При недостаточном доступном количестве резерв не создаётся.

## 3.5. Связь с Cart и Checkout

Cart Item является предварительным намерением приобрести товар.

На этапе Checkout Backend повторно проверяет:

- SKU;
    
- количество;
    
- цену;
    
- скидки;
    
- акции;
    
- валюту;
    
- коммерческие условия;
    
- доступный остаток.
    

После успешной проверки может быть создан резерв.

Таким образом:

```
Cart Item
   │
   ▼
Revalidation
   │
   ▼
Reservation
   │
   ▼
Order
```

Изменение содержимого корзины не должно автоматически приводить к резервированию товара, если отдельными бизнес-правилами не установлено иное.

## 3.6. Жизненный цикл резерва

Резерв должен иметь собственный жизненный цикл.

Базовая модель:

```
Created
   │
   ▼
Active
   │
   ├──► Confirmed
   │
   ├──► Released
   │
   └──► Expired
```

Дополнительные состояния могут быть введены при необходимости.

Состояние `Confirmed` означает, что резерв связан с подтверждённым результатом бизнес-операции.

Состояние `Released` означает, что зарезервированное количество снова доступно для использования в соответствии с правилами складского учёта.

Состояние `Expired` означает автоматическое завершение резерва по истечении установленного срока.

Конкретный набор состояний может быть уточнён при детальной реализации.

## 3.7. Связь резерва с заказом

После успешного создания Order резерв должен быть однозначно связан с соответствующей операцией заказа.

Order не должен зависеть от текущего состояния Cart.

Изменение или удаление Cart после создания Order не должно изменять резерв заказа.

При невозможности корректного создания Order ранее созданный резерв должен быть освобождён или переведён в другое допустимое состояние согласно правилам транзакции.

## 3.8. Связь с оплатой

Резервирование и Payment являются независимыми бизнес-операциями.

Успешное резервирование не означает успешную оплату.

Успешная оплата не должна автоматически создавать резерв задним числом.

Связь между Payment и Reservation определяется бизнес-процессом заказа.

При необходимости резерв может сохраняться до подтверждения оплаты, а при неуспешной или отменённой оплате освобождаться.

Конкретная последовательность:

```
Reservation → Payment
```

или

```
Payment → Reservation
```

не фиксируется настоящим ADR как универсальное правило и должна определяться конкретным сценарием оформления заказа.

## 3.9. Срок действия резерва

Резерв может иметь ограниченный срок действия.

Архитектура должна поддерживать:

- время создания;
    
- время окончания;
    
- автоматическое истечение;
    
- ручное освобождение;
    
- продление, если такое правило будет введено;
    
- фиксацию причины завершения.
    

Конкретный срок действия резерва не устанавливается ADR-035.

## 3.10. Конкурентное резервирование

При одновременных запросах нескольких клиентов Backend должен предотвращать превышение доступного количества товара.

Операция резервирования должна обеспечивать согласованное изменение:

```
Available Quantity
        +
Reserved Quantity
```

Нельзя допускать создание резервов, суммарное количество которых превышает доступный объём товара.

Конкретный механизм обеспечения конкурентного доступа определяется на уровне физической реализации и базы данных.

## 3.11. Идемпотентность

Операции создания, подтверждения и освобождения резерва должны быть защищены от неконтролируемого повторного выполнения.

Повтор одного и того же запроса не должен создавать несколько независимых резервов для одной бизнес-операции.

Это особенно важно при:

- повторных HTTP-запросах;
    
- сетевых сбоях;
    
- повторной доставке внешних событий;
    
- повторном выполнении фоновых задач;
    
- восстановлении после ошибки.
    

Для асинхронных операций применяются принципы ADR-033.

## 3.12. Синхронизация с ERP/WMS

Внешняя ERP/WMS может предоставлять данные о фактическом складском состоянии.

Интеграция выполняется через Integration Layer согласно ADR-028.

Внешняя система не должна напрямую изменять внутренние Reservation.

Полученные данные проходят:

```
ERP/WMS
   │
   ▼
Integration Layer
   │
   ▼
Stock Synchronization Service
   │
   ▼
Stock Domain
```

Правила разрешения конфликтов между SmEl и ERP/WMS определяются ADR-042.

## 3.13. Освобождение резерва

Резерв должен освобождаться при наступлении предусмотренного бизнес-события.

Возможные причины:

- отмена заказа;
    
- отказ от оформления;
    
- неуспешная операция оплаты;
    
- истечение срока;
    
- невозможность дальнейшего исполнения заказа;
    
- ручная отмена уполномоченным пользователем;
    
- другие бизнес-события.
    

Освобождение должно быть отдельной контролируемой операцией.

Повторное освобождение уже освобождённого резерва не должно приводить к повторному увеличению доступного количества.

# 4. Правила

1. Резерв является отдельной сущностью складского домена.
    
2. Cart Item не создаёт резерв автоматически.
    
3. Checkout проверяет актуальность товара и возможность резервирования.
    
4. Резерв создаётся только Backend.
    
5. Frontend не управляет резервом непосредственно.
    
6. Резерв не является физическим складским остатком.
    
7. Суммарный объём активных резервов не должен превышать доступное количество.
    
8. Создание резерва должно быть атомарной бизнес-операцией.
    
9. Резерв имеет собственный жизненный цикл.
    
10. Резерв может иметь срок действия.
    
11. Резерв должен быть однозначно связан с соответствующей бизнес-операцией.
    
12. Order и Reservation являются различными сущностями.
    
13. Payment и Reservation являются различными бизнес-операциями.
    
14. Освобождение резерва является контролируемой операцией.
    
15. Повторное выполнение операций резервирования не должно создавать дублирующие резервы.
    
16. Внешние ERP/WMS не изменяют Reservation напрямую.
    
17. Все бизнес-операции резервирования проходят через Service Layer.
    
18. Асинхронные операции резервирования подчиняются ADR-033.
    
19. Конкретные правила конфликтов ERP/WMS определяются ADR-042.
    
20. Конкретный механизм технической блокировки определяется при физической реализации.

# 6. Заключительные положения

ADR-035 устанавливает архитектурную модель резервирования товара SmEl и отделяет её от хранения остатков, корзины, заказа, оплаты и доставки.

Архитектура предусматривает создание резерва на этапе Checkout, отдельный жизненный цикл, контроль конкурентного доступа, идемпотентность и управляемое освобождение.

Конкретные сроки действия резерва, последовательность резервирования и оплаты, технический механизм блокировок и правила разрешения конфликтов с ERP/WMS остаются предметом дальнейшей детализации.
