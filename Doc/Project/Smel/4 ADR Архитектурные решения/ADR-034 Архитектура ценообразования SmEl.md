# 1. Назначение

Настоящее архитектурное решение определяет архитектуру ценообразования SmEl.

Решение устанавливает единый подход к формированию коммерческой стоимости товара с учётом базовой стоимости, скидок и акций, а также правила получения и фиксации итоговой стоимости.

# 2. Область применения

Решение распространяется на:

- базовую стоимость товара;
    
- прайс-листы;
    
- цены SKU;
    
- скидки;
    
- акции;
    
- коммерческие условия;
    
- группы клиентов;
    
- периоды действия коммерческих условий;
    
- расчёт стоимости Cart Item;
    
- расчёт итоговой стоимости Checkout;
    
- фиксацию стоимости Order Item.
    

Настоящее решение не определяет конкретную налоговую модель, платёжного провайдера или пользовательский интерфейс.

# 3. Основная часть

## 3.1. Единый блок ценообразования

В SmEl **стоимость, скидки и акции рассматриваются как части единого блока ценообразования**.

Блок ценообразования является источником правил формирования актуальной коммерческой стоимости товара.

Архитектура разделяет:

- исходную стоимость;
    
- коммерческие условия;
    
- применённые скидки;
    
- применённые акции;
    
- итоговую стоимость.
    

## 3.2. Источник цены

Базовая цена определяется Backend на основании актуальных коммерческих данных.

Frontend не является источником цены и не может самостоятельно устанавливать стоимость товара.

Цена, отображаемая пользователю, должна быть получена через REST API.

Backend является источником истины для актуальной коммерческой стоимости.

## 3.3. Прайс-листы

SmEl поддерживает несколько прайс-листов.

Прайс-лист может определять:

- набор SKU;
    
- базовую цену;
    
- валюту;
    
- период действия;
    
- группу клиентов или иное условие применимости;
    
- приоритет.
    

Конкретный набор правил выбора прайс-листа определяется бизнес-требованиями и может быть уточнён отдельным решением.

## 3.4. Скидки

Скидка является коммерческим механизмом уменьшения стоимости.

Скидка может зависеть от:

- SKU;
    
- категории;
    
- количества;
    
- группы клиента;
    
- прайс-листа;
    
- периода действия;
    
- иных коммерческих условий.
    

Скидка не изменяет исходную цену как историческое значение.

Результат применения скидки является частью рассчитанной коммерческой стоимости.

## 3.5. Акции

Акция является отдельным коммерческим механизмом, способным изменять условия покупки.

Акция может предоставлять:

- скидку;
    
- специальную цену;
    
- ценовое преимущество;
    
- условное коммерческое предложение.
    

Акция не должна напрямую изменять исходные данные товара.

Её результат определяется механизмом ценообразования.

## 3.6. Порядок расчёта

Расчёт коммерческой стоимости выполняется централизованно на Backend.

Общая модель:

```
SKU
 │
 ▼
Актуальная базовая цена
 │
 ▼
Проверка прайс-листа
 │
 ▼
Проверка коммерческих условий
 │
 ▼
Определение применимых скидок
 │
 ▼
Определение применимых акций
 │
 ▼
Расчёт итоговой стоимости
 │
 ▼
Cart Item / Checkout
 │
 ▼
Order Item
```

Конкретный математический алгоритм и порядок применения нескольких скидок и акций должны быть однозначно определены бизнес-правилами.

## 3.7. Приоритет коммерческих условий

Если одновременно применимы несколько коммерческих условий, Backend должен определить набор условий, которые могут быть применены совместно.

Не допускается неконтролируемое суммирование скидок и акций.

Для каждого применяемого коммерческого условия должна быть возможность определить:

- основание применения;
    
- период действия;
    
- источник;
    
- размер или эффект;
    
- результат применения.
    

## 3.8. Конфликт скидок и акций

При наличии нескольких взаимоисключающих условий должна применяться определённая политика выбора.

Допустимые архитектурные стратегии:

- приоритет;
    
- наиболее выгодное условие;
    
- взаимоисключающие группы;
    
- последовательное применение;
    
- комбинация правил.
    

Конкретная стратегия для SmEl является отдельным бизнес-решением и должна быть зафиксирована до реализации соответствующего расчёта.

## 3.9. Расчёт Cart Item

При добавлении товара в корзину Backend получает актуальные коммерческие условия и рассчитывает стоимость.

Cart Item может содержать результат текущего расчёта:

- количество;
    
- применённую стоимость;
    
- скидку;
    
- применённую акцию;
    
- валюту;
    
- итоговую стоимость позиции.
    

Этот результат является временным и не заменяет окончательную проверку Checkout.

## 3.10. Повторный расчёт при Checkout

Перед созданием Order Backend повторно проверяет коммерческие условия.

Проверяются:

- существование SKU;
    
- возможность продажи;
    
- актуальность цены;
    
- применимость скидок;
    
- применимость акций;
    
- валюта;
    
- коммерческие ограничения;
    
- количество.
    

Изменение стоимости или коммерческих условий между добавлением товара в корзину и Checkout не является само по себе ошибкой.

Checkout использует актуальные условия Backend.

## 3.11. Фиксация стоимости в Order

При создании Order результат ценообразования фиксируется в Order Item.

Order Item должен сохранять коммерческий результат покупки, необходимый для последующего восстановления состава заказа и его стоимости.

Изменение будущей цены, скидки или акции не должно изменять историческую стоимость уже созданного заказа.

## 3.12. История цен

Изменения коммерческой стоимости должны сохраняться таким образом, чтобы можно было определить историческое значение цены, действовавшее в соответствующий период.

История необходима для:

- аудита;
    
- анализа заказов;
    
- восстановления коммерческого результата;
    
- контроля изменений;
    
- интеграций.
    

## 3.13. Валюта

Стоимость должна быть связана с определённой валютой.

Все операции расчёта внутри одной коммерческой операции должны использовать согласованную валюту.

Автоматическая конвертация валют не вводится настоящим ADR и требует отдельного решения при необходимости.

## 3.14. Архитектурное размещение

Расчёт выполняется через Service Layer.

Архитектура:

```
Frontend
   │
   ▼
REST API
   │
   ▼
Pricing Service
   │
   ├── Price
   ├── Discount
   ├── Promotion
   ├── Price List
   └── Commercial Rules
   │
   ▼
PostgreSQL
```

Frontend не реализует собственный независимый расчёт итоговой стоимости.

## 3.15. Асинхронность

Обычный расчёт стоимости Cart Item и Checkout должен выполняться синхронно, поскольку результат необходим для продолжения пользовательской операции.

Асинхронная обработка может использоваться для:

- массового обновления цен;
    
- импорта прайс-листов;
    
- массового применения коммерческих данных;
    
- фоновой синхронизации.
    

Такие операции выполняются в соответствии с ADR-033.

# 4. Правила

1. Стоимость, скидки и акции являются частями единого блока ценообразования.
    
2. Backend является источником истины для актуальной коммерческой стоимости.
    
3. Frontend не устанавливает цену и не является источником коммерческих правил.
    
4. Исходная цена не изменяется вследствие применения скидки или акции.
    
5. Скидки и акции применяются централизованным механизмом ценообразования.
    
6. Неконтролируемое суммирование скидок и акций запрещено.
    
7. Все применённые коммерческие условия должны быть определимы при формировании результата расчёта.
    
8. Cart Item содержит временный результат ценообразования.
    
9. Checkout выполняет повторную проверку актуальных коммерческих условий.
    
10. Order Item фиксирует коммерческий результат покупки.
    
11. Изменение будущих цен не изменяет стоимость существующего заказа.
    
12. Исторические коммерческие данные должны сохраняться в необходимом объёме.
    
13. Расчёт выполняется через Service Layer.
    
14. Асинхронность применяется для массовых и фоновых операций, но не заменяет синхронный расчёт, необходимый пользователю.
    
15. Конкретные бизнес-правила приоритета скидок и акций должны быть определены до их реализации.

# 6. Заключительные положения

Ценообразование SmEl является централизованным механизмом формирования коммерческой стоимости.

Стоимость, скидки и акции не рассматриваются как независимые архитектурные подсистемы, а образуют единый блок ценообразования.

Актуальный результат рассчитывается Backend, а результат покупки фиксируется в Order Item.

Конкретные правила применения нескольких скидок и акций должны быть определены до реализации соответствующего функционала.
