# 1. Назначение

Настоящее архитектурное решение определяет принцип организации учета товарных остатков и складских данных в проекте **Smart Electric (SmEl)**.

Решение фиксирует самостоятельность складского учета и его отделение от каталога товаров и коммерческих условий.

# 2. Область применения

Решение применяется к данным и операциям, связанным с:

- товарными остатками;
    
- складами;
    
- резервированием товаров;
    
- ожидаемыми поступлениями;
    
- доступным количеством;
    
- определением доступности товара для продажи;
    
- интеграцией с ERP, WMS и другими учетными системами.
    

Каталог товаров и коммерческие условия не являются местом хранения оперативных складских данных.

# 3. Основная часть

## 3.1. Самостоятельность складского учета

В SmEl учет товарных остатков выделяется в самостоятельную подсистему.

Остатки не являются свойством товара и не входят непосредственно в состав коммерческих условий.

Каждый `SKU` может одновременно находиться на одном или нескольких складах, при этом для каждого склада ведется независимый учет.

## 3.2. Логическая модель

```
Product (SKU)
      │
      └──────────────< Stock
                            │
                            ├── Warehouse
                            ├── Quantity Available
                            ├── Quantity Reserved
                            ├── Quantity Incoming
                            ├── Quantity On Order
                            ├── Last Update
                            └── Status
```

## 3.3. Назначение подсистемы

Подсистема складского учета отвечает за:

- учет остатков по каждому складу;
    
- резервирование товаров;
    
- учет ожидаемых поставок;
    
- отображение доступного количества;
    
- определение доступности товара для продажи;
    
- обмен данными с ERP, WMS и другими учетными системами.
    

## 3.4. Структура складских данных

```
SKU
   │
   ├── Warehouse A
   │      ├── Available
   │      ├── Reserved
   │      ├── Incoming
   │      └── Status
   │
   ├── Warehouse B
   │      ├── Available
   │      ├── Reserved
   │      ├── Incoming
   │      └── Status
   │
   └── Warehouse C
          └── ...
```

# 4. Правила

1. Каждый `SKU` может иметь множество записей остатков.
    
2. Каждая запись остатков относится только к одному складу.
    
3. Остатки не хранятся непосредственно в основной сущности товара (`Product`).
    
4. Изменение остатков не изменяет структуру каталога.
    
5. Остатки обновляются независимо от цен и характеристик товара.
    
6. Резервирование и ожидаемые поступления учитываются отдельно от доступного физического остатка.
    
7. Логика определения доступного количества должна быть централизована.
    
8. Операции резервирования, списания и поступления выполняются через специализированные сервисы.
    
9. Операции складского учета должны обеспечивать целостность данных.
    
10. Изменение остатков не должно изменять идентификатор товара (`SKU`) или его коммерческие условия.
    

# 5. Обоснование

Самостоятельное выделение складского учета выбрано по следующим причинам:

- разделение каталога и оперативного учета;
    
- поддержка нескольких складов;
    
- возможность интеграции с внешними системами учета;
    
- независимое обновление остатков без изменения данных товара;
    
- подготовка к работе с распределенной складской сетью;
    
- возможность частого обновления складской информации без нагрузки на основной каталог.
    

# 6. Последствия

## 6.1. Преимущества

- независимое управление складскими остатками;
    
- поддержка мультискладского учета;
    
- возможность отображения доступности товара по складам;
    
- упрощение интеграции с ERP и WMS;
    
- масштабируемость при добавлении новых складов и каналов поставки;
    
- снижение нагрузки на каталог при частом обновлении остатков.
    

## 6.2. Ограничения

- остатки не должны храниться непосредственно в сущности `Product`;
    
- логика расчета доступного количества должна быть централизована;
    
- изменение остатков не должно влиять на идентификацию товара (`SKU`) и его коммерческие условия;
    
- операции резервирования, списания и поступления требуют специализированной логики, обеспечивающей целостность складских данных;
    
- конкретные правила резервирования, списания и синхронизации с внешними системами требуют отдельных архитектурных решений.

# 8. Заключительные положения

Настоящее решение фиксирует архитектурное разделение трех самостоятельных аспектов товарной информации:

- **каталог товаров** — что представляет собой товар;
    
- **коммерческие условия** — по какой цене и на каких условиях он продается;
    
- **складской учет** — где находится товар и в каком количестве он доступен.
    

Такое разделение позволяет независимо развивать соответствующие подсистемы, интегрировать SmEl с внешними ERP/WMS-системами и поддерживать как учет одного склада, так и распределенную складскую инфраструктуру без изменения базовой архитектуры каталога.
