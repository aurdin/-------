# 1. Назначение

Настоящее архитектурное решение определяет общие принципы построения production-инфраструктуры проекта SmEl.

Документ устанавливает логическое разделение компонентов, сетевые границы, требования к размещению приложений, базы данных, интеграционного контура и вспомогательных инфраструктурных компонентов.

Конкретные поставщики облачной инфраструктуры, серверное оборудование, операционная система и конкретные технологии развертывания настоящим решением не фиксируются.

# 2. Область применения

Решение применяется к production-среде SmEl и охватывает:

- Frontend;
    
- Backend;
    
- REST API;
    
- PostgreSQL;
    
- Service Layer;
    
- Integration Layer;
    
- внешние сервисы;
    
- хранилище медиа;
    
- резервное копирование;
    
- мониторинг и журналирование;
    
- сетевые и защитные компоненты.
    

Среды разработки и тестирования не являются основной областью настоящего решения.

# 3. Основная часть

## 3.1. Общие принципы

Production-инфраструктура должна обеспечивать разделение:

- клиентского слоя;
    
- прикладного слоя;
    
- слоя данных;
    
- интеграционного слоя;
    
- инфраструктурных сервисов.
    

Компоненты должны размещаться с учётом их ответственности и уровня доверия.

Общая логическая архитектура:

```
                    Internet
                       │
                       ▼
              ┌────────────────┐
              │ Public Entry   │
              │ / Web Layer    │
              └───────┬────────┘
                      │
             ┌────────┴────────┐
             ▼                 ▼
        Frontend           REST API
                              │
                              ▼
                       Backend / Django
                              │
                              ▼
                       Service Layer
                       │          │
                       ▼          ▼
                   PostgreSQL  Integration
                                  Layer
                                    │
                         ┌──────────┼──────────┐
                         ▼          ▼          ▼
                      Payment    Delivery   ERP / WMS
                      Provider   Provider
```

## 3.2. Frontend

Frontend является клиентской частью системы и предоставляет пользовательский интерфейс.

Frontend:

- не имеет прямого доступа к PostgreSQL;
    
- не имеет прямого доступа к внутренним сервисам Backend;
    
- взаимодействует с Backend через REST API;
    
- не содержит серверных секретов;
    
- не выполняет критические бизнес-операции самостоятельно.
    

Frontend может размещаться отдельно от Backend и обслуживаться специализированным web/CDN-слоем.

Конкретный способ размещения определяется техническим решением.

## 3.3. Backend

Backend является центральным прикладным компонентом production-среды.

Он предоставляет:

- REST API;
    
- аутентификацию и авторизацию;
    
- бизнес-операции;
    
- Service Layer;
    
- доступ к данным;
    
- интеграционные операции;
    
- административные функции.
    

Backend должен быть доступен из внешней сети только через контролируемую точку входа.

## 3.4. Service Layer

Service Layer является внутренним прикладным уровнем Backend.

Он не должен предоставляться непосредственно Internet-клиентам.

Все критические бизнес-операции выполняются внутри Backend через определённые сервисы.

Production-размещение не должно создавать возможность обхода Service Layer для внешнего клиента.

## 3.5. PostgreSQL

PostgreSQL является основным хранилищем бизнес-данных SmEl.

База данных должна быть изолирована от непосредственного доступа из Internet.

Доступ к PostgreSQL предоставляется только необходимым внутренним компонентам Backend и инфраструктурным операциям.

Frontend не имеет доступа к PostgreSQL.

Внешние интеграционные системы также не должны получать прямой доступ к базе данных.

## 3.6. Integration Layer

Integration Layer является границей взаимодействия SmEl с внешними системами.

Через него могут выполняться интеграции с:

- платёжными провайдерами;
    
- службами доставки;
    
- ERP;
    
- WMS;
    
- поставщиками;
    
- иными внешними системами.
    

Внешняя система не должна обращаться непосредственно к внутренним таблицам PostgreSQL.

Интеграционные операции должны выполняться через контролируемые интерфейсы.

## 3.7. Сетевые границы

Production-среда должна иметь разделение сетевых зон с различным уровнем доступности.

Минимально должны быть выделены:

```
Public Zone
     │
     ▼
Application Zone
     │
     ▼
Data Zone
```

В Public Zone размещаются компоненты, которым необходим внешний доступ.

Application Zone содержит Backend и внутренние прикладные компоненты.

Data Zone содержит PostgreSQL и другие внутренние хранилища.

Прямой внешний доступ к Data Zone запрещается.

## 3.8. HTTPS и внешний доступ

Внешнее взаимодействие с системой должно осуществляться по защищённому протоколу HTTPS.

HTTP-трафик не должен использоваться для передачи защищаемых данных в production.

Точка внешнего входа должна обеспечивать контролируемую маршрутизацию запросов к Frontend и REST API.

Конкретный reverse proxy, load balancer или иной edge-компонент определяется отдельным техническим решением.

## 3.9. Масштабирование

Архитектура должна допускать независимое масштабирование компонентов.

В первую очередь должна существовать возможность масштабирования:

- Frontend;
    
- Backend;
    
- отдельных интеграционных процессов;
    
- фоновых задач;
    
- хранилища медиа.
    

PostgreSQL масштабируется с учётом требований к согласованности и характеру нагрузки.

Конкретная стратегия horizontal/vertical scaling настоящим ADR не фиксируется.

## 3.10. Фоновые процессы

Операции, которые не требуют непосредственного ответа пользователю, могут выполняться асинхронно.

К ним могут относиться:

- импорт;
    
- синхронизация остатков;
    
- обработка внешних событий;
    
- отправка уведомлений;
    
- формирование резервных копий;
    
- тяжёлые операции обработки данных.
    

Использование очереди сообщений, task queue или конкретного брокера определяется отдельным техническим решением.

## 3.11. Мониторинг и журналирование

Production-инфраструктура должна обеспечивать централизованный контроль:

- доступности компонентов;
    
- ошибок;
    
- производительности;
    
- интеграций;
    
- фоновых процессов;
    
- базы данных;
    
- резервного копирования.
    

Логи не должны содержать секреты и иные данные, которые не должны раскрываться.

Критические события должны быть доступны для диагностики и аудита.

## 3.12. Резервное копирование

Production-инфраструктура должна быть связана с системой резервного копирования, определённой ADR-030.

Резервные копии не должны храниться исключительно на том же инфраструктурном ресурсе, что и рабочая база данных.

Процедура восстановления должна быть независима от конкретного экземпляра production-сервера.

## 3.13. Управление секретами

Production-секреты должны управляться согласно ADR-029.

Они не должны:

- храниться в исходном коде;
    
- передаваться Frontend;
    
- включаться в публичные конфигурационные файлы;
    
- попадать в логи.
    

Production и другие среды должны быть логически разделены.

## 3.14. Отказоустойчивость

Production-архитектура должна предусматривать возможность восстановления после отказа отдельных компонентов.

Критические компоненты должны иметь определённую стратегию восстановления.

Приоритет восстановления определяется бизнес-критичностью:

1. доступность прикладного контура;
    
2. доступность базы данных;
    
3. восстановление интеграций;
    
4. восстановление вторичных сервисов.
    

Конкретные SLA, RPO и RTO определяются отдельными требованиями.

# 4. Правила

1. Production-среда должна иметь логическое разделение клиентского, прикладного, интеграционного и информационного уровней.
    
2. Frontend не имеет прямого доступа к PostgreSQL.
    
3. Внешние системы не имеют прямого доступа к PostgreSQL.
    
4. Backend является центральным прикладным компонентом.
    
5. Service Layer не предоставляется непосредственно внешним клиентам.
    
6. REST API является контролируемой внешней границей Backend.
    
7. Integration Layer является контролируемой границей взаимодействия с внешними системами.
    
8. PostgreSQL размещается во внутренней зоне, недоступной непосредственно из Internet.
    
9. Внешний защищённый трафик production осуществляется по HTTPS.
    
10. Серверные секреты не передаются Frontend.
    
11. Production-секреты управляются согласно ADR-029.
    
12. Резервное копирование выполняется согласно ADR-030.
    
13. Резервные копии должны быть отделены от основной рабочей среды.
    
14. Production должна иметь средства мониторинга и журналирования.
    
15. Логи не должны содержать секреты.
    
16. Долгие и фоновые операции могут выполняться асинхронно.
    
17. Production-архитектура должна допускать масштабирование компонентов.
    
18. Сетевые зоны должны иметь минимально необходимые разрешения доступа.
    
19. Доступ к внутренним ресурсам предоставляется по принципу минимальных привилегий.
    
20. Конкретные серверы, облачный провайдер, reverse proxy, контейнеризация, оркестрация и брокер сообщений определяются отдельными техническими решениями.
    
21. Конкретные значения SLA, RPO и RTO определяются отдельными требованиями.
    
22. Production-инфраструктура не должна изменять установленные границы бизнес-архитектуры SmEl.

Конкретные инфраструктурные технологии, поставщики, топология, контейнеризация, оркестрация, балансировка нагрузки, мониторинг, брокеры сообщений и параметры масштабирования определяются отдельными техническими решениями.
