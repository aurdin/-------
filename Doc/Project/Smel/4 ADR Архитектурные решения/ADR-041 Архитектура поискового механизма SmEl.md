# 1. Назначение

Документ определяет архитектуру поискового механизма интернет-магазина SmEl.

Цель решения — обеспечить быстрый и единообразный поиск товаров по каталожным и идентификационным данным с сохранением единого источника бизнес-истины на стороне Backend.

Поисковый механизм является специализированным read-oriented контуром и не заменяет основной каталог и бизнес-логику SmEl.

# 2. Область применения

Решение распространяется на:

- полнотекстовый поиск товаров;
    
- поиск по названию и локализованным данным;
    
- поиск по SKU;
    
- поиск по артикулу производителя;
    
- поиск по EAN/GTIN;
    
- поиск по характеристикам;
    
- поиск по бренду и серии;
    
- фильтрацию результатов;
    
- сортировку результатов;
    
- фасетную навигацию;
    
- подсказки и автодополнение;
    
- индексацию опубликованных данных каталога;
    
- обновление поискового индекса;
    
- использование поискового механизма через REST API.
    

Решение не определяет:

- структуру основной базы данных;
    
- бизнес-правила ценообразования;
    
- резервирование товара;
    
- оформление заказа;
    
- конкретный поисковый интерфейс Frontend;
    
- SEO-архитектуру как самостоятельную область;
    
- конкретную технологию поискового движка, если она не будет выбрана настоящим решением.
    

# 3. Основная часть

## 3.1. Архитектурная позиция поиска

Поиск является отдельным read-oriented контуром поверх данных каталога.

Основной источник бизнес-данных остается в PostgreSQL и доменных моделях SmEl.

Поисковый индекс является производным представлением данных и не является источником истины.

Архитектурная схема:

```
                 ┌─────────────────┐
                 │    Frontend     │
                 └────────┬────────┘
                          │ REST API
                          ▼
                 ┌─────────────────┐
                 │     Backend     │
                 │  Search Service │
                 └────────┬────────┘
                          │
                          ▼
                 ┌─────────────────┐
                 │ Search Index    │
                 │  Read Model     │
                 └─────────────────┘
                          ▲
                          │ Indexing
                          │
                 ┌─────────────────┐
                 │ Catalog / DB    │
                 │ Source of Truth │
                 └─────────────────┘
```

Frontend не обращается непосредственно к поисковому движку.

Все поисковые запросы проходят через Backend и его API.

## 3.2. Search Service

В Backend выделяется Search Service.

Search Service отвечает за:

- формирование поискового запроса;
    
- применение фильтров;
    
- сортировку;
    
- пагинацию;
    
- получение фасетов;
    
- обработку подсказок;
    
- преобразование результата поиска в API-модель;
    
- проверку доступности и опубликованности результатов.
    

Search Service не должен дублировать бизнес-правила каталога.

## 3.3. Индексируемые данные

В поисковый индекс могут включаться:

- идентификатор товара;
    
- SKU;
    
- артикул производителя;
    
- EAN/GTIN;
    
- локализованные названия;
    
- краткое и поисковое описание;
    
- бренд;
    
- серия;
    
- категория;
    
- группа;
    
- тип;
    
- конфигурация;
    
- исполнение;
    
- характеристики;
    
- поисковые признаки;
    
- признаки доступности;
    
- признаки публикации.
    

Коммерческие данные могут использоваться для поиска и фильтрации только в форме, необходимой для поискового сценария.

Поисковый индекс не должен становиться самостоятельным источником актуальной цены, скидки или остатка.

Актуальные критические коммерческие данные при необходимости подтверждаются Backend в соответствующем бизнес-контуре.

## 3.4. Локализация

Поиск поддерживает локализованные данные SmEl.

Основные языки:

- украинский;
    
- русский;
    
- английский.
    

Поисковый индекс должен хранить локализованные поисковые поля раздельно либо использовать эквивалентный механизм, позволяющий выполнять языково-зависимый поиск.

Frontend передает поисковый запрос и параметры поиска, но не выбирает внутреннее поле хранения локализованного названия.

Языковая обработка определяется Backend.

## 3.5. Виды поиска

Архитектура должна поддерживать следующие виды поиска:

### Полнотекстовый поиск

Поиск по названиям, описаниям и другим текстовым полям.

### Идентификационный поиск

Поиск по:

- SKU;
    
- артикулу;
    
- EAN/GTIN.
    

Для идентификаторов допускается более точное сопоставление, чем для обычного текста.

### Поиск по характеристикам

Поиск и фильтрация по значениям характеристик товара.

### Поиск по классификации

Поиск и фильтрация по:

- бренду;
    
- серии;
    
- категории;
    
- группе;
    
- типу;
    
- конфигурации;
    
- исполнению.
    

## 3.6. Фильтрация и фасеты

Search Service должен поддерживать фильтрацию результатов.

Фильтры могут включать:

- категорию;
    
- бренд;
    
- серию;
    
- характеристики;
    
- диапазоны числовых параметров;
    
- наличие;
    
- коммерческие признаки;
    
- другие параметры, определенные каталогом.
    

Для пользовательской навигации могут формироваться фасеты — агрегированные значения доступных фильтров и количество результатов по ним.

Фасеты являются производными данными поискового контура.

## 3.7. Сортировка

Поиск должен поддерживать сортировку результатов.

Возможные варианты:

- релевантность;
    
- название;
    
- цена;
    
- популярность;
    
- наличие;
    
- дата добавления или изменения;
    
- другие определенные бизнесом критерии.
    

Критерии сортировки, связанные с бизнес-данными, должны использовать актуальные данные или контролируемые производные признаки.

## 3.8. Пагинация

Результаты поиска выдаются постранично.

Search Service отвечает за:

- размер страницы;
    
- позицию или cursor;
    
- ограничения максимального размера;
    
- стабильность порядка результатов.
    

Frontend не должен самостоятельно получать весь набор результатов и выполнять пагинацию локально.

## 3.9. Подсказки и автодополнение

Механизм поиска может предоставлять:

- подсказки по названиям;
    
- подсказки по SKU и артикулам;
    
- подсказки по брендам;
    
- подсказки по сериям;
    
- наиболее релевантные поисковые варианты.
    

Подсказки также предоставляются через Backend API.

Поисковый движок не становится самостоятельным публичным API для Frontend.

# 4. Правила

## 4.1. Источник истины

PostgreSQL и доменные данные SmEl являются источником истины.

Поисковый индекс является производным read model.

Изменение данных через поисковый индекс запрещено.

## 4.2. Граница доступа

Frontend → REST API → Search Service → Search Index.

Прямой доступ Frontend к поисковому индексу запрещен.

Другие внешние системы также не должны обращаться к поисковому индексу в обход Backend без отдельного архитектурного решения.

## 4.3. Индексация

Индексация выполняется на основании данных каталога.

При изменении индексируемых данных соответствующий поисковый документ должен быть создан, обновлен или удален.

Индексация может выполняться:

- синхронно для небольших операций;
    
- асинхронно для массовых изменений;
    
- пакетно при первоначальном построении индекса.
    

Для массовой и фоновой индексации используется архитектура асинхронной обработки ADR-033.

## 4.4. Согласованность

Поисковый индекс допускает временную задержку относительно основной базы данных.

Такая eventual consistency допустима, поскольку индекс является производным представлением.

Критические бизнес-решения не должны приниматься только на основании потенциально устаревшего поискового индекса.

## 4.5. Удаление и публикация товаров

Товар, который:

- удален;
    
- снят с публикации;
    
- запрещен к отображению;
    
- больше не должен быть доступен пользователю,
    

не должен оставаться доступным через обычный пользовательский поиск после завершения соответствующего обновления индекса.

Backend дополнительно контролирует допустимость выдачи.

## 4.6. Актуальность коммерческих данных

Поисковый индекс может содержать производные признаки:

- наличие;
    
- диапазон цены;
    
- признак доступности;
    
- другие необходимые признаки.
    

Однако цена, скидка, акция и итоговая стоимость определяются согласно ADR-010 и ADR-034.

Поиск не заменяет Pricing Service.

Актуальные коммерческие условия при переходе к Cart или Checkout должны быть повторно рассчитаны и проверены Backend.

## 4.7. Актуальность остатков

Поисковая выдача может использовать признак наличия для навигации пользователя.

Однако фактическая доступность товара определяется централизованным контуром Stock/Reservation.

Search Service не выполняет резервирование и не гарантирует наличие товара для покупки.

## 4.8. Отказ поискового механизма

Поисковый индекс является производным контуром.

Его недоступность не должна приводить к потере основных бизнес-данных.

В зависимости от сценария Backend может:

- вернуть контролируемую ошибку поиска;
    
- использовать ограниченный fallback-механизм;
    
- временно использовать другой read-oriented источник.
    

Конкретная fallback-стратегия определяется при реализации.

## 4.9. Восстановление индекса

Индекс должен иметь возможность полного восстановления из основной базы данных.

Поэтому архитектура должна обеспечивать:

- воспроизводимую схему индекса;
    
- определенную структуру индексируемого документа;
    
- полную перестроенную индексацию;
    
- контроль версии структуры индекса.
    

Потеря поискового индекса не должна означать потерю каталога.

## 4.10. Идемпотентность

Операции индексации должны быть идемпотентными.

Повторное выполнение одной операции индексации не должно создавать дублирующие поисковые документы или неконтролируемые состояния.

Для асинхронной индексации применяются правила ADR-033.

## 4.11. Производительность

Поисковый контур должен быть отделен от транзакционных операций каталога настолько, чтобы интенсивный пользовательский поиск не создавал недопустимую нагрузку на основной бизнес-контур.

Конкретные количественные показатели производительности определяются после появления требований и нагрузочного профиля.

## 4.12. Технология поискового движка

Архитектура допускает использование специализированного поискового движка.

Возможными вариантами являются:

- PostgreSQL Full-Text Search;
    
- Elasticsearch;
    
- OpenSearch;
    
- другой совместимый поисковый механизм.
    

Выбор конкретной технологии выполняется на основании:

- объема каталога;
    
- требований к полнотекстовому поиску;
    
- количества фильтров и фасетов;
    
- требований к релевантности;
    
- нагрузки;
    
- сложности эксплуатации;
    
- требований к отказоустойчивости.
    

На архитектурном уровне SmEl не должен привязывать бизнес-логику к конкретному поисковому движку.

## 4.13. Изоляция технологии

Search Service является архитектурным адаптером между REST API и поисковым механизмом.

Замена поискового движка не должна требовать изменения Frontend API и основной бизнес-модели SmEl.

## 4.14. Безопасность

Поисковый механизм:

- не содержит секретов Frontend;
    
- не предоставляет прямой доступ пользователю к базе данных;
    
- не должен раскрывать внутренние технические поля;
    
- возвращает только разрешенные для публикации данные.
    

Все внешние запросы проходят через стандартные механизмы безопасности API.

# 6. Заключительные положения

Поисковый механизм SmEl является производным read-oriented контуром, предназначенным для быстрого поиска и навигации по каталогу.

Основная база данных и Backend сохраняют статус источника бизнес-истины.

Search Service изолирует Frontend и бизнес-логику от конкретной технологии поискового индекса.

Поисковый индекс может обновляться асинхронно и допускает временную рассогласованность с основной базой данных.

Потеря или перестроение поискового индекса не должно приводить к потере бизнес-данных.

Конкретная технология поискового движка, параметры релевантности, количественные показатели производительности и fallback-механизм могут быть уточнены на этапе реализации.
