# 1. Назначение

Документ определяет архитектурную политику SmEl в отношении:

- RPO — допустимой потери данных;
    
- RTO — целевого времени восстановления;
    
- приоритетов восстановления;
    
- различий между критическими и производными данными;
    
- контроля достижения заданных показателей.
    

Цель решения — определить целевые параметры восстановления, которые используются при проектировании резервного копирования, инфраструктуры и процедур аварийного восстановления.

# 2. Область применения

Решение распространяется на:

- Production SmEl;
    
- PostgreSQL;
    
- критические бизнес-данные;
    
- Media;
    
- Backend;
    
- поисковый контур;
    
- интеграционные состояния;
    
- процедуры восстановления;
    
- backup/recovery;
    
- контроль RPO/RTO.
    

Решение не определяет:

- конкретный backup-инструмент;
    
- конкретное облако или инфраструктурного провайдера;
    
- конкретную технологию PostgreSQL replication;
    
- конкретный механизм мониторинга;
    
- конкретный disaster recovery site.
    

# 3. Основная часть

## 3.1. Определение RPO

**RPO (Recovery Point Objective)** — максимально допустимый объем потери последних изменений данных после аварии.

Для SmEl RPO определяется не только технической возможностью резервного копирования, но и критичностью соответствующего бизнес-данного.

## 3.2. Определение RTO

**RTO (Recovery Time Objective)** — целевое максимальное время, необходимое для восстановления системы до состояния, позволяющего возобновить критические бизнес-операции.

RTO включает:

- обнаружение проблемы;
    
- выбор точки восстановления;
    
- восстановление данных;
    
- запуск компонентов;
    
- проверку;
    
- восстановление необходимых интеграций;
    
- возобновление критических операций.
    

## 3.3. Целевые значения

Для Production SmEl устанавливаются следующие целевые значения:

|Контур|RPO|RTO|Приоритет|
|---|---|---|---|
|PostgreSQL / критические бизнес-данные|≤ 1 часа|≤ 4 часов|Критический|
|Media|≤ 24 часов|≤ 8 часов|Высокий|
|Search Index|0 как самостоятельное требование|≤ 8 часов|Средний|
|Cache|Не применяется|≤ 8 часов|Низкий|
|Task Queue / временные задачи|≤ 1 часа*|≤ 8 часов|Средний|
|Интеграционные производные данные|≤ 1 часа*|≤ 8 часов|Средний|

* Для конкретного интеграционного контура значение может быть уточнено исходя из характера операции и требований внешней системы.

## 3.4. Приоритет PostgreSQL

PostgreSQL имеет наивысший приоритет восстановления, поскольку содержит основные бизнес-данные SmEl.

В первую очередь должны быть восстановлены:

- Product;
    
- Catalog;
    
- Price;
    
- Discount;
    
- Promotion;
    
- Stock;
    
- Reservation;
    
- Customer;
    
- Cart;
    
- Order;
    
- Order Item;
    
- Payment;
    
- Delivery.
    

## 3.5. Приоритет Media

Media имеет отдельный RPO/RTO, поскольку ее отсутствие не должно препятствовать восстановлению основной базы данных.

При восстановлении:

1. восстанавливается PostgreSQL;
    
2. запускается Backend;
    
3. восстанавливается доступ к Media;
    
4. проверяется соответствие Media бизнес-сущностям.
    

## 3.6. Приоритет производных данных

Производные данные не должны ухудшать RTO основной бизнес-системы.

Search Index может быть перестроен из PostgreSQL согласно ADR-041.

Cache может быть создан заново.

Поэтому потеря таких данных не считается потерей бизнес-истины.

## 3.7. Влияние RPO на резервное копирование

Для достижения RPO PostgreSQL ≤ 1 часа архитектура резервного копирования должна обеспечивать возможность восстановления с потерей не более одного часа изменений в штатном сценарии.

Предпочтительно использовать механизм, позволяющий получить более точную точку восстановления, чем минимально установленное значение.

## 3.8. Влияние RTO на архитектуру

Для достижения RTO ≤ 4 часов необходимо заранее подготовить:

- процедуру восстановления;
    
- доступ к резервным копиям;
    
- необходимые конфигурации;
    
- документацию;
    
- доступы;
    
- процедуру проверки;
    
- процедуру восстановления интеграций.
    

RTO не может быть обеспечено исключительно наличием backup-файла.

## 3.9. Приоритет восстановления

При аварии применяется следующий приоритет:

```
1. PostgreSQL
      │
      ▼
2. Backend
      │
      ▼
3. Critical Business Operations
      │
      ▼
4. External Integrations
      │
      ▼
5. Media
      │
      ▼
6. Search Index
      │
      ▼
7. Cache / Non-critical Derived Data
```

Фактическая последовательность может изменяться в зависимости от характера аварии.

## 3.10. Ограничение RTO

RTO является целевым показателем, а не гарантией при любых обстоятельствах.

Катастрофические сценарии, включая полную потерю инфраструктуры или недоступность внешних систем, могут потребовать отдельного disaster recovery плана.

Такие сценарии не детализируются настоящим ADR.

## 3.11. Внешние системы

RPO/RTO SmEl не означает, что внешние системы автоматически восстанавливаются одновременно с SmEl.

После восстановления:

- Payment сверяется с платежным провайдером;
    
- Delivery сверяется с провайдером доставки;
    
- Stock сверяется с ERP/WMS.
    

Состояние внешних операций определяется согласно соответствующим ADR.

## 3.12. Финансовые операции

Финансовая целостность имеет приоритет над скоростью восстановления.

При неоднозначном состоянии Payment:

```
Restore
   │
   ▼
Detect Ambiguous Payment
   │
   ▼
Reconcile Provider
   │
   ▼
Determine Actual State
   │
   ▼
Resume Payment Operations
```

Нельзя ускорять восстановление путем повторного запуска неизвестной финансовой операции.

## 3.13. Резервирование товара

После восстановления Reservation должна быть проверена совместно с актуальным Stock.

При необходимости выполняется сверка с ERP/WMS согласно ADR-042.

Это предотвращает продолжение продаж на основании устаревшего состояния остатков.

# 4. Правила

## 4.1. Production является основным объектом RPO/RTO

Целевые показатели RPO/RTO применяются прежде всего к Production.

Dev/Test окружения не обязаны соответствовать Production RPO/RTO.

## 4.2. RPO не распространяется одинаково на все данные

Критические бизнес-данные требуют более строгого RPO, чем производные данные.

## 4.3. RTO не требует одновременного восстановления всех компонентов

Критические бизнес-операции должны восстанавливаться раньше второстепенных функций.

## 4.4. Backup должен соответствовать RPO

Политика резервного копирования должна обеспечивать достижение установленного RPO.

Если фактический backup-процесс не способен обеспечить RPO ≤ 1 часа, архитектура считается несоответствующей настоящему ADR.

## 4.5. Recovery должен соответствовать RTO

Процедура восстановления должна регулярно проверяться.

Если тестовое восстановление превышает установленный RTO, причина должна быть выявлена и устранена либо целевой показатель пересмотрен отдельным архитектурным решением.

## 4.6. Тестирование

RPO/RTO должны проверяться на практике.

Необходимо периодически выполнять:

- тест восстановления PostgreSQL;
    
- тест восстановления Media;
    
- запуск Backend после восстановления;
    
- проверку критических бизнес-операций;
    
- проверку Search Index reconstruction;
    
- проверку интеграционной сверки.
    

## 4.7. Измерение фактических значений

Для каждого теста восстановления рекомендуется фиксировать:

- время начала;
    
- время обнаружения;
    
- выбранную точку восстановления;
    
- фактическую потерю данных;
    
- время восстановления PostgreSQL;
    
- время запуска Backend;
    
- время восстановления критических операций;
    
- время полного восстановления;
    
- ошибки;
    
- результаты проверки.
    

## 4.8. Нарушение RPO

Если фактическая потеря данных превышает установленный RPO, это считается нарушением политики восстановления.

Причина должна быть проанализирована.

## 4.9. Нарушение RTO

Если фактическое время восстановления превышает установленный RTO, это также считается нарушением политики.

Необходимо определить:

- техническую причину;
    
- организационную причину;
    
- недостаток автоматизации;
    
- недостаток резервных ресурсов;
    
- ошибку процедуры.
    

## 4.10. Мониторинг

Production должен предоставлять информацию, необходимую для оценки:

- времени последнего успешного backup;
    
- возраста последней точки восстановления;
    
- состояния backup;
    
- состояния восстановления;
    
- результатов тестов.
    

## 4.11. Изменение RPO/RTO

RPO/RTO могут быть изменены только после анализа:

- бизнес-критичности;
    
- стоимости инфраструктуры;
    
- стоимости потери данных;
    
- фактических результатов восстановления;
    
- требований REQ;
    
- изменений архитектуры.
    

Изменение оформляется отдельным изменением ADR.

# 6. Заключительные положения

Для Production SmEl устанавливаются следующие целевые показатели:

- **RPO критических бизнес-данных PostgreSQL — не более 1 часа.**
    
- **RTO критических бизнес-операций — не более 4 часов.**
    
- **RPO Media — не более 24 часов.**
    
- **RTO Media — не более 8 часов.**
    
- Производные данные могут восстанавливаться отдельно от основной бизнес-системы.
    

Основным приоритетом является восстановление PostgreSQL и критических бизнес-операций.

Восстановление внешних операций выполняется посредством сверки с соответствующими внешними системами.

RPO/RTO должны подтверждаться регулярным тестированием, а не только наличием формально настроенного backup.
