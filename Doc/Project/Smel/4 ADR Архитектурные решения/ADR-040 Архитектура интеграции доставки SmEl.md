# 1. Назначение

ADR-040 определяет архитектуру интеграции SmEl с внешними провайдерами доставки.

Документ детализирует ADR-026 в части:

- выбора способа доставки;
    
- расчёта стоимости;
    
- создания доставки;
    
- передачи данных провайдеру;
    
- получения идентификатора отправления;
    
- tracking;
    
- синхронизации статусов;
    
- обработки внешних событий;
    
- ошибок и повторных операций.
    

Цель решения — обеспечить контролируемое взаимодействие между внутренним объектом Delivery и внешними службами доставки.

# 2. Область применения

Решение распространяется на:

- Order;
    
- Delivery;
    
- Delivery Method;
    
- Delivery Address;
    
- Delivery Service;
    
- Delivery Integration;
    
- внешний Delivery Provider;
    
- REST API;
    
- webhook/callback;
    
- tracking;
    
- Service Layer;
    
- Frontend.
    

ADR-040 не определяет:

- конкретного провайдера доставки;
    
- конкретный API или протокол;
    
- конкретные тарифы;
    
- перечень пунктов выдачи;
    
- конкретную транспортную компанию;
    
- конкретную инфраструктуру Integration Layer.
    

# 3. Основная часть

## 3.1. Архитектурная граница

Внешний провайдер доставки является отдельной системой.

Он не получает прямого доступа к PostgreSQL SmEl.

Основная архитектура:

```
Frontend
   │
   ▼
REST API
   │
   ▼
Service Layer
   │
   ▼
Delivery Service
   │
   ▼
Delivery Integration
   │
   ▼
External Delivery Provider
```

Обратные события:

```
External Delivery Provider
          │
          ▼
     Webhook / Callback
          │
          ▼
      REST API
          │
          ▼
  Delivery Integration
          │
          ▼
    Delivery Service
          │
          ▼
        Delivery
```

## 3.2. Delivery и Delivery Method

Delivery и Delivery Method являются различными сущностями.

Delivery Method описывает способ доставки, например:

- курьерская доставка;
    
- доставка в пункт выдачи;
    
- доставка перевозчиком;
    
- самовывоз.
    

Delivery представляет конкретную операцию доставки определённого Order.

Один Delivery Method может использоваться множеством Delivery.

## 3.3. Выбор способа доставки

На этапе Checkout Backend определяет доступные Delivery Method.

При выборе учитываются:

- адрес;
    
- регион;
    
- состав заказа;
    
- масса и габариты, если применимо;
    
- ограничения метода;
    
- доступность провайдера;
    
- стоимость;
    
- другие коммерческие условия.
    

Frontend отображает доступные варианты, но окончательная допустимость выбора определяется Backend.

## 3.4. Адрес доставки

Delivery Address является отдельными данными доставки.

После создания Order адрес, относящийся к заказу, должен быть зафиксирован.

Изменение текущего адреса клиента не должно изменять исторический адрес уже оформленного заказа.

Провайдер получает только необходимые данные адресата и доставки.

## 3.5. Расчёт стоимости доставки

Стоимость доставки является частью коммерческих условий заказа.

Возможная схема:

```
Order Context
     │
     ▼
Delivery Method
     │
     ▼
Delivery Calculation
     │
     ├── Address
     ├── Weight / Dimensions
     ├── Region
     └── Provider Rules
     │
     ▼
Delivery Cost
     │
     ▼
Checkout / Order
```

Расчёт может выполняться:

- SmEl;
    
- внешним провайдером;
    
- комбинированно.
    

Однако окончательная стоимость, включённая в Order, должна быть подтверждена Backend.

## 3.6. Фиксация стоимости

После оформления Order стоимость доставки становится частью зафиксированных условий заказа.

Изменение текущего тарифа провайдера не должно изменять уже созданный Order.

Для нового расчёта используется актуальный тариф.

Таким образом:

```
Current Provider Tariff
          │
          ▼
      Calculation
          │
          ▼
    Checkout Result
          │
          ▼
         Order
          │
          ▼
   Frozen Delivery Cost
```

## 3.7. Создание Delivery

После создания Order Backend может создать Delivery.

Общий процесс:

```
Order
  │
  ▼
Delivery Service
  │
  ▼
Create Delivery
  │
  ▼
Delivery Integration
  │
  ▼
Provider
  │
  ▼
External Shipment ID
```

Внутренний Delivery и внешняя отправка являются связанными, но различными объектами.

## 3.8. Идентификаторы

Delivery должен иметь внутренний идентификатор.

Внешний провайдер может предоставить:

- Shipment ID;
    
- Tracking Number;
    
- Label ID;
    
- другие идентификаторы.
    

Внешний идентификатор не заменяет внутренний идентификатор SmEl.

Связь:

```
SmEl Delivery ID
       │
       └── External Shipment ID
```

## 3.9. Передача данных провайдеру

SmEl передаёт провайдеру только необходимые данные.

В зависимости от провайдера это могут быть:

- сведения об отправителе;
    
- сведения о получателе;
    
- адрес;
    
- контактные данные;
    
- состав отправления;
    
- масса;
    
- размеры;
    
- стоимость;
    
- выбранный способ доставки;
    
- идентификаторы заказа.
    

Избыточные данные не должны передаваться без необходимости.

## 3.10. Жизненный цикл Delivery

Базовый жизненный цикл:

```
Created
   │
   ▼
Planned
   │
   ▼
Prepared
   │
   ▼
Handed Over
   │
   ▼
In Transit
   │
   ▼
Delivered
```

Дополнительные состояния могут включать:

- Cancelled;
    
- Returned;
    
- Failed;
    
- Lost;
    
- Exception.
    

Окончательный набор состояний может быть расширен при реализации.

## 3.11. Tracking

Tracking предоставляет актуальную информацию о движении отправления.

Tracking может получать данные:

- по запросу Backend;
    
- через webhook;
    
- через периодическую синхронизацию.
    

Архитектура:

```
Provider
   │
   ├──► Tracking API
   │
   └──► Webhook
          │
          ▼
   Delivery Integration
          │
          ▼
    Delivery Service
          │
          ▼
       Delivery
```

Frontend получает tracking-информацию только через Backend.

## 3.12. Webhook

Webhook провайдера доставки рассматривается как внешний недоверенный вход.

Перед изменением Delivery Backend должен проверить:

- источник события;
    
- подпись или механизм аутентификации;
    
- идентификатор события;
    
- внешний Shipment ID;
    
- соответствие внутреннему Delivery;
    
- допустимость перехода состояния;
    
- повторность события.
    

Webhook не должен непосредственно изменять PostgreSQL.

## 3.13. Идемпотентность

Повторное получение одного события доставки не должно:

- создавать новую Delivery;
    
- повторно изменять состояние;
    
- повторно выполнять бизнес-операцию;
    
- приводить к некорректному переходу статуса.
    

Для внешних событий используется идентификатор события или эквивалентный механизм дедупликации.

Повторные операции создания отправления также должны быть защищены от неконтролируемого дублирования.

## 3.14. Синхронизация статусов

Статус внешней доставки не должен без проверки напрямую заменять внутреннее состояние Delivery.

Backend сопоставляет внешний статус с внутренней моделью.

```
External Status
      │
      ▼
Mapping
      │
      ▼
Validation
      │
      ▼
Delivery Service
      │
      ▼
Internal Delivery Status
```

Таким образом, различия между моделями статусов разных провайдеров скрываются внутри Integration Layer.

## 3.15. Источник истины

Внешний провайдер является источником фактического состояния своей транспортной операции.

SmEl является источником истины для:

- внутреннего Delivery;
    
- связи Delivery с Order;
    
- выбранного Delivery Method;
    
- зафиксированной стоимости доставки;
    
- внутренней истории состояния.
    

Внешний статус используется SmEl после проверки и преобразования.

## 3.16. Ошибки интеграции

Ошибки разделяются на:

- ошибки выбора метода;
    
- ошибки расчёта;
    
- ошибки создания отправления;
    
- ошибки сети;
    
- ошибки провайдера;
    
- ошибки webhook;
    
- ошибки сопоставления идентификаторов;
    
- некорректные переходы статусов;
    
- внутренние технические ошибки.
    

Временные ошибки могут приводить к повторной попытке.

Повторные попытки должны быть ограничены.

Неоднозначный результат создания отправления требует проверки состояния у провайдера перед повторным созданием.

## 3.17. Асинхронная обработка

Интеграционные операции могут выполняться асинхронно согласно ADR-033.

К асинхронным операциям относятся:

- получение обновлений tracking;
    
- синхронизация статусов;
    
- создание отправления при длительном ответе;
    
- периодическая проверка состояния;
    
- массовая синхронизация.
    

Worker не должен содержать самостоятельную копию бизнес-логики Delivery.

## 3.18. Отмена и возврат

Отмена Delivery и возврат отправления являются отдельными операциями.

Они могут приводить к изменению состояния Delivery, но не должны автоматически удалять Order.

Физический возврат товара и финансовый Refund являются различными процессами.

Финансовая часть определяется ADR-039.

## 3.19. Безопасность

Интеграция должна:

- использовать защищённый канал;
    
- хранить credentials вне исходного кода;
    
- не передавать секреты Frontend;
    
- проверять webhook;
    
- ограничивать права Integration Layer;
    
- не записывать секреты в логи;
    
- применять ADR-029.
    

Персональные данные получателя должны передаваться провайдеру только в объёме, необходимом для выполнения доставки.

## 3.20. Аудит

Для Delivery должны сохраняться:

- внутренний идентификатор;
    
- Order;
    
- Delivery Method;
    
- адрес доставки;
    
- стоимость;
    
- внешний Shipment ID;
    
- Tracking Number;
    
- состояния;
    
- время изменений;
    
- результаты интеграционных операций;
    
- ошибки;
    
- внешние события, необходимые для аудита.
    

История не должна теряться при изменении текущего статуса.

# 4. Правила

1. Delivery является отдельной сущностью.
    
2. Delivery Method и Delivery являются различными сущностями.
    
3. Внешний Delivery Provider является отдельной системой.
    
4. Провайдер не имеет прямого доступа к PostgreSQL SmEl.
    
5. Интеграция выполняется через Integration Layer.
    
6. Бизнес-операции Delivery выполняются через Service Layer.
    
7. Frontend не взаимодействует с провайдером напрямую для изменения Delivery.
    
8. Delivery Address является отдельными данными доставки.
    
9. Адрес оформленного заказа должен быть зафиксирован.
    
10. Стоимость доставки подтверждается Backend.
    
11. Зафиксированная стоимость доставки не изменяется вследствие изменения текущего тарифа провайдера.
    
12. Delivery имеет собственный жизненный цикл.
    
13. Внешний Shipment ID не заменяет внутренний Delivery ID.
    
14. Tracking доступен через Backend.
    
15. Webhook является недоверенным внешним входом.
    
16. Webhook проходит проверку перед изменением Delivery.
    
17. Внешние события должны обрабатываться идемпотентно.
    
18. Внешний статус проходит mapping и validation.
    
19. Неоднозначный результат интеграционной операции проверяется перед повторением.
    
20. Асинхронные операции подчиняются ADR-033.
    
21. Секреты интеграции управляются согласно ADR-029.
    
22. Order не удаляется при отмене или возврате Delivery.
    
23. Финансовый Refund является отдельной операцией согласно ADR-039.
    
24. История Delivery должна сохраняться для аудита.

# 6. Заключительные положения

ADR-040 определяет архитектурную границу между SmEl и внешними службами доставки.

Backend является центральной точкой управления внутренним Delivery. Внешний провайдер предоставляет данные транспортной операции, которые проходят проверку и преобразование перед использованием внутри SmEl.

Стоимость доставки фиксируется в заказе и не изменяется вследствие последующего изменения тарифов провайдера.

Интеграция должна поддерживать tracking, webhook, идемпотентность и контролируемую обработку ошибок.

Конкретный провайдер, протокол, тарифные правила и детальные сценарии отмены/возврата определяются на последующих этапах.
