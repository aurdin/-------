# 1. Назначение

Документ определяет архитектуру резервного копирования и восстановления данных SmEl.

Цель решения — обеспечить возможность восстановления критических бизнес-данных после отказов, повреждения данных, ошибочных операций или потери отдельных компонентов системы.

Архитектура резервного копирования должна обеспечивать восстановление не только PostgreSQL, но и других данных, необходимых для целостной работы системы.

# 2. Область применения

Решение распространяется на:

- резервное копирование PostgreSQL;
    
- восстановление PostgreSQL;
    
- резервирование Media;
    
- конфигурацию, необходимую для восстановления;
    
- хранение резервных копий;
    
- проверку резервных копий;
    
- тестовое восстановление;
    
- защиту резервных копий;
    
- удаление и ротацию устаревших копий;
    
- восстановление после отказа;
    
- восстановление согласованного состояния системы.
    

Решение не определяет:

- конкретный backup-инструмент;
    
- конкретное облачное или физическое хранилище;
    
- точную периодичность создания копий;
    
- конкретные значения RPO/RTO;
    
- физическую инфраструктуру Production;
    
- стратегию disaster recovery отдельного дата-центра.
    

# 3. Основная часть

## 3.1. Критические данные

Основным источником бизнес-данных SmEl является PostgreSQL.

К критическим данным относятся:

- каталог;
    
- характеристики;
    
- цены и коммерческие условия;
    
- остатки;
    
- клиенты;
    
- корзины;
    
- заказы;
    
- платежные данные и состояния платежей;
    
- доставки;
    
- резервы;
    
- настройки, необходимые для восстановления бизнес-состояния.
    

PostgreSQL является основным объектом резервного копирования.

## 3.2. Архитектура резервного копирования

Общая схема:

```
                ┌─────────────────┐
                │   PostgreSQL    │
                │ Business Data   │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ Backup Process  │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ Backup Storage  │
                └────────┬────────┘
                         │
                    Protected
                     Storage
```

Backup Process не является частью бизнес-логики приложения.

Он должен выполняться независимо от Frontend и обычных API-запросов.

## 3.3. PostgreSQL

Для PostgreSQL должна обеспечиваться возможность:

- создания резервной копии;
    
- восстановления полной базы;
    
- восстановления на определенный момент времени, если выбранная технология это поддерживает;
    
- проверки целостности резервной копии;
    
- хранения истории операций резервирования.
    

Конкретный механизм Point-in-Time Recovery определяется при реализации.

## 3.4. Полные резервные копии

Полная резервная копия должна содержать данные, необходимые для восстановления PostgreSQL в согласованное состояние.

Полные копии являются основой долгосрочного восстановления.

Их количество и период хранения определяются политикой резервного копирования.

## 3.5. Инкрементальное восстановление

Архитектура допускает использование:

- WAL;
    
- incremental backup;
    
- differential backup;
    
- других механизмов,
    

если они необходимы для достижения установленного RPO.

Конкретная технология не фиксируется настоящим ADR.

## 3.6. Media

Медиафайлы не должны считаться восстановленными только потому, что восстановлена PostgreSQL.

Архитектура резервного копирования Media является отдельным контуром.

```
PostgreSQL Backup ───────► DB Recovery

Media Storage Backup ────► Media Recovery
```

Для Media должна обеспечиваться возможность восстановления файлов, связанных с актуальными бизнес-сущностями.

## 3.7. Производные данные

Производные данные не обязательно должны резервироваться как основной источник.

К таким данным относятся:

- поисковый индекс;
    
- кэш;
    
- временные файлы;
    
- очереди задач;
    
- временные результаты обработки.
    

Если производный компонент может быть воспроизведен из источника истины, предпочтительно восстановить его путем реконструкции.

Например:

```
PostgreSQL
    │
    ▼
Rebuild
    │
    ▼
Search Index
```

Это соответствует ADR-041.

## 3.8. Конфигурация и секреты

Конфигурация, необходимая для восстановления системы, должна быть документирована и воспроизводима.

Секреты не должны включаться в обычные резервные копии в открытом виде.

Хранение и защита секретов выполняются согласно ADR-029.

Если для восстановления необходимы секреты, должна существовать отдельная защищенная процедура их получения.

## 3.9. Хранение резервных копий

Резервные копии должны храниться отдельно от основной рабочей базы.

Минимальный принцип:

```
Production PostgreSQL
        │
        ▼
   Backup Storage
        │
        ├── Primary Backup Location
        │
        └── Independent / Off-site Copy
```

Потеря Production-инфраструктуры не должна автоматически означать потерю всех резервных копий.

## 3.10. Защита резервных копий

Резервные копии должны быть защищены от:

- несанкционированного доступа;
    
- случайного удаления;
    
- повреждения;
    
- подмены;
    
- распространения содержащихся в них персональных данных.
    

Должны применяться:

- контроль доступа;
    
- шифрование при необходимости;
    
- аудит доступа;
    
- разграничение ролей;
    
- защищенное удаление.
    

## 3.11. Ротация

Резервные копии должны иметь управляемый жизненный цикл.

Концептуально:

```
Created
   │
   ▼
Verified
   │
   ▼
Retained
   │
   ▼
Expired
   │
   ▼
Deleted
```

Удаление резервной копии должно учитывать минимальный период хранения и требования восстановления.

## 3.12. Проверка резервных копий

Факт успешного создания файла резервной копии не означает, что резервная копия пригодна для восстановления.

Необходимо контролировать:

- успешность создания;
    
- целостность;
    
- размер;
    
- доступность;
    
- соответствие ожидаемой структуре;
    
- возможность восстановления.
    

Ошибки резервного копирования должны обнаруживаться автоматически либо посредством регулярного контроля.

## 3.13. Тестовое восстановление

Восстановление должно регулярно проверяться на отдельном окружении.

Тестовое восстановление должно подтверждать:

- возможность прочитать backup;
    
- возможность восстановить PostgreSQL;
    
- целостность основных бизнес-данных;
    
- возможность запуска Backend;
    
- возможность доступа к восстановленной базе;
    
- восстановление необходимых Media;
    
- возможность реконструкции производных данных.
    

Результат тестового восстановления должен фиксироваться.

## 3.14. Согласованность восстановления

Восстановление должно стремиться к согласованному состоянию бизнес-системы.

Нельзя рассматривать PostgreSQL, Media, Payment, Delivery и внешние системы как автоматически восстановленные в одном состоянии только потому, что восстановлена база.

Особое внимание требуется уделять внешним операциям:

- платежам;
    
- возвратам;
    
- доставкам;
    
- интеграционным событиям.
    

После восстановления необходимо определить состояние внешних операций через соответствующие Integration Layer и внешние системы.

## 3.15. Платежи после восстановления

После восстановления SmEl не должен автоматически повторять финансовую операцию только потому, что локальное состояние выглядит незавершенным.

Если состояние Payment неоднозначно, оно должно быть сверено с внешним платежным провайдером согласно ADR-038 и ADR-039.

Это особенно важно для предотвращения повторного списания или повторного возврата.

## 3.16. Доставки после восстановления

Состояние Delivery после восстановления при необходимости должно быть сверено с внешним провайдером доставки согласно ADR-040.

Восстановление базы не должно автоматически создавать повторную отправку.

## 3.17. Резервирование

Reservation восстанавливается из PostgreSQL как часть внутреннего бизнес-состояния.

После восстановления необходимо учитывать актуальность физического Stock.

При необходимости состояние остатков сверяется с ERP/WMS согласно ADR-042.

## 3.18. Аварийное восстановление

При необходимости восстановления применяется последовательность:

```
Detect Incident
      │
      ▼
Protect Current State
      │
      ▼
Select Recovery Point
      │
      ▼
Restore PostgreSQL
      │
      ▼
Restore Media
      │
      ▼
Start Backend
      │
      ▼
Rebuild Derived Data
      │
      ▼
Reconcile External Systems
      │
      ▼
Validate Business State
      │
      ▼
Resume Operations
```

Конкретные шаги и порядок могут зависеть от типа аварии.

# 4. Правила

## 4.1. Backend не управляет резервным копированием через обычный бизнес API

Backup является инфраструктурной операцией.

Frontend и обычные пользователи не должны иметь доступа к операциям резервного копирования или восстановления.

## 4.2. Резервные копии не являются источником истины

Backup — это копия состояния системы.

Источником бизнес-истины после восстановления становится восстановленная PostgreSQL и соответствующие внешние источники для тех данных, которые принадлежат внешним системам.

## 4.3. Изоляция резервных копий

Резервные копии должны быть логически и, по возможности, физически отделены от Production.

Компрометация основной среды не должна автоматически уничтожать все резервные копии.

## 4.4. Минимально необходимые права

Процессы резервирования должны использовать минимально необходимые права.

Доступ к восстановлению должен быть ограничен отдельными административными ролями.

## 4.5. Защита персональных данных

Резервные копии могут содержать персональные и коммерчески чувствительные данные.

К ним применяются те же требования защиты, что и к соответствующим данным Production.

## 4.6. Нельзя считать backup успешным без проверки

Успешным считается только резервирование, результат которого прошел предусмотренную проверку.

## 4.7. Нельзя считать систему восстановленной только после запуска приложения

Восстановление считается завершенным только после проверки критических бизнес-контуров.

Минимально проверяются:

- PostgreSQL;
    
- Backend;
    
- каталог;
    
- Stock;
    
- Cart;
    
- Order;
    
- Payment;
    
- Delivery;
    
- необходимые интеграции;
    
- Media;
    
- производные read-модели.
    

## 4.8. Восстановление производных данных

Производные данные должны по возможности восстанавливаться путем повторного построения.

Это относится, в частности, к Search Index согласно ADR-041.

## 4.9. Идемпотентность recovery-операций

Повторное выполнение операций восстановления и последующей синхронизации не должно приводить к:

- повторному платежу;
    
- повторному возврату;
    
- повторному созданию доставки;
    
- повторному резервированию;
    
- дублированию интеграционных операций.
    

Для этого применяются правила соответствующих ADR.

## 4.10. Мониторинг

Состояние резервного копирования должно контролироваться.

Минимально отслеживаются:

- время последнего успешного backup;
    
- результат последней операции;
    
- наличие доступной копии;
    
- ошибки;
    
- состояние хранилища;
    
- результаты тестового восстановления.

# 6. Заключительные положения

Резервное копирование SmEl строится вокруг PostgreSQL как основного хранилища бизнес-данных.

Media резервируются отдельным контуром.

Производные данные, такие как поисковый индекс и кэш, должны по возможности восстанавливаться путем реконструкции.

Резервные копии должны быть защищены, изолированы от Production и регулярно проверяться посредством тестового восстановления.

После аварийного восстановления внешние финансовые и логистические операции должны быть сверены с соответствующими внешними системами до продолжения связанных операций.

Количественные значения:

- RPO;
    
- RTO;
    
- периодичность backup;
    
- сроки хранения;
    
- количество копий;
    
- допустимое время восстановления,
    

не фиксируются настоящим ADR и определяются в **ADR-044 «Архитектура RPO/RTO SmEl»**.
