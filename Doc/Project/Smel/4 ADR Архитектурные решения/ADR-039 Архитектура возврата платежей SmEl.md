# 1. Назначение

ADR-039 определяет архитектуру возврата денежных средств в SmEl.

Документ детализирует ADR-025 и ADR-038 в части:

- инициирования возврата;
    
- связи возврата с исходным платежом;
    
- частичного и полного возврата;
    
- взаимодействия с платёжным провайдером;
    
- получения результата возврата;
    
- идемпотентности;
    
- истории финансовых операций;
    
- обработки ошибок и неоднозначных состояний.
    

Цель решения — обеспечить контролируемый возврат денежных средств без изменения или потери истории исходных платёжных операций.

# 2. Область применения

Решение распространяется на:

- Order;
    
- Payment;
    
- Payment Attempt;
    
- Refund;
    
- Refund Attempt;
    
- Payment Service;
    
- Payment Integration;
    
- внешний платёжный провайдер;
    
- REST API;
    
- Service Layer;
    
- административные и клиентские сценарии возврата.
    

ADR-039 не определяет:

- конкретного платёжного провайдера;
    
- конкретный платёжный протокол;
    
- конкретные правила возврата товара;
    
- гарантийные процессы;
    
- бухгалтерский или налоговый учёт;
    
- конкретный интерфейс администратора.
    

# 3. Основная часть

## 3.1. Возврат как отдельная операция

Refund является самостоятельной финансовой операцией.

Он не должен изменять или удалять исходный Payment.

Архитектура:

```
Order
  │
  ▼
Payment
  │
  ├──► Payment Attempt
  │
  └──► Refund
          │
          ▼
      Refund Attempt
          │
          ▼
   Payment Provider
```

История исходного платежа сохраняется независимо от результата возврата.

## 3.2. Полный и частичный возврат

Архитектура должна поддерживать:

- полный возврат;
    
- частичный возврат.
    

Полный возврат возвращает всю допустимую сумму платежа.

Частичный возврат возвращает только определённую сумму.

Суммарная сумма успешно выполненных возвратов не должна превышать сумму, доступную для возврата по соответствующей платёжной операции.

## 3.3. Связь Refund с Payment

Каждый Refund должен однозначно ссылаться на Payment.

При необходимости Refund также связывается с конкретным Payment Attempt.

```
Payment
   │
   ├── Attempt 1
   ├── Attempt 2
   │
   └── Refund
         │
         └── Refund Attempt
```

Refund не создаётся независимо от исходного платежа.

## 3.4. Инициирование возврата

Возврат инициируется через Backend.

Общий процесс:

```
Authorized User / Business Process
             │
             ▼
        REST API
             │
             ▼
       Service Layer
             │
             ▼
       Payment Service
             │
             ▼
          Refund
             │
             ▼
    Payment Integration
             │
             ▼
     Payment Provider
```

Frontend не должен непосредственно обращаться к платёжному провайдеру для выполнения возврата.

## 3.5. Проверки перед возвратом

Перед созданием Refund Backend должен проверить:

- существование Order;
    
- существование Payment;
    
- успешность исходной платёжной операции;
    
- доступную для возврата сумму;
    
- допустимость возврата;
    
- валюту;
    
- отсутствие превышения ранее возвращённой суммы;
    
- полномочия инициатора;
    
- возможность выполнения операции через платёжного провайдера.
    

Бизнес-правила, определяющие право клиента на возврат, могут зависеть от отдельного процесса возврата товара и не фиксируются полностью ADR-039.

## 3.6. Сумма возврата

Сумма Refund фиксируется при создании операции.

Она не должна рассчитываться на основании текущей цены каталога.

Для частичного возврата Backend использует установленную сумму возврата.

Например:

```
Payment = 1000

Refund 1 = 300
Refund 2 = 200

Successfully refunded = 500
Remaining refundable = 500
```

Повторный возврат сверх допустимой суммы запрещён.

## 3.7. Жизненный цикл Refund

Базовый жизненный цикл:

```
Created
   │
   ▼
Pending
   │
   ├──► Succeeded
   │
   ├──► Failed
   │
   └──► Cancelled
```

Конкретный набор состояний может быть расширен при реализации.

Состояние `Succeeded` означает подтверждённый успешный возврат со стороны внешней платёжной системы.

## 3.8. Refund Attempt

Как и Payment Attempt, Refund может иметь отдельные попытки выполнения.

```
Refund
  │
  ├── Refund Attempt 1 → Failed
  │
  └── Refund Attempt 2 → Succeeded
```

Это позволяет сохранять историю повторных операций без создания нескольких независимых Refund для одной бизнес-операции.

## 3.9. Взаимодействие с платёжным провайдером

Внешняя операция выполняется через Payment Integration.

Backend передаёт провайдеру только необходимые данные:

- внешний идентификатор исходной операции;
    
- сумму;
    
- валюту;
    
- идентификатор операции возврата;
    
- другие обязательные параметры протокола.
    

Credentials и секреты провайдера не передаются Frontend.

## 3.10. Подтверждение возврата

Ответ платёжного провайдера не должен без проверки изменять внутреннее состояние SmEl.

Возможная схема:

```
Provider
   │
   ▼
Response / Webhook
   │
   ▼
Validation
   │
   ▼
Payment Integration
   │
   ▼
Refund Service
   │
   ▼
Refund
```

Webhook обрабатывается как внешний недоверенный вход согласно ADR-038.

## 3.11. Идемпотентность

Операция возврата должна быть идемпотентной.

Повтор одного и того же запроса не должен приводить к повторному возврату денежных средств.

Особенно важно предотвращать:

- повторную отправку Refund;
    
- повторное создание Refund Attempt;
    
- повторное изменение суммы возвращённых средств;
    
- повторную обработку webhook.
    

Для каждой бизнес-операции возврата должен существовать механизм идентификации повторного запроса.

## 3.12. Ошибки возврата

Ошибки могут возникать из-за:

- недостаточной доступной суммы;
    
- недопустимого состояния Payment;
    
- отказа провайдера;
    
- сетевого сбоя;
    
- некорректных параметров;
    
- нарушения бизнес-правил;
    
- повторного запроса;
    
- внутренней ошибки SmEl.
    

Временная техническая ошибка может привести к повторной попытке.

Повторные попытки должны быть ограничены и контролируемы.

## 3.13. Неоднозначный результат

Если SmEl не получил подтверждение результата Refund из-за сетевого сбоя, операция не должна автоматически считаться неуспешной.

Например:

```
SmEl → Provider
          │
          ▼
       Refund
          │
          X
     Network Error
```

В этом случае Refund может находиться в промежуточном состоянии до получения подтверждения или проверки состояния операции.

Backend может запросить состояние Refund у провайдера.

Нельзя без проверки повторно отправлять финансовую операцию, если существует вероятность, что предыдущая операция уже была выполнена.

## 3.14. Асинхронная обработка

Получение результата Refund может происходить асинхронно.

Для этого могут использоваться:

- webhook;
    
- фоновые задачи;
    
- периодическая проверка состояния.
    

Асинхронные операции подчиняются ADR-033.

Worker не должен содержать собственную копию бизнес-логики возврата.

## 3.15. Связь Refund и Order

Refund связан с Payment, а Payment связан с Order.

Поэтому:

```
Order
  │
  ▼
Payment
  │
  ▼
Refund
```

Refund не должен изменять состав Order или Order Item.

Изменение статуса заказа в связи с возвратом является отдельной бизнес-операцией и выполняется через Service Layer.

Например, `Refunded` Payment не означает автоматически, что Order должен быть удалён или изменён в любой другой части.

## 3.16. Частичный возврат по Order Item

Архитектура допускает связь Refund с причиной или основанием возврата конкретных Order Item.

Однако финансовая операция и физический возврат товара остаются различными процессами.

Например:

```
Order
 │
 ├── Order Item A
 ├── Order Item B
 │
 └── Payment
       │
       └── Refund
```

Связь Refund с конкретными товарами может использоваться для бизнес-анализа и контроля суммы, но не должна смешивать финансовую и логистическую операции.

## 3.17. Безопасность

Операция возврата относится к критическим финансовым операциям.

Она должна:

- выполняться только уполномоченным субъектом или разрешённым бизнес-процессом;
    
- проходить серверную авторизацию;
    
- проверять объектный доступ;
    
- использовать защищённый канал;
    
- не раскрывать секреты;
    
- фиксироваться в журнале операций;
    
- иметь идентификатор операции.
    

Секреты платёжного провайдера управляются согласно ADR-029.

## 3.18. Аудит

Для Refund должна сохраняться история:

- кто или какой процесс инициировал операцию;
    
- когда она была создана;
    
- сумма;
    
- валюта;
    
- исходный Payment;
    
- внешний идентификатор;
    
- состояние;
    
- результат;
    
- время изменения состояния;
    
- причина ошибки, если операция завершилась ошибкой.
    

История не должна удаляться при последующей попытке возврата.

# 4. Правила

1. Refund является отдельной финансовой операцией.
    
2. Refund всегда связан с существующим Payment.
    
3. Исходный Payment не изменяется и не удаляется при создании Refund.
    
4. Поддерживаются полный и частичный возврат.
    
5. Сумма возвратов не может превышать доступную для возврата сумму.
    
6. Refund создаётся только Backend.
    
7. Frontend не выполняет возврат непосредственно у платёжного провайдера.
    
8. Возврат выполняется через Payment Service и Payment Integration.
    
9. Внешний результат возврата должен быть подтверждён Backend.
    
10. Webhook рассматривается как недоверенный внешний вход.
    
11. Refund должен быть идемпотентным.
    
12. Повторное выполнение одной операции не должно приводить к повторному возврату средств.
    
13. Refund Attempt сохраняет историю отдельных попыток.
    
14. Неоднозначный финансовый результат требует проверки состояния операции перед повторной отправкой.
    
15. Ошибки и повторные попытки должны быть контролируемыми.
    
16. Refund может обрабатываться асинхронно согласно ADR-033.
    
17. Refund не изменяет состав Order и Order Item.
    
18. Финансовая операция и возврат физического товара являются различными процессами.
    
19. Операции Refund требуют авторизации.
    
20. Секреты платёжной интеграции управляются согласно ADR-029.
    
21. История Refund должна сохраняться для аудита.
    
22. Бизнес-правила возврата товара не определяются настоящим ADR.

# 6. Заключительные положения

ADR-039 определяет возврат денежных средств как самостоятельную финансовую операцию, связанную с исходным Payment.

Архитектура поддерживает полный и частичный возврат, несколько попыток выполнения, идемпотентность, webhook и асинхронное подтверждение результата.

История исходного платежа и история возврата сохраняются независимо.

Конкретный платёжный провайдер, протокол возврата и бизнес-правила, определяющие право клиента на возврат, устанавливаются отдельными решениями.
