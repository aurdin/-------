# 1. Назначение

Настоящее архитектурное решение определяет принципы реализации доменной модели проекта **Smart Electric (SmEl)** в физической модели данных PostgreSQL и объектной модели Django ORM.

Цель решения — установить единый подход к проектированию моделей данных, их взаимосвязей и структуры хранения с сохранением соответствия ранее принятым архитектурным решениям и стандартам проекта.

# 2. Область применения

Решение распространяется на:

- модели Django ORM;
    
- структуру базы данных PostgreSQL;
    
- связи между моделями;
    
- ограничения целостности;
    
- индексацию;
    
- миграции;
    
- разделение моделей по Django-приложениям;
    
- реализацию многоязычных данных;
    
- физическую реализацию доменных областей SmEl.
    

Решение определяет архитектурные принципы физической модели, но не фиксирует конкретный состав всех моделей и полей. Детальная структура определяется на этапе реализации.

# 3. Основная часть

## 3.1. Переход от доменной модели к физической

Физическая модель данных строится на основе доменной модели, определенной в **ADR-018**.

Основными принципами являются:

- каждой доменной сущности соответствует отдельная модель Django, если иное не обосновано архитектурно;
    
- каждая модель имеет единственную область ответственности;
    
- модели распределяются по специализированным Django-приложениям;
    
- связи между моделями определяются явно;
    
- физическая структура PostgreSQL должна сохранять установленные доменные границы.
    

## 3.2. Структура Django-приложений

Физическая модель распределяется между специализированными приложениями:

```
backend/apps/

lists/
catalog/
prices/
stock/
customers/
users/
cart/
orders/
media/
seo/
import/
dbview/
```

Каждое приложение реализует собственную предметную область.

Конкретный состав приложений может изменяться при развитии проекта при условии сохранения архитектурных границ, определенных в ADR-002 и ADR-018.

## 3.3. Принципы построения моделей

Для моделей проекта устанавливаются следующие правила:

- одна модель соответствует одной основной сущности;
    
- одна модель имеет одну основную ответственность;
    
- каждая модель имеет первичный ключ;
    
- связи реализуются средствами Django ORM;
    
- ограничения целостности определяются на уровне базы данных;
    
- повторное использование общей структуры допускается через абстрактные базовые модели;
    
- структура моделей не должна нарушать доменные границы.
    

## 3.4. Общие базовые модели

Для обеспечения единообразия допускается использование общих абстрактных моделей.

Возможные базовые модели:

- `BaseModel`;
    
- `TimestampedModel`;
    
- `NamedModel`;
    
- `OrderedModel`;
    
- `SeoModel`;
    
- `MediaModel`.
    

Конкретный состав, назначение и область применения базовых моделей определяется на этапе реализации.

Использование базовых моделей не должно приводить к объединению различных доменных сущностей в одну модель.

# 4. Правила

## 4.1. Идентификация

Все внутренние связи строятся на основе стабильных внутренних идентификаторов.

SKU является основным внутренним идентификатором товарной позиции.

Артикул производителя является внешним идентификатором и не используется в качестве основного внутреннего ключа.

Правила идентификации определяются ADR-008.

## 4.2. Ссылочная целостность

Связи между сущностями должны обеспечивать ссылочную целостность.

Использование внешних ключей и других ограничений целостности определяется физической моделью и должно соответствовать правилам PostgreSQL и Django ORM.

Критичные связи не должны зависеть исключительно от логики приложения.

## 4.3. Нормализация

Физическая модель должна обеспечивать:

- отсутствие необоснованного дублирования данных;
    
- нормализованную структуру;
    
- явные связи между сущностями;
    
- однозначное владение данными;
    
- возможность масштабирования.
    

Денормализация допускается только при наличии архитектурного обоснования.

## 4.4. Разделение доменных областей

При реализации моделей сохраняется разделение следующих областей:

- каталог;
    
- технические характеристики;
    
- коммерческие данные;
    
- складской учет;
    
- пользователи;
    
- клиенты;
    
- корзина;
    
- заказы;
    
- медиа;
    
- поиск и SEO;
    
- интеграция.
    

Смешивание различных доменных областей в одной модели не допускается без архитектурного обоснования.

## 4.5. Разделение технических и коммерческих данных

В соответствии с **STD-006** технические и коммерческие данные товара реализуются независимыми моделями.

Карточка товара не должна непосредственно содержать:

- цену;
    
- остаток;
    
- скидку;
    
- акцию;
    
- коммерческие условия.
    

Коммерческие данные связываются с товарной позицией через установленные связи, включая SKU.

## 4.6. Многоязычность

Все пользовательские текстовые поля проектируются с учетом обязательной поддержки:

- украинского (`uk`);
    
- русского (`ru`);
    
- английского (`en`).
    

Локализация реализуется на Backend в соответствии с ADR-017.

Механизм хранения переводов должен обеспечивать возможность изменения и расширения языковой реализации без нарушения API и доменной модели.

## 4.7. Миграции

Изменение структуры базы данных выполняется посредством контролируемых миграций Django.

Миграции должны обеспечивать:

- последовательное изменение схемы;
    
- воспроизводимость структуры базы данных;
    
- сохранение целостности данных;
    
- возможность контролируемого развертывания изменений.
    

Прямое изменение структуры производственной базы данных в обход принятого механизма миграций не допускается, кроме специально обоснованных эксплуатационных операций.

## 4.8. Представления базы данных

Для сложных операций чтения могут использоваться SQL-представления в соответствии с **ADR-006**.

Представления:

- предназначены преимущественно для чтения;
    
- не являются источником бизнес-логики;
    
- не используются для записи бизнес-данных;
    
- реализуются в соответствии с правилами подсистемы `dbview`.
    

## 4.9. Индексация и производительность

Физическая модель должна предусматривать:

- индексацию часто используемых полей;
    
- индексацию полей, участвующих в фильтрации и поиске;
    
- оптимизацию связей и запросов;
    
- использование SQL-представлений для сложных операций чтения при необходимости;
    
- возможность последующего применения механизмов кэширования.
    

Индексы должны создаваться на основании реальных сценариев доступа и требований производительности, а не добавляться без необходимости.

# 5. Ограничения

При проектировании и реализации физической модели запрещается:

- смешивать различные доменные области без архитектурного обоснования;
    
- хранить коммерческие данные непосредственно в каталоге;
    
- использовать SQL VIEW для записи бизнес-данных;
    
- использовать внешний артикул как основной внутренний идентификатор товара;
    
- обходить бизнес-логику посредством прямого изменения данных;
    
- создавать дублирующие модели одной и той же предметной сущности без архитектурной необходимости;
    
- изменять структуру базы данных вне установленного процесса миграций без специального обоснования;
    
- нарушать принятые архитектурные решения.
    

# 6. Причины выбора

Выбранный подход обеспечивает:

- соответствие физической модели доменной модели;
    
- единообразную реализацию моделей Django;
    
- прозрачную структуру PostgreSQL;
    
- снижение связанности компонентов;
    
- высокую сопровождаемость;
    
- сохранение ссылочной целостности;
    
- возможность масштабирования;
    
- независимое развитие Django-приложений;
    
- контролируемое изменение структуры базы данных.
    

# 7. Последствия

## 7.1. Преимущества

- единая архитектура моделей Django;
    
- прозрачная структура PostgreSQL;
    
- четкое разделение доменных областей;
    
- снижение риска дублирования данных;
    
- упрощение сопровождения;
    
- независимое развитие приложений;
    
- контролируемое изменение схемы базы данных;
    
- готовность к дальнейшему масштабированию проекта.
    

## 7.2. Ограничения

- изменение доменной модели требует пересмотра физической модели;
    
- новые модели должны соответствовать существующим архитектурным решениям;
    
- сложные изменения схемы требуют анализа влияния на существующие данные;
    
- чрезмерная нормализация может увеличивать сложность запросов;
    
- конкретный состав моделей и полей определяется на этапе реализации.

# 9. Заключительные положения

Физическая модель данных SmEl реализуется на основе доменной модели, определенной в ADR-018, с использованием **PostgreSQL** и **Django ORM**.

Модели данных распределяются по специализированным Django-приложениям и должны сохранять установленные доменные границы, ссылочную целостность, нормализованную структуру и единый подход к идентификации.

Изменения структуры базы данных выполняются контролируемо посредством миграций Django.

Настоящее решение является архитектурной основой для последующего детального проектирования моделей Django ORM, структуры таблиц PostgreSQL, индексов, ограничений и механизмов хранения данных.
