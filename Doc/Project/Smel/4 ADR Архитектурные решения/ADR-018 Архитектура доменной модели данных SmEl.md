# 1. Назначение

Настоящее архитектурное решение определяет общую архитектуру доменной модели данных проекта **Smart Electric (SmEl)**.

Цель решения — определить основные бизнес-сущности системы, их зоны ответственности и правила взаимодействия между ними до перехода к физической реализации в PostgreSQL и Django ORM.

# 2. Область применения

Решение распространяется на основные домены и связанные с ними сущности SmEl:

- каталог товаров;
    
- коммерческие данные;
    
- складской учет;
    
- клиенты и пользователи;
    
- корзина и заказы;
    
- платежи;
    
- доставка;
    
- медиа-контент;
    
- поиск и SEO;
    
- интеграции с внешними системами.
    

Физическая структура таблиц PostgreSQL и конкретная реализация моделей Django ORM настоящим решением не фиксируются.

# 3. Основная часть

## 3.1. Принцип разделения доменов

Доменная модель SmEl строится по принципу разделения ответственности между предметными областями.

Основные домены:

```
SmEl Domain Model

├── Catalog Domain
│
├── Commercial Domain
│
├── Inventory Domain
│
├── Customer Domain
│
├── Order Domain
│
├── Media Domain
│
├── Search & SEO Domain
│
└── Integration Domain
```

Каждый домен имеет собственную ответственность и взаимодействует с другими доменами через явно определенные связи и архитектурные интерфейсы.

## 3.2. Общая модель сущностей

Основная структура товарных данных:

```
                         Catalog

Category
    │
    ▼
Group
    │
    ▼
Type
    │
    ▼
Configuration
    │
    ▼
Execution
    │
    ▼
SKU / Product


SKU
 │
 ├────────────── Technical Data
 │               ├── Characteristics
 │               ├── Brand
 │               ├── Series
 │               ├── Media
 │               └── SEO
 │
 ├────────────── Commercial Data
 │               ├── Price
 │               ├── Discount
 │               └── Promotion
 │
 ├────────────── Inventory Data
 │               ├── Warehouse
 │               ├── Stock
 │               └── Reservation
 │
 └────────────── Sales Process
                 ├── Cart
                 └── Order
```

SKU является стабильной внутренней идентификацией товарной позиции и основной точкой связи товарных данных с коммерческими, складскими и торговыми процессами.

При этом остальные домены сохраняют собственные сущности и идентификаторы.

# 4. Доменные сущности

## 4.1. Каталог товаров

Каталог отвечает за техническое и классификационное описание товарных позиций.

Включает:

- Category;
    
- Group;
    
- Type;
    
- Configuration;
    
- Execution;
    
- Product / SKU;
    
- Brand;
    
- Series;
    
- Characteristics.
    

Каталог не содержит непосредственно:

- цены;
    
- скидки;
    
- акции;
    
- складские остатки;
    
- резервирование;
    
- корзины;
    
- заказы.
    

Коммерческие и складские данные связаны с товарной позицией через установленные архитектурные связи.

## 4.2. Коммерческий домен

Коммерческий домен отвечает за условия продажи товара.

Включает:

- Price List;
    
- Product Price;
    
- Discount;
    
- Promotion;
    
- Currency;
    
- Commercial Rules.
    

Стоимость, скидки и акции являются частью коммерческого блока ценообразования.

Коммерческие данные отделены от технического описания товара и связаны с товарными позициями через SKU.

## 4.3. Складской домен

Складской домен отвечает за наличие и движение товарных позиций.

Включает:

- Warehouse;
    
- Stock;
    
- Reservation;
    
- Incoming Supply.
    

Складские данные не изменяют техническое описание товара и не определяют его идентичность.

## 4.4. Клиентский домен

Клиентский домен отвечает за участников коммерческого взаимодействия с системой.

Включает:

- User;
    
- Customer;
    
- Company;
    
- Address;
    
- Role;
    
- Permission.
    

User отвечает за учетную запись и доступ к системе, а Customer — за участника коммерческих отношений.

Связи между User и Customer определяются архитектурой клиентского домена.

## 4.5. Домен продаж и заказов

Домен продаж отвечает за жизненный цикл покупки.

Включает:

- Cart;
    
- Cart Item;
    
- Checkout;
    
- Order;
    
- Order Item;
    
- Payment;
    
- Delivery.
    

Cart является временным изменяемым состоянием покупки.

Order является зафиксированным результатом оформления покупки и сохраняет коммерческую историю операции.

## 4.6. Медиа-домен

Медиа-домен отвечает за изображения, документы и другие связанные с товарами информационные ресурсы.

Включает:

- Media;
    
- MediaLink;
    
- Image;
    
- Document;
    
- Video;
    
- Certificate;
    
- Manual;
    
- другие типы медиа.
    

Медиа-объекты являются самостоятельными сущностями и могут связываться с несколькими объектами предметной области.

## 4.7. Домен поиска и SEO

Домен поиска и SEO отвечает за:

- поиск товаров;
    
- фильтрацию;
    
- сортировку;
    
- фасеты;
    
- поисковые представления;
    
- SEO-данные;
    
- URL;
    
- canonical URL;
    
- sitemap;
    
- структурированные данные.
    

Данный домен использует данные каталога и других подсистем, но не изменяет их исходные бизнес-сущности.

## 4.8. Интеграционный домен

Интеграционный домен обеспечивает взаимодействие SmEl с внешними системами и источниками данных.

Включает механизмы:

- импорта;
    
- синхронизации;
    
- преобразования данных;
    
- сопоставления;
    
- передачи данных;
    
- журналирования интеграционных операций.
    

Интеграционный домен не должен переносить структуру внешних систем непосредственно во внутреннюю доменную модель SmEl.

# 5. Правила связей между доменами

## 5.1. SKU как точка связи товарных данных

SKU является стабильным внутренним идентификатором товарной позиции.

Основные связи товарной позиции:

```
Catalog
   │
   ▼
 SKU
   │
   ├── Price
   ├── Stock
   ├── Cart Item
   ├── Order Item
   └── Media
```

SKU используется для связи товарной позиции с коммерческими, складскими, торговыми и медиа-данными.

## 5.2. Независимость доменов

Каждый домен должен сохранять собственную ответственность.

Изменение данных одного домена не должно приводить к неявному изменению сущностей другого домена.

Связи между доменами должны быть явными и архитектурно обоснованными.

## 5.3. Отсутствие дублирования

Одна предметная сущность не должна иметь несколько независимых реализаций без архитектурной необходимости.

Общие данные должны иметь единственный источник истины.

## 5.4. История важных данных

Для сущностей, изменения которых имеют коммерческое или операционное значение, должна обеспечиваться возможность сохранения истории изменений.

Конкретный механизм хранения истории определяется отдельными архитектурными решениями.

# 6. Правила хранения данных

Обязательными являются следующие требования:

- каждая сущность имеет определенную ответственность;
    
- данные не дублируются без необходимости;
    
- связи между доменами являются явными;
    
- технические данные отделены от коммерческих;
    
- складские данные отделены от каталога;
    
- данные клиентов отделены от товарных данных;
    
- изменения критичных данных должны контролироваться;
    
- удаление критичных данных должно выполняться по установленным правилам;
    
- физическая структура базы данных не должна нарушать установленные доменные границы.
    

# 7. Многоязычность

Все пользовательские текстовые данные должны поддерживать:

- `uk`;
    
- `ru`;
    
- `en`.
    

Требование распространяется, в частности, на:

- категории;
    
- товары;
    
- характеристики;
    
- серии;
    
- описания;
    
- SEO-данные;
    
- другие пользовательские текстовые данные.
    

Языковая логика реализуется на уровне Backend в соответствии с ADR-017.

Многоязычность является обязательным архитектурным требованием и должна учитываться при проектировании новых доменных сущностей.

# 8. Причины выбора

Выбранная доменная модель обеспечивает:

- соответствие принятой архитектуре разделения ответственности;
    
- снижение связанности подсистем;
    
- независимое развитие доменов;
    
- контролируемые связи между сущностями;
    
- возможность масштабирования отдельных подсистем;
    
- упрощение интеграции с внешними системами;
    
- снижение риска дублирования данных;
    
- подготовку к дальнейшей реализации модели данных;
    
- соответствие основным принципам **DDD (Domain-Driven Design)**.
    

# 9. Последствия

## 9.1. Преимущества

- понятная структура доменной модели;
    
- четкое разделение ответственности;
    
- упрощение расширения функциональности;
    
- возможность независимого развития подсистем;
    
- снижение связанности;
    
- снижение риска архитектурных ошибок;
    
- возможность последующего развития отдельных доменов.
    

## 9.2. Ограничения

- не допускается создание универсальных сущностей без четкого назначения;
    
- не допускается смешивание различных доменов в одной модели без архитектурного обоснования;
    
- новые сущности должны иметь определенную принадлежность к домену;
    
- междоменные связи должны быть явно определены;
    
- изменение доменной модели требует архитектурного анализа;
    
- физическая реализация не должна нарушать установленные доменные границы.

# 11. Заключительные положения

Доменная модель SmEl строится вокруг разделения предметных областей на независимые домены с четко определенной ответственностью.

**SKU является стабильной внутренней точкой связи товарной позиции с коммерческими, складскими, торговыми и медиа-данными, но не заменяет идентификаторы и сущности других доменов.**

Технические, коммерческие, складские, клиентские и операционные данные должны сохранять самостоятельность и взаимодействовать через явно определенные архитектурные связи.

Настоящее решение является основой для последующего проектирования физической модели данных PostgreSQL и моделей Django ORM.
