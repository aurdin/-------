# 1. Назначение

ADR-038 определяет архитектуру интеграции SmEl с внешним платёжным провайдером.

Документ детализирует ADR-025 в части:

- инициирования платежа;
    
- взаимодействия с внешним платёжным провайдером;
    
- получения результата платежной операции;
    
- webhook/callback;
    
- подтверждения результата;
    
- синхронизации состояния Payment и Order;
    
- обработки повторных и ошибочных событий.
    

Цель решения — обеспечить контролируемую границу между внутренней платёжной моделью SmEl и внешней платёжной системой.

# 2. Область применения

Решение распространяется на:

- Order;
    
- Payment;
    
- Payment Attempt;
    
- Payment Service;
    
- Payment Integration;
    
- REST API;
    
- внешний платёжный провайдер;
    
- webhook/callback;
    
- Service Layer;
    
- Frontend.
    

ADR-038 не определяет:

- конкретного платёжного провайдера;
    
- конкретный платёжный протокол;
    
- конкретную платёжную валюту;
    
- конкретные тарифы провайдера;
    
- конкретный формат webhook;
    
- конкретный способ хранения платёжных реквизитов.
    

# 3. Основная часть

## 3.1. Архитектурная граница

Внешний платёжный провайдер является внешней системой и не получает прямого доступа к внутренней базе данных SmEl.

Основная архитектура:

```
Frontend
   │
   ▼
REST API
   │
   ▼
Payment Service
   │
   ▼
Payment Integration
   │
   ▼
External Payment Provider
```

Обратное взаимодействие:

```
External Payment Provider
          │
          ▼
     Webhook / Callback
          │
          ▼
      REST API
          │
          ▼
 Payment Integration
          │
          ▼
    Payment Service
          │
          ▼
      Order / Payment
```

Внешний провайдер взаимодействует только с предусмотренной Integration/API границей.

## 3.2. Создание Payment

После создания Order Backend может создать Payment как отдельную бизнес-сущность.

Payment должен иметь собственный идентификатор и состояние.

Order и Payment не являются одной сущностью.

```
Order
  │
  ▼
Payment
  │
  ▼
Payment Attempt
  │
  ▼
External Provider
```

Один Order может иметь несколько Payment Attempt.

## 3.3. Инициация платежа

Платёж инициируется Backend через Payment Service.

Общий процесс:

```
Order
 │
 ▼
Create Payment
 │
 ▼
Create Payment Attempt
 │
 ▼
Payment Integration
 │
 ▼
External Provider
 │
 ▼
Payment Instruction / Payment URL
 │
 ▼
Frontend
```

Frontend получает только необходимые данные для продолжения платёжного сценария.

Frontend не определяет сумму платежа самостоятельно.

## 3.4. Сумма платежа

Сумма платежа определяется Backend на основании зафиксированного коммерческого результата Order.

В расчёт могут входить:

- стоимость Order Item;
    
- применённые скидки;
    
- применённые акции;
    
- стоимость доставки;
    
- другие подтверждённые коммерческие условия;
    
- итоговая сумма заказа.
    

После создания Order сумма, передаваемая платёжному провайдеру, не должна рассчитываться Frontend самостоятельно.

Payment не должен использовать текущую цену каталога вместо зафиксированной стоимости Order.

## 3.5. Payment Attempt

Каждая попытка проведения платежа должна иметь собственный идентификатор.

Payment Attempt может содержать:

- внутренний идентификатор;
    
- ссылку на Payment;
    
- внешний идентификатор операции;
    
- сумму;
    
- валюту;
    
- время создания;
    
- время завершения;
    
- состояние;
    
- результат;
    
- техническую информацию интеграции;
    
- причину ошибки.
    

Payment Attempt позволяет сохранить историю повторных попыток.

## 3.6. Состояния платежа

Базовый жизненный цикл:

```
Created
   │
   ▼
Pending
   │
   ├──► Paid
   │
   ├──► Failed
   │
   └──► Cancelled

Paid
 │
 ▼
Refunded
```

Конкретный набор состояний и переходов может быть расширен.

Состояние Payment должно изменяться только контролируемой серверной операцией.

## 3.7. Webhook / Callback

Webhook является одним из основных механизмов получения результата платежа от внешнего провайдера.

```
Payment Provider
      │
      ▼
Webhook
      │
      ▼
API Boundary
      │
      ▼
Validation
      │
      ▼
Payment Integration
      │
      ▼
Payment Service
      │
      ▼
Payment / Order
```

Webhook не должен напрямую изменять PostgreSQL.

Обработка проходит через Integration Layer и Service Layer.

## 3.8. Проверка webhook

Каждый внешний webhook рассматривается как недоверенный входящий запрос.

Backend должен проверить:

- источник события;
    
- подпись или другой механизм аутентификации;
    
- идентификатор события;
    
- внешний идентификатор платежной операции;
    
- соответствие Payment;
    
- сумму;
    
- валюту;
    
- допустимость перехода состояния;
    
- повторность события.
    

Только после успешной проверки результат может изменить внутреннее состояние Payment.

## 3.9. Идемпотентность

Webhook может быть доставлен повторно.

Повторное получение одного события не должно:

- повторно создавать Payment;
    
- повторно подтверждать заказ;
    
- повторно изменять финансовое состояние;
    
- повторно выполнять другие бизнес-операции.
    

Каждое внешнее событие должно иметь идентификатор или иной механизм определения повторной обработки.

Для повторной доставки применяется принцип идемпотентности ADR-033.

## 3.10. Авторитет источников

Для разных данных используются разные источники истины.

**SmEl является источником истины для:**

- Order;
    
- внутреннего Payment;
    
- внутренних состояний заказа;
    
- внутренних связей между Order и Payment.
    

**Платёжный провайдер является источником результата внешней платёжной операции.**

Backend обязан проверять внешний результат перед изменением внутреннего Payment.

Наличие сообщения от Frontend о якобы успешной оплате не является подтверждением платежа.

## 3.11. Frontend после оплаты

Frontend может получить от платёжного провайдера информацию о результате пользовательского сценария.

Однако Frontend не имеет права самостоятельно переводить Payment или Order в состояние `Paid`.

Окончательное состояние определяется Backend после подтверждения результата внешней операции.

Поэтому возможна ситуация:

```
Frontend → "Payment completed"
             │
             ▼
        Backend verification
             │
       ┌─────┴─────┐
       ▼           ▼
   Confirmed     Rejected
```

## 3.12. Синхронное и асинхронное взаимодействие

Инициация платежа может выполняться синхронно.

Получение окончательного результата может выполняться асинхронно через webhook.

При необходимости Backend может дополнительно запросить состояние платежа у провайдера.

Архитектура:

```
Initiation
   │
   ▼
Provider
   │
   ├──► Immediate Response
   │
   └──► Webhook
            │
            ▼
       Final Verification
```

Длительные и повторяемые фоновые операции могут выполняться через механизм ADR-033.

## 3.13. Ошибки интеграции

Ошибки должны разделяться на:

- ошибки клиента;
    
- ошибки бизнес-правил;
    
- ошибки платёжного провайдера;
    
- ошибки сети;
    
- ошибки валидации webhook;
    
- повторные события;
    
- внутренние технические ошибки.
    

Временные ошибки могут приводить к повторной попытке.

Повторные попытки должны быть ограничены.

Неуспешный платёж должен иметь контролируемое состояние и сохраняться в истории.

## 3.14. Несогласованность Payment и Order

Payment и Order изменяются независимо, поэтому возможны промежуточные состояния.

Например:

```
Provider → Payment = Paid
             │
             ▼
        Order update
             │
             ▼
       Order = Paid
```

Обновление должно выполняться через Service Layer и транзакционные механизмы там, где это возможно.

При техническом сбое состояние должно быть обнаруживаемым и подлежать контролируемому восстановлению.

## 3.15. Повторная проверка результата

Для критических платёжных операций Backend может запросить состояние операции непосредственно у внешнего провайдера.

Это особенно важно при:

- отсутствии webhook;
    
- неоднозначном ответе;
    
- сетевом сбое;
    
- повторном запросе;
    
- восстановлении после ошибки.
    

Frontend не является механизмом подтверждения платежа.

## 3.16. Безопасность

Платёжная интеграция должна:

- использовать защищённый канал;
    
- не передавать секреты Frontend;
    
- защищать credentials провайдера;
    
- проверять входящие webhook;
    
- не записывать секреты в логи;
    
- ограничивать права интеграционного компонента;
    
- использовать секреты согласно ADR-029.
    

Если платёжный провайдер поддерживает токенизацию или hosted payment page, предпочтительно не передавать через Backend SmEl полные платёжные реквизиты клиента без архитектурной необходимости.

## 3.17. Повторная оплата

Повторная попытка оплаты должна создавать новый Payment Attempt либо использовать иной явно определённый механизм повторной операции.

Повторная попытка не должна создавать новый Order автоматически.

Order сохраняет исходную покупку, а Payment сохраняет историю её финансовых операций.

## 3.18. Возврат денежных средств

Возврат является отдельной операцией.

ADR-038 не определяет детальную архитектуру возврата; она устанавливается ADR-039.

Payment history должна позволять связать возврат с исходной платёжной операцией.

# 4. Правила

1. Внешний платёжный провайдер является отдельной системой.
    
2. Прямой доступ провайдера к PostgreSQL запрещён.
    
3. Интеграция с провайдером выполняется через Integration Layer.
    
4. Бизнес-операции Payment выполняются через Service Layer.
    
5. Order и Payment являются различными сущностями.
    
6. Payment Attempt является отдельной операцией внутри платёжного процесса.
    
7. Один Order может иметь несколько Payment Attempt.
    
8. Сумма платежа определяется Backend на основании зафиксированного Order.
    
9. Frontend не определяет окончательную сумму платежа.
    
10. Frontend не подтверждает успешность Payment самостоятельно.
    
11. Webhook рассматривается как недоверенный внешний вход.
    
12. Webhook проходит обязательную проверку.
    
13. Повторный webhook не должен повторно выполнять бизнес-операцию.
    
14. Payment должен иметь собственный жизненный цикл.
    
15. Внешний результат платежа должен быть подтверждён Backend.
    
16. SmEl является источником истины для внутреннего состояния Order и Payment.
    
17. Внешний провайдер является источником результата внешней платёжной операции.
    
18. Временные ошибки интеграции могут обрабатываться повторно с ограничением количества попыток.
    
19. Повторная попытка оплаты не создаёт новый Order автоматически.
    
20. Секреты платёжной интеграции управляются согласно ADR-029.
    
21. Асинхронная обработка платёжных событий подчиняется ADR-033.
    
22. Возвраты являются отдельной операцией и детализируются ADR-039.

# 6. Заключительные положения

ADR-038 фиксирует архитектурную границу между SmEl и внешним платёжным провайдером.

Платёж инициируется Backend, а окончательный результат подтверждается Backend на основании проверенного ответа внешнего провайдера. Webhook рассматривается как внешний недоверенный вход и обрабатывается через Integration Layer и Service Layer.

Order, Payment и Payment Attempt сохраняют независимые жизненные циклы и историю операций.

Конкретный платёжный провайдер, протокол интеграции и детальные правила возврата определяются отдельными архитектурными решениями.
