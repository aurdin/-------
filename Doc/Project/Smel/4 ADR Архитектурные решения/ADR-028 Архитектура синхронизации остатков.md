# 1. Назначение

Настоящее архитектурное решение определяет принципы синхронизации складских остатков и доступности товарных позиций в проекте SmEl.

Документ устанавливает границы процесса синхронизации, источники и получателей данных, требования к актуальности, идентификации, повторной обработке и согласованности данных.

# 2. Область применения

Решение применяется к синхронизации данных, связанных с:

- физическими остатками;
    
- доступным количеством;
    
- резервами;
    
- поступлениями;
    
- складами;
    
- статусом доступности товара;
    
- внешними ERP/WMS и иными складскими системами.
    

Решение не определяет конкретную ERP/WMS, протокол интеграции или периодичность обмена.

# 3. Основная часть

## 3.1. Общие принципы

Складской учет является отдельной предметной областью и отделён от каталога и ценообразования.

SKU является основным идентификатором связи товарной позиции с остатками.

Система SmEl должна иметь централизованное представление об остатках и доступности, используемое корзиной, Checkout и другими бизнес-процессами.

## 3.2. Источник складских данных

При наличии внешней складской системы она является источником фактических складских данных в пределах своей ответственности.

Обобщённая архитектура:

```
External ERP / WMS
        │
        ▼
Integration Layer
        │
        ▼
Stock Synchronization Service
        │
        ▼
Stock Domain
        │
        ▼
PostgreSQL
        │
        ├──────────► Catalog Availability
        ├──────────► Cart / Checkout
        └──────────► Order Processing
```

Frontend не взаимодействует непосредственно с ERP/WMS.

Если внешнего источника нет, внутренний складской контур SmEl является источником соответствующих данных.

## 3.3. Данные остатков

Для товарной позиции и склада могут учитываться:

- Quantity Available;
    
- Quantity Reserved;
    
- Quantity Incoming;
    
- Quantity On Order;
    
- Last Update;
    
- Stock Status.
    

Фактический набор полей и формулы расчёта доступного количества определяются последующими решениями.

Остаток и доступность являются различными понятиями.

## 3.4. Идентификация

Сопоставление внешних складских данных с внутренними товарными позициями выполняется через контролируемое отображение идентификаторов.

Основным внутренним идентификатором является SKU.

Article и EAN/GTIN могут использоваться как внешние идентификаторы при импорте, но не заменяют внутренний SKU.

Неоднозначное или отсутствующее сопоставление должно приводить к ошибке обработки записи, а не к созданию произвольной товарной позиции.

## 3.5. Процесс синхронизации

Общий процесс:

```
Получение данных
      ↓
Валидация
      ↓
Идентификация SKU
      ↓
Проверка склада
      ↓
Нормализация
      ↓
Обновление Stock
      ↓
Фиксация результата
      ↓
Логирование
```

Каждый этап выполняется контролируемым сервисом.

Ошибочная запись не должна автоматически изменять остатки другой товарной позиции.

## 3.6. Полная и инкрементальная синхронизация

Система должна поддерживать архитектурную возможность:

- полной синхронизации;
    
- инкрементальной синхронизации.
    

Полная синхронизация используется для восстановления или полной сверки состояния.

Инкрементальная синхронизация предназначена для передачи только изменившихся данных.

Конкретный режим может зависеть от возможностей внешней системы.

## 3.7. Идемпотентность

Повторное получение одной и той же информации не должно приводить к некорректному накоплению остатков.

Операции синхронизации должны быть идемпотентными либо иметь механизм определения уже обработанных сообщений/изменений.

Это особенно важно при:

- повторной передаче;
    
- сетевых сбоях;
    
- повторной обработке очереди;
    
- восстановлении после ошибки;
    
- повторном запуске синхронизации.
    

## 3.8. Актуальность

Для данных остатков должна учитываться дата и/или время последнего подтверждённого обновления.

Backend не должен представлять устаревшие данные как гарантированно актуальные без соответствующей бизнес-логики.

Порог допустимой устарелости определяется отдельными требованиями и техническими решениями.

## 3.9. Остаток и резерв

Физический остаток, доступное количество и резерв не должны смешиваться.

Резерв является отдельным состоянием складского учета.

Изменение резерва должно выполняться отдельной бизнес-операцией и не должно имитироваться простым импортом доступного остатка.

Правила резервирования товара при Checkout или оформлении заказа определяются отдельным архитектурным решением.

## 3.10. Использование данных в корзине и Checkout

Cart и Checkout используют централизованные данные Stock для проверки возможности продолжения оформления.

Наличие товара в корзине само по себе не гарантирует наличие товара на складе в момент Checkout.

Перед созданием заказа Backend должен повторно проверить актуальное состояние доступности согласно бизнес-правилам.

ADR-028 не фиксирует, создаётся ли резерв:

- при добавлении в корзину;
    
- при Checkout;
    
- при создании заказа;
    
- при оплате.
    

Это определяется отдельным решением.

## 3.11. Ошибки синхронизации

Ошибки должны фиксироваться отдельно от успешно обработанных данных.

Минимально должны быть различимы:

- ошибка идентификации товара;
    
- ошибка идентификации склада;
    
- ошибка формата;
    
- ошибка валидации;
    
- конфликт данных;
    
- ошибка внешнего источника;
    
- ошибка внутренней обработки.
    

Ошибка одной записи не должна останавливать обработку всех остальных корректных записей, если это допускается конкретным режимом синхронизации.

## 3.12. История изменений

Для складских данных должна существовать возможность определить:

- текущее состояние;
    
- источник изменения;
    
- время обновления;
    
- результат обработки.
    

Детальная модель аудита и хранения полной истории изменений определяется последующими решениями.

# 4. Правила

1. Остатки являются отдельной предметной областью.
    
2. SKU является основным внутренним идентификатором складской позиции.
    
3. Article и EAN/GTIN могут использоваться для внешнего сопоставления.
    
4. Frontend не взаимодействует с ERP/WMS напрямую.
    
5. Все операции синхронизации проходят через Integration Layer и Backend.
    
6. Stock является централизованным источником данных об остатках внутри SmEl.
    
7. Физический остаток, доступное количество и резерв являются различными понятиями.
    
8. Резерв не должен моделироваться как обычное обновление остатка.
    
9. Синхронизация должна поддерживать полную и инкрементальную обработку.
    
10. Повторная обработка одинаковых данных не должна приводить к некорректному изменению остатков.
    
11. Каждое обновление должно иметь контролируемую дату и/или время актуальности.
    
12. Ошибки синхронизации должны фиксироваться и быть доступны для анализа.
    
13. Ошибка одной записи не должна без необходимости блокировать обработку остальных записей.
    
14. Неоднозначное сопоставление SKU должно приводить к контролируемой ошибке.
    
15. Данные Stock используются Cart и Checkout для проверки доступности.
    
16. Наличие товара в Cart не является гарантией наличия товара при Checkout.
    
17. Перед созданием Order Backend должен повторно проверить доступность товара.
    
18. Правила резервирования определяются отдельным архитектурным решением.
    
19. Внешняя система является источником фактических складских данных только в пределах определённой для неё ответственности.
    
20. Конкретные ERP/WMS, протоколы, частота синхронизации и механизм обмена определяются отдельными решениями.
