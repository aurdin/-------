# 1. Назначение

Настоящее архитектурное решение определяет принципы управления секретами и конфиденциальными параметрами проекта SmEl.

Документ устанавливает правила хранения, использования, передачи, изменения и защиты секретов, необходимых для работы Backend, Frontend, базы данных и внешних интеграций.

# 2. Область применения

Решение распространяется на:

- пароли;
    
- ключи API;
    
- токены;
    
- секреты аутентификации;
    
- ключи подписи;
    
- учетные данные баз данных;
    
- секреты внешних интеграций;
    
- секреты платёжных и логистических провайдеров;
    
- криптографические ключи;
    
- другие конфиденциальные параметры, компрометация которых может нарушить безопасность системы.
    

Публичная конфигурация приложения не считается секретом, если её раскрытие не создаёт угрозу безопасности.

# 3. Основная часть

## 3.1. Общие принципы

Секреты являются конфиденциальными данными и должны быть отделены от исходного кода приложения.

Секреты не должны храниться непосредственно в репозитории исходного кода.

Каждая среда выполнения должна использовать собственный набор секретов, если это необходимо для изоляции окружений.

Минимально должны различаться:

- локальная разработка;
    
- тестовая среда;
    
- production.
    

## 3.2. Источник секретов

Архитектурно допускается использование специализированного хранилища секретов либо защищённого механизма передачи конфигурации в среду выполнения.

Обобщённая схема:

```
Secrets Management
        │
        ▼
Application Environment
        │
   ┌────┴─────┐
   ▼          ▼
 Backend    Integration
   │
   ▼
PostgreSQL / External Services
```

Конкретная технология хранения секретов настоящим ADR не фиксируется.

## 3.3. Разделение конфигурации и секретов

Конфигурационные параметры и секреты должны рассматриваться отдельно.

К конфигурации могут относиться:

- URL сервисов;
    
- режим работы приложения;
    
- идентификаторы окружения;
    
- настройки функций;
    
- параметры, не содержащие конфиденциальной информации.
    

К секретам относятся значения, предоставляющие доступ, возможность аутентификации, подписи или расшифровки.

Секрет не должен превращаться в обычный конфигурационный параметр только ради удобства разработки.

## 3.4. Использование Backend

Backend получает необходимые секреты из защищённого источника во время запуска или выполнения приложения.

Секреты не должны передаваться во Frontend без архитектурной необходимости.

Особенно запрещается передавать клиентскому приложению:

- пароли;
    
- database credentials;
    
- private keys;
    
- внутренние API secrets;
    
- секреты интеграций;
    
- секреты платёжных провайдеров;
    
- секреты серверной аутентификации.
    

## 3.5. Frontend

Vue 3 Frontend считается недоверенной клиентской средой.

Любое значение, попавшее в Frontend, потенциально доступно пользователю.

Поэтому секрет, необходимый исключительно Backend, не должен попадать в клиентский JavaScript, публичную конфигурацию или API-ответ.

Публичные идентификаторы и параметры, специально предназначенные для клиента, не считаются серверными секретами.

## 3.6. Интеграции

Для каждой внешней интеграции секреты должны храниться отдельно от бизнес-данных.

Например:

```
Payment Provider
      │
      └── API credentials / signing secret

Delivery Provider
      │
      └── API credentials / integration secret

ERP / WMS
      │
      └── Integration credentials
```

Сервис интеграции получает только те секреты, которые необходимы для выполнения соответствующей операции.

## 3.7. Принцип минимальных привилегий

Доступ к секрету предоставляется только компоненту или процессу, которому он необходим.

Не допускается использование одного общего секрета для всех подсистем без архитектурной необходимости.

По возможности должны использоваться отдельные учетные данные для:

- разных окружений;
    
- разных внешних систем;
    
- разных сервисных операций;
    
- разных технических компонентов.
    

## 3.8. Жизненный цикл секрета

Секрет должен иметь управляемый жизненный цикл:

```
Создание
   ↓
Хранение
   ↓
Использование
   ↓
Ротация
   ↓
Отзыв
   ↓
Удаление
```

Компрометация секрета должна приводить к возможности его отзыва и замены.

Механизм и периодичность ротации зависят от типа секрета и определяются отдельными техническими решениями.

## 3.9. Логи и мониторинг

Секреты не должны попадать в:

- application logs;
    
- error messages;
    
- audit records;
    
- API responses;
    
- telemetry;
    
- диагностические сообщения.
    

При необходимости регистрации операции должен сохраняться факт события, но не само секретное значение.

Ошибки должны маскировать конфиденциальные параметры.

## 3.10. Репозиторий исходного кода

Секреты запрещается помещать в:

- исходный код;
    
- Git history;
    
- конфигурационные файлы, предназначенные для публикации;
    
- документацию;
    
- тестовые данные production;
    
- публичные issue и другие открытые артефакты.
    

Локальные файлы разработки, содержащие секреты, должны быть исключены из контроля версий.

## 3.11. Резервное копирование

Секреты и резервные копии данных должны рассматриваться как разные категории защищаемых ресурсов.

Резервная копия не должна автоматически становиться способом распространения секретов.

Если резервирование секретов необходимо для восстановления системы, должен использоваться отдельный защищённый механизм.

# 4. Правила

1. Секреты не хранятся в исходном коде.
    
2. Секреты не должны попадать в публичный репозиторий.
    
3. Production-секреты не должны использоваться в других окружениях без необходимости.
    
4. Backend является основным потребителем серверных секретов.
    
5. Frontend не считается доверенной средой хранения секретов.
    
6. Серверные секреты не передаются Frontend.
    
7. Секреты внешних интеграций хранятся отдельно от бизнес-данных.
    
8. Доступ к секретам предоставляется по принципу минимальных привилегий.
    
9. Разные интеграции по возможности используют разные учетные данные.
    
10. Секрет должен иметь управляемый жизненный цикл.
    
11. Компрометированный секрет должен иметь возможность отзыва и замены.
    
12. Секреты не записываются в логи.
    
13. Секреты не должны присутствовать в API-ответах и диагностических сообщениях.
    
14. Ошибки и технические сообщения не должны раскрывать секретные значения.
    
15. Локальные файлы с секретами должны исключаться из контроля версий.
    
16. Секреты не должны включаться в архитектурную документацию в открытом виде.
    
17. Резервное копирование секретов выполняется только при наличии обоснованной необходимости и отдельного защищённого механизма.
    
18. Конкретная технология Secrets Management определяется отдельным техническим решением.
    
19. Конкретные алгоритмы ротации и сроки действия секретов определяются отдельными решениями.
    
20. Ответственность за доступ к секрету должна соответствовать ответственности компонента, использующего этот секрет.
