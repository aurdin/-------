# 1. Назначение

Настоящий документ определяет модель развёртывания системы **SmEl (Smart Electric)**.

Документ устанавливает логическое размещение основных программных компонентов системы, сред выполнения и каналов взаимодействия между ними.

AMD-051 развивает технологическую модель **AMD-050**.

# 2. Область применения

Модель развёртывания распространяется на:

- пользовательский Frontend;
    
- серверный Backend;
    
- REST API;
    
- базу данных;
    
- административный интерфейс;
    
- интеграционный контур;
    
- внешние системы;
    
- среды разработки, тестирования и эксплуатации.
    

Документ определяет логическую структуру развёртывания и не фиксирует конкретного поставщика инфраструктуры.

# 3. Принцип развёртывания

SmEl разделяется на несколько логических уровней:

**Клиент → Frontend → Backend / API → PostgreSQL**

Внешние взаимодействия:

**Backend → Integration Layer → External Systems**

Административный доступ:

**Administrator → Admin Interface → Backend → PostgreSQL**

# 4. Основные узлы развёртывания

Модель включает следующие логические узлы:

- клиентское устройство;
    
- Frontend;
    
- Backend;
    
- API;
    
- PostgreSQL;
    
- административный интерфейс;
    
- интеграционный слой;
    
- внешние системы.
    

Один физический сервер может содержать несколько логических узлов.

Логическое разделение не требует обязательного физического разделения.

# 5. Клиентское устройство

Клиентское устройство представляет браузер или иной пользовательский клиент, через который осуществляется доступ к интернет-магазину.

На клиентском устройстве выполняется Frontend-приложение.

Клиентское устройство не должно иметь прямого доступа к:

- PostgreSQL;
    
- внутренним серверным компонентам;
    
- административным данным;
    
- внутренним интерфейсам интеграций.
    

# 6. Frontend

Frontend развёртывается как пользовательская часть SmEl.

Технологическая основа:

- Vue 3;
    
- TypeScript;
    
- Pinia;
    
- Vue Router;
    
- Tailwind CSS.
    

Frontend предоставляет пользовательский интерфейс и взаимодействует с Backend через REST API.

# 7. Backend

Backend является центральным серверным узлом системы.

На Backend размещаются:

- бизнес-логика;
    
- серверные функциональные компоненты;
    
- обработка API-запросов;
    
- работа с данными;
    
- управление корзиной;
    
- Checkout;
    
- заказы;
    
- оплата;
    
- доставка;
    
- интеграционный слой.
    

Backend должен иметь доступ к PostgreSQL.

# 8. REST API

REST API является логической точкой взаимодействия Frontend с Backend.

API реализуется средствами Django REST Framework.

Поток взаимодействия:

**Frontend → REST API → Backend**

API не должен предоставлять клиенту прямой доступ к базе данных.

# 9. PostgreSQL

PostgreSQL является узлом постоянного хранения данных.

В PostgreSQL размещаются данные:

- каталога;
    
- товаров;
    
- категорий;
    
- характеристик;
    
- изображений;
    
- цен;
    
- скидок;
    
- акций;
    
- наличия;
    
- клиентов;
    
- корзин;
    
- Checkout;
    
- заказов;
    
- оплаты;
    
- доставки.
    

Доступ к PostgreSQL осуществляется серверной частью.

# 10. Административный интерфейс

Административный интерфейс реализуется средствами Django Admin.

Администратор взаимодействует с системой через административный интерфейс:

**Administrator → Django Admin → Backend → PostgreSQL**

Административный интерфейс не должен предоставлять прямой доступ к базе данных.

# 11. Интеграционный слой

Интеграционный слой располагается на стороне Backend.

Он обеспечивает взаимодействие с внешними системами.

Основной поток:

**Backend → Integration Layer → External System**

Интеграционный слой отвечает за:

- вызов внешних сервисов;
    
- преобразование данных;
    
- обработку ответов;
    
- обработку ошибок;
    
- повторные операции;
    
- регистрацию значимых операций.
    

# 12. Внешние системы

Внешние системы находятся за пределами технологической границы SmEl.

К ним могут относиться:

- платёжные системы;
    
- службы доставки;
    
- источники товарных данных;
    
- системы учёта наличия;
    
- сервисы уведомлений;
    
- другие внешние сервисы.
    

Конкретный состав определяется **AMD-060 — Интеграционная модель SmEl**.

# 13. Основной поток взаимодействия

Основной пользовательский поток:

**Client Device → Frontend → REST API → Backend → PostgreSQL**

Ответ возвращается по обратному направлению:

**PostgreSQL → Backend → REST API → Frontend → Client Device**

# 14. Поток административного управления

Административный поток:

**Administrator → Django Admin → Backend → PostgreSQL**

Результат операции возвращается через административный интерфейс.

Административные операции должны выполняться с соблюдением серверных бизнес-правил.

# 15. Поток внешней интеграции

Для взаимодействия с внешними системами:

**Backend → Integration Layer → External System**

Ответ:

**External System → Integration Layer → Backend**

После получения результата Backend определяет дальнейшее изменение состояния соответствующей сущности.

# 16. Среды развёртывания

Для SmEl предусматриваются следующие логические среды:

- **Development** — разработка;
    
- **Test** — тестирование;
    
- **Production** — эксплуатация.
    

Среды должны быть логически разделены.

Данные Production не должны использоваться в Development или Test без соответствующего обезличивания и разрешения.

# 17. Среда Development

Development предназначена для разработки и локальной проверки системы.

В среде могут размещаться:

- Frontend;
    
- Backend;
    
- PostgreSQL;
    
- инструменты разработки;
    
- тестовые внешние интеграции.
    

Конфигурация Development не должна рассматриваться как Production-конфигурация.

# 18. Среда Test

Test предназначена для проверки:

- функциональности;
    
- интеграций;
    
- взаимодействия компонентов;
    
- корректности API;
    
- бизнес-правил;
    
- изменений данных.
    

Test должна использовать отдельные данные и конфигурацию.

# 19. Среда Production

Production предназначена для реальной эксплуатации интернет-магазина.

В Production размещаются необходимые для работы:

- Frontend;
    
- Backend;
    
- API;
    
- PostgreSQL;
    
- интеграционный контур.
    

Конкретное физическое размещение определяется инфраструктурой проекта.

# 20. Логическое разделение узлов

Архитектура должна позволять независимо рассматривать:

- Frontend;
    
- Backend;
    
- PostgreSQL;
    
- Integration Layer.
    

При этом начальная реализация может размещать несколько компонентов на одном физическом узле.

Логическая архитектурная граница важнее физического количества серверов.

# 21. Сетевые границы

В модели развёртывания выделяются следующие логические границы:

**Публичная граница**

Клиент ↔ Frontend / API

**Серверная граница**

API ↔ Backend

**Граница хранения**

Backend ↔ PostgreSQL

**Интеграционная граница**

Backend ↔ External Systems

Конкретные сетевые правила и механизмы защиты определяются в **AMD-070 — Модели безопасности SmEl**.

# 22. Доступ к данным

Доступ к PostgreSQL разрешается только серверным компонентам.

Frontend:

**не имеет прямого доступа к PostgreSQL.**

Внешние системы:

**не имеют прямого доступа к PostgreSQL.**

Администратор:

**не имеет прямого доступа к PostgreSQL в рамках штатной работы системы.**

Доступ к данным осуществляется через соответствующие программные интерфейсы.

# 23. Развёртывание Frontend и Backend

Frontend и Backend являются независимо рассматриваемыми частями системы.

Frontend может развёртываться отдельно от Backend.

Backend может развёртываться отдельно от PostgreSQL.

Такое разделение обеспечивает возможность дальнейшего масштабирования и изменения инфраструктуры без изменения логической архитектуры системы.

# 24. Масштабирование

Модель развёртывания должна допускать масштабирование серверных компонентов.

В первую очередь потенциально масштабируются:

- Frontend;
    
- Backend/API;
    
- отдельные интеграционные процессы.
    

PostgreSQL масштабируется в соответствии с возможностями выбранной конфигурации и требованиями проекта.

Конкретная стратегия масштабирования определяется после появления количественных нефункциональных требований.

# 25. Отказоустойчивость

Развёртывание должно обеспечивать возможность повышения устойчивости критических компонентов.

Критическими являются:

- Backend;
    
- API;
    
- PostgreSQL;
    
- интеграционный контур.
    

Конкретные механизмы:

- резервирование;
    
- репликация;
    
- автоматическое восстановление;
    
- балансировка нагрузки
    

определяются на инфраструктурном уровне.

# 26. Резервное копирование и восстановление

Для Production должны предусматриваться:

- резервное копирование критических данных;
    
- контроль успешности резервного копирования;
    
- возможность восстановления;
    
- проверка процедур восстановления.
    

Параметры RPO и RTO должны быть определены на основании количественных нефункциональных требований.

# 27. Конфигурация среды

Каждая среда должна иметь собственную конфигурацию.

Конфигурационные параметры не должны смешиваться между средами.

Секретные параметры не должны храниться в исходном коде приложения.

Конкретный механизм управления конфигурацией и секретами определяется технологической и инфраструктурной реализацией.

# 28. Мониторинг развёртывания

Production должен иметь возможность контролировать состояние основных узлов:

- Frontend;
    
- Backend;
    
- API;
    
- PostgreSQL;
    
- интеграций.
    

Контролироваться могут:

- доступность;
    
- ошибки;
    
- загрузка;
    
- состояние процессов;
    
- состояние базы данных;
    
- состояние интеграций.
    

Детальная модель мониторинга может быть определена в последующих архитектурных решениях.

# 29. Обновление системы

Обновление компонентов должно выполняться контролируемо.

Необходимо учитывать:

- совместимость версий;
    
- изменения структуры данных;
    
- миграции;
    
- возможность отката;
    
- влияние на пользовательские операции.
    

Особое внимание должно уделяться изменениям Backend и PostgreSQL.

# 30. Трассируемость развёртывания

Для Production должна обеспечиваться возможность определить:

- версию Frontend;
    
- версию Backend;
    
- версию API;
    
- версию структуры данных;
    
- конфигурацию среды;
    
- состояние интеграций.
    

Это необходимо для диагностики и восстановления после ошибок.

# 31. Связь с технологической моделью

AMD-051 реализует технологические компоненты AMD-050:

**Vue 3 → Frontend Node**

**Django / DRF → Backend Node**

**PostgreSQL → Database Node**

**Django Admin → Administrative Interface**

**Integration Layer → Integration Node**

Развёртывание сохраняет технологические границы AMD-050.

# 32. Связь с моделью взаимодействий

AMD-051 реализует каналы взаимодействия AMD-041:

**Client → Frontend → API → Backend**

**Backend → PostgreSQL**

**Backend → Integration Layer → External System**

**Administrator → Django Admin → Backend**

# 33. Связь с требованиями

AMD-051 основан на:

- **REQ-030 — Нефункциональные требования SmEl**;
    
- **REQ-040 — Интеграционные требования SmEl**;
    
- **REQ-050 — Ограничения и бизнес-правила SmEl**.
    

Также учитываются:

- **REQ-001 — Бизнес-требования SmEl**;
    
- **REQ-010 — Функциональные требования SmEl**;
    
- **REQ-020 — Информационные требования SmEl**.
    

# 34. Связь с архитектурными решениями

AMD-051 должен соответствовать:

- **STD-001 — Технологический стек SmEl**;
    
- **ADR-001–ADR-020 — Архитектурные решения SmEl**.
    

Инфраструктурные решения, которые потребуют отдельного архитектурного обоснования, должны фиксироваться в ADR.

# 35. Граница модели развёртывания

AMD-051 определяет логическое размещение компонентов и основные среды выполнения.

Документ не определяет:

- конкретного облачного провайдера;
    
- конкретные серверы;
    
- IP-адреса;
    
- DNS;
    
- балансировщики;
    
- контейнерную платформу;
    
- Kubernetes;
    
- конкретную схему резервирования;
    
- конкретные параметры виртуальных машин.
    

Эти вопросы могут быть определены отдельными техническими и архитектурными решениями.

# 36. Основание для последующих моделей

AMD-051 является основанием для:

- **AMD-060 — Интеграционной модели SmEl**;
    
- **AMD-070 — Модели безопасности SmEl**.
    

Также модель может использоваться при формировании инфраструктурных ADR.

# 37. Заключительные положения

AMD-051 определяет модель развёртывания SmEl и устанавливает логическое размещение основных компонентов системы.

Модель сохраняет основные архитектурные границы:

**Client → Frontend → API → Backend → PostgreSQL**

и

**Backend → Integration Layer → External Systems**.

Физическая инфраструктура может изменяться без изменения логической модели при сохранении установленных границ ответственности и взаимодействия компонентов.

На основании AMD-051 следующим специализированным уровнем является **AMD-060 — Интеграционная модель SmEl**, определяющая внешние системы, направления обмена и интеграционные взаимодействия.
