# 1. Назначение

Настоящий документ определяет модель взаимодействий программных компонентов системы **SmEl (Smart Electric)**.

Документ устанавливает основные последовательности взаимодействия компонентов при выполнении пользовательских и системных операций.

AMD-041 развивает компонентную модель **AMD-040** и уточняет взаимодействия, определённые функциональной моделью **AMD-020** и информационной моделью **AMD-030**.

# 2. Область применения

Модель взаимодействий распространяется на основные функциональные процессы интернет-магазина SmEl:

- работу с каталогом;
    
- просмотр товара;
    
- ценообразование;
    
- управление корзиной;
    
- проверку актуальности;
    
- Checkout;
    
- создание заказа;
    
- оплату;
    
- доставку;
    
- работу клиента;
    
- административное управление;
    
- интеграции с внешними системами.
    

Документ описывает логическое взаимодействие компонентов и не определяет конкретные протоколы и технологии реализации.

# 3. Основной принцип взаимодействия

Взаимодействие компонентов должно осуществляться через определённые архитектурные границы.

Клиентское приложение взаимодействует с серверной частью через API.

Серверная часть выполняет бизнес-логику и обеспечивает контроль критических операций.

Компоненты не должны обходить установленные границы ответственности других компонентов.

# 4. Общая схема взаимодействия

Основной поток взаимодействия имеет вид:

**Клиентское приложение → API → Функциональный компонент → Компонент данных**

При необходимости взаимодействия с внешней системой:

**Функциональный компонент → Компонент интеграций → Внешняя система**

Результат операции возвращается по обратному пути к инициатору.

# 5. Взаимодействие с каталогом

При открытии каталога взаимодействие выполняется следующим образом:

1. Клиентское приложение запрашивает каталог.
    
2. API принимает запрос.
    
3. Компонент каталога определяет необходимые данные.
    
4. Компонент данных предоставляет актуальные данные каталога.
    
5. Компонент каталога формирует результат.
    
6. API возвращает данные клиентскому приложению.
    

# 6. Взаимодействие при просмотре товара

При открытии карточки товара:

1. Клиентское приложение запрашивает товар.
    
2. API передаёт запрос компоненту товара.
    
3. Компонент товара получает данные Product.
    
4. При необходимости получает характеристики и изображения.
    
5. Компонент ценообразования определяет актуальные коммерческие условия.
    
6. Информация о доступности получает актуальное значение.
    
7. API возвращает результат клиентскому приложению.
    

# 7. Взаимодействие с ценообразованием

При определении стоимости:

1. Функциональный компонент передаёт данные о товаре компоненту ценообразования.
    
2. Компонент ценообразования получает актуальные Price, Discount и Promotion.
    
3. Проверяет применимость коммерческих условий.
    
4. Рассчитывает итоговую стоимость.
    
5. Возвращает результат инициировавшему компоненту.
    

Клиентское приложение не должно самостоятельно определять окончательную стоимость товара.

# 8. Добавление товара в корзину

При добавлении товара:

1. Клиентское приложение передаёт запрос через API.
    
2. API передаёт операцию компоненту корзины.
    
3. Компонент корзины определяет текущую корзину.
    
4. Проверяется существование товара.
    
5. Проверяется допустимость добавляемого количества.
    
6. Создаётся или изменяется Cart Item.
    
7. Компонент корзины сохраняет изменения.
    
8. Актуальное состояние корзины возвращается клиенту.
    

Добавление товара в корзину не означает окончательной фиксации его цены.

# 9. Изменение корзины

При изменении количества:

1. Клиент передаёт новое количество.
    
2. API передаёт операцию компоненту корзины.
    
3. Компонент корзины проверяет допустимость изменения.
    
4. Cart Item обновляется.
    
5. Состояние корзины сохраняется.
    
6. Клиент получает актуальное состояние корзины.
    

При необходимости последующая проверка актуальности выполняется отдельно.

# 10. Проверка актуальности корзины

Перед Checkout выполняется проверка:

1. Компонент Checkout инициирует проверку.
    
2. Компонент проверки актуальности получает Cart и Cart Item.
    
3. Проверяется существование товара.
    
4. Проверяется наличие.
    
5. Проверяется количество.
    
6. Проверяется цена.
    
7. Проверяются скидки и акции.
    
8. Проверяется срок нахождения позиции в корзине.
    
9. Проверяются иные условия продажи.
    
10. Формируется результат проверки.
    

Результат должен однозначно определить возможность продолжения оформления.

# 11. Обработка неактуальной корзины

Если одна или несколько позиций неактуальны:

1. Проверка актуальности возвращает информацию о проблемных позициях.
    
2. Checkout не должен создавать заказ до устранения критических несоответствий.
    
3. Клиенту передаётся информация о необходимости изменения корзины.
    
4. После изменения корзины проверка выполняется повторно.
    

Таким образом, неактуальная корзина не должна напрямую переходить в заказ.

# 12. Взаимодействие Checkout

Checkout координирует подготовку заказа.

В рамках Checkout взаимодействуют:

- корзина;
    
- проверка актуальности;
    
- ценообразование;
    
- клиент;
    
- доставка;
    
- оплата;
    
- заказ.
    

Основной поток:

**Cart → Проверка актуальности → Ценообразование → Доставка / Оплата → Order**

# 13. Выбор доставки

При выборе доставки:

1. Checkout запрашивает доступные способы доставки.
    
2. Компонент доставки определяет доступные варианты.
    
3. При необходимости компонент интеграций получает данные внешней службы.
    
4. Определяется стоимость доставки.
    
5. Выбранный способ и данные получения передаются обратно в Checkout.
    
6. Данные сохраняются как часть формируемого заказа.
    

# 14. Выбор оплаты

При выборе оплаты:

1. Checkout запрашивает доступные способы оплаты.
    
2. Компонент оплаты предоставляет доступные варианты.
    
3. Клиент выбирает способ оплаты.
    
4. Выбор передаётся компоненту оплаты.
    
5. Информация связывается с текущим Checkout.
    
6. При необходимости создаётся платёжная операция через компонент интеграций.
    

# 15. Создание заказа

Создание заказа выполняется только после успешной проверки актуальности.

Основной поток:

**Checkout → Проверка актуальности → Order**

При создании заказа компонент заказов:

- получает актуальный состав;
    
- формирует Order;
    
- формирует Order Item;
    
- фиксирует стоимость;
    
- фиксирует скидки и акции;
    
- фиксирует данные клиента;
    
- фиксирует доставку;
    
- фиксирует способ оплаты;
    
- сохраняет исторические данные.
    

После успешного создания заказ становится самостоятельной сущностью.

# 16. Взаимодействие с оплатой после создания заказа

После создания заказа:

1. Компонент заказов передаёт данные компоненту оплаты.
    
2. Компонент оплаты инициирует платёжную операцию, если это предусмотрено выбранным способом.
    
3. При необходимости компонент интеграций взаимодействует с платёжной системой.
    
4. Результат операции возвращается компоненту оплаты.
    
5. Состояние оплаты связывается с заказом.
    
6. Изменение состояния оплаты может приводить к изменению соответствующего состояния заказа.
    

# 17. Взаимодействие с доставкой после создания заказа

После создания заказа:

1. Компонент заказов передаёт данные доставки компоненту доставки.
    
2. Компонент доставки формирует или активирует операцию доставки.
    
3. При необходимости выполняется обращение к внешней службе через компонент интеграций.
    
4. Полученный результат сохраняется.
    
5. Состояние доставки связывается с заказом.
    

# 18. Взаимодействие с клиентом

Компонент клиентов взаимодействует с:

- корзиной;
    
- Checkout;
    
- заказами;
    
- аутентификацией.
    

Для авторизованного клиента:

**Customer → Cart**

**Customer → Order**

Корзина авторизованного клиента должна быть доступна между сеансами.

Для гостя идентификация корзины выполняется в рамках текущей сессии.

# 19. Взаимодействие административного компонента

Административный компонент взаимодействует с серверными компонентами управления данными.

Основные операции:

- создание;
    
- изменение;
    
- удаление;
    
- просмотр;
    
- управление состояниями.
    

Изменения административных данных должны проходить через установленные бизнес-правила.

Особенно контролируются изменения:

- цены;
    
- скидок;
    
- акций;
    
- наличия;
    
- товаров;
    
- заказов.
    

# 20. Взаимодействие с внешними системами

Внешние системы не должны взаимодействовать непосредственно с внутренними компонентами бизнес-логики.

Взаимодействие осуществляется через компонент интеграций:

**SmEl Component → Integration Component → External System**

Компонент интеграций отвечает за преобразование внешнего представления данных во внутреннее и обратно.

# 21. Обработка ошибок

Ошибка взаимодействия должна:

1. быть обнаружена компонентом, выполняющим операцию;
    
2. классифицироваться;
    
3. при необходимости журналироваться;
    
4. возвращаться инициировавшему компоненту;
    
5. преобразовываться API в соответствующий ответ клиенту.
    

Ошибка внешней системы не должна приводить к неконтролируемому изменению внутренних данных.

# 22. Повторное выполнение операций

Для операций, которые могут быть повторены вследствие сетевых или внешних ошибок, должна обеспечиваться защита от некорректного дублирования.

Особенно это относится к:

- созданию заказа;
    
- оплате;
    
- операциям доставки;
    
- интеграционным операциям.
    

Повторная обработка не должна приводить к созданию нескольких логически одинаковых операций.

# 23. Синхронное и асинхронное взаимодействие

Синхронное взаимодействие применяется для операций, результат которых необходим непосредственно инициатору.

Асинхронное взаимодействие может применяться для:

- внешних уведомлений;
    
- длительных интеграционных операций;
    
- обновления состояний;
    
- фоновой синхронизации;
    
- операций, не требующих немедленного результата.
    

Конкретный механизм взаимодействия определяется технологической моделью.

# 24. Последовательность основного бизнес-процесса

Основная последовательность взаимодействий:

**Клиентское приложение → API → Каталог → Товар**

**Клиентское приложение → API → Корзина**

**Checkout → Проверка актуальности → Ценообразование**

**Checkout → Доставка**

**Checkout → Оплата**

**Checkout → Заказ**

**Заказ → Оплата → Интеграция → Платёжная система**

**Заказ → Доставка → Интеграция → Служба доставки**

Эта последовательность соответствует основному функциональному контуру SmEl.

# 25. Правила взаимодействия компонентов

Компоненты должны соблюдать следующие правила:

1. взаимодействовать только через определённые интерфейсы;
    
2. не обходить ответственность других компонентов;
    
3. не дублировать бизнес-логику;
    
4. использовать актуальные данные;
    
5. обеспечивать целостность операций;
    
6. фиксировать критические изменения;
    
7. корректно обрабатывать ошибки;
    
8. обеспечивать трассируемость значимых операций.
    

# 26. Серверная ответственность

Серверная часть является контролирующей стороной взаимодействия.

На сервере должны выполняться:

- проверка прав доступа;
    
- бизнес-правила;
    
- расчёт стоимости;
    
- проверка корзины;
    
- создание заказа;
    
- изменение критических состояний;
    
- обработка результатов оплаты;
    
- обработка результатов доставки.
    

Клиентское приложение не должно иметь возможности обойти эти проверки.

# 27. Связь с информационной моделью

Взаимодействия компонентов приводят к изменению или получению информационных объектов AMD-030.

Основные преобразования:

**Product → Cart Item**

**Cart Item → Checkout**

**Checkout → Order Item**

**Order Item → Order**

При этом Checkout является промежуточным состоянием, а Order — исторически зафиксированным результатом оформления.

# 28. Связь с компонентной моделью

AMD-041 реализует взаимодействия компонентов, определённых AMD-040.

Основными участниками являются:

- клиентское приложение;
    
- API;
    
- каталог;
    
- товар;
    
- ценообразование;
    
- корзина;
    
- проверка актуальности;
    
- Checkout;
    
- заказ;
    
- оплата;
    
- доставка;
    
- клиент;
    
- административный компонент;

- компонент данных.

# 30. Связь с архитектурными решениями

Модель взаимодействий должна соответствовать принятым архитектурным решениям:

- **ADR-001–ADR-020 — Архитектурные решения SmEl**.
    

При появлении новых архитектурных решений соответствующие взаимодействия должны быть актуализированы.

# 31. Граница модели взаимодействий

AMD-041 определяет логические взаимодействия компонентов.

Документ не определяет:

- конкретные HTTP-методы;
    
- URL API;
    
- классы и функции;
    
- структуру программного кода;
    
- конкретные очереди сообщений;
    
- конкретные механизмы интеграции;
    
- физическое размещение компонентов.
    

Эти вопросы относятся к технологической и последующим архитектурным моделям.

# 32. Основание для последующих моделей

AMD-041 является основанием для разработки:

- **AMD-050 — Технологическая модель SmEl**;
    
- **AMD-051 — Модель развёртывания SmEl**;
    
- **AMD-060 — Интеграционная модель SmEl**;
    
- **AMD-070 — Модель безопасности SmEl**.
    

# 33. Заключительные положения

AMD-041 определяет логическую модель взаимодействий компонентов SmEl.

Модель обеспечивает согласованность между функциональной моделью AMD-020, информационной моделью AMD-030 и компонентной моделью AMD-040.

Ключевым принципом является централизованный контроль бизнес-логики серверной частью и прохождение критических операций через установленные компонентные границы.

На основании AMD-041 должна быть разработана **AMD-050 — Технологическая модель SmEl**, связывающая архитектурные компоненты с конкретным технологическим стеком проекта.
