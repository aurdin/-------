# 1. Назначение

Настоящий документ определяет интеграционную модель системы **SmEl (Smart Electric)**.

Документ устанавливает внешние системы, направления обмена данными, логические границы интеграций и основные правила взаимодействия SmEl с внешними системами.

AMD-060 развивает модель взаимодействий **AMD-041** и технологическую модель **AMD-050**.

# 2. Область применения

Интеграционная модель распространяется на взаимодействие SmEl с:

- платёжными системами;
    
- службами доставки;
    
- источниками товарных данных;
    
- системами учёта наличия;
    
- сервисами уведомлений;
    
- иными внешними сервисами.
    

Внутреннее взаимодействие компонентов SmEl определяется AMD-041 и не является самостоятельной внешней интеграцией.

# 3. Принцип интеграции

Все внешние взаимодействия должны проходить через определённую интеграционную границу SmEl.

Основной принцип:

**SmEl Backend → Integration Layer → External System**

Внешняя система не должна напрямую обращаться к внутренним компонентам SmEl, если такое взаимодействие отдельно не предусмотрено архитектурой.

# 4. Интеграционная граница

Интеграционная граница разделяет:

**Внутренний контур SmEl**

и

**Внешние системы**.

Внутренний контур включает:

- Frontend;
    
- API;
    
- Backend;
    
- компонент данных;
    
- бизнес-компоненты.
    

Внешний контур включает системы и сервисы, не являющиеся частью SmEl.

# 5. Основные интеграции

В текущей архитектуре предусматриваются следующие интеграционные направления:

|Интеграция|Направление|Назначение|
|---|---|---|
|Платёжная система|Двунаправленное|Оплата заказа|
|Служба доставки|Двунаправленное|Организация доставки|
|Источник товарных данных|Входящее|Получение данных товаров|
|Система учёта наличия|Двунаправленное или входящее|Получение актуального наличия|
|Сервис уведомлений|Исходящее|Уведомление клиента|
|Иные сервисы|По необходимости|Дополнительные функции|

Конкретный состав внешних систем может быть расширен.

# 6. Платёжная интеграция

Платёжная интеграция обеспечивает выполнение операций оплаты.

Основной поток:

**Order → Payment Component → Integration Layer → Payment System**

Результат:

**Payment System → Integration Layer → Payment Component → Order**

Передаваемые данные могут включать:

- идентификатор заказа;
    
- сумму;
    
- идентификатор платежа;
    
- статус операции;
    
- технические данные, необходимые для обработки платежа.
    

Конкретный состав данных определяется выбранной платёжной системой.

# 7. Принцип обработки оплаты

SmEl не должен считать оплату успешной только на основании клиентского сообщения.

Результат оплаты должен подтверждаться серверной частью и, если предусмотрено интеграцией, внешней платёжной системой.

После подтверждения Backend изменяет состояние оплаты и связанные состояния заказа.

# 8. Интеграция доставки

Интеграция доставки обеспечивает передачу данных заказа внешней службе доставки.

Основной поток:

**Order → Delivery Component → Integration Layer → Delivery Service**

Обратный поток:

**Delivery Service → Integration Layer → Delivery Component → Order**

Могут передаваться:

- данные заказа;
    
- данные получателя;
    
- адрес или пункт получения;
    
- состав отправления;
    
- вес или иные параметры, если они необходимы;
    
- стоимость доставки;
    
- идентификатор доставки.
    

# 9. Состояние доставки

Внешняя служба доставки может передавать изменения состояния доставки.

Backend должен проверять полученные данные перед изменением внутреннего состояния.

Внутреннее состояние доставки не должно изменяться неконтролируемым прямым обращением внешней системы к базе данных.

# 10. Источник товарных данных

SmEl может взаимодействовать с внешними источниками товарных данных.

Такая интеграция может использоваться для получения:

- артикулов;
    
- наименований;
    
- описаний;
    
- характеристик;
    
- изображений;
    
- категорий;
    
- иных данных товара.
    

Полученные данные должны проходить обработку и проверку перед использованием во внутреннем каталоге.

# 11. Синхронизация каталога

При синхронизации с внешним источником:

**External Product Source → Integration Layer → Backend → PostgreSQL**

SmEl должен определить:

- идентификатор внешнего объекта;
    
- соответствующий внутренний объект;
    
- правила создания;
    
- правила обновления;
    
- правила удаления или деактивации;
    
- обработку конфликтов.
    

Внешний источник не должен автоматически изменять внутренние данные без установленных правил синхронизации.

# 12. Интеграция с системой наличия

Система учёта наличия может предоставлять данные о доступности товаров.

Основной поток:

**Stock System → Integration Layer → Backend → Stock**

При необходимости SmEl может передавать внешней системе данные об изменении состояния товара или заказа.

Конкретное направление зависит от выбранной системы учёта.

# 13. Актуальность наличия

Полученные данные о наличии должны учитываться при:

- отображении доступности товара;
    
- добавлении товара в корзину;
    
- изменении количества;
    
- проверке актуальности корзины;
    
- Checkout;
    
- создании заказа.
    

Перед созданием заказа Backend должен использовать актуальное значение наличия.

# 14. Сервис уведомлений

SmEl может взаимодействовать с внешними сервисами уведомлений.

Возможные каналы:

- электронная почта;
    
- SMS;
    
- push-уведомления;
    
- иные каналы.
    

Основной поток:

**Backend → Integration Layer → Notification Service**

Сервис уведомлений не должен определять состояние заказа или оплаты.

# 15. Внешняя система как зависимость

Внешняя система рассматривается как зависимость SmEl.

Отказ внешней системы не должен приводить к неконтролируемому нарушению внутренней целостности данных.

SmEl должен уметь определить:

- факт недоступности;
    
- результат последней операции;
    
- необходимость повторения;
    
- необходимость ручной обработки.
    

# 16. Синхронные интеграции

Синхронное взаимодействие применяется, когда результат внешней операции необходим для продолжения текущей операции.

Примеры:

- получение результата платежной операции;
    
- получение доступного способа доставки;
    
- расчёт стоимости доставки;
    
- получение актуального наличия, если оно необходимо непосредственно перед оформлением.
    

# 17. Асинхронные интеграции

Асинхронное взаимодействие может применяться для операций:

- уведомления;
    
- фоновой синхронизации;
    
- обновления каталога;
    
- получения изменений состояния доставки;
    
- получения результатов длительных внешних операций.
    

Конкретный механизм определяется технологической реализацией.

# 18. Форматы обмена

Формат обмена определяется конкретной внешней системой.

Приоритетным форматом для REST-интеграций является JSON.

При необходимости могут использоваться другие форматы, если они определены внешним интерфейсом.

Внутреннее представление данных SmEl не должно без необходимости зависеть от формата конкретной внешней системы.

# 19. Преобразование данных

Integration Layer отвечает за преобразование внешних данных во внутреннее представление SmEl и обратно.

Принцип:

**External Model ↔ Integration Model ↔ Internal Model**

Это позволяет изолировать бизнес-логику SmEl от особенностей внешнего API.

# 20. Идентификация интеграционных объектов

Для интеграционных объектов должна обеспечиваться возможность сопоставить:

- внутренний идентификатор;
    
- внешний идентификатор;
    
- тип объекта;
    
- источник данных.
    

Особенно это важно для:

- платежей;
    
- доставок;
    
- товаров;
    
- операций синхронизации.
    

# 21. Обработка ошибок

Ошибки внешних систем должны классифицироваться.

Возможные категории:

- временная недоступность;
    
- ошибка сети;
    
- ошибка авторизации;
    
- ошибка формата;
    
- ошибка бизнес-правил внешней системы;
    
- неизвестная ошибка.
    

Для каждой категории должна быть предусмотрена соответствующая обработка.

# 22. Повторные операции

Для операций, допускающих повторение, должна обеспечиваться защита от дублирования.

Особое значение это имеет для:

- платежей;
    
- создания доставки;
    
- передачи заказа;
    
- синхронизации;
    
- уведомлений.
    

Повторный запрос не должен приводить к созданию нескольких одинаковых бизнес-операций.

# 23. Идемпотентность

Для критических интеграционных операций должна использоваться возможность идентифицировать повторный запрос.

Идемпотентность должна обеспечивать безопасное повторение операции после:

- сетевого сбоя;
    
- тайм-аута;
    
- отсутствия ответа;
    
- временной недоступности внешней системы.
    

Конкретный механизм определяется архитектурным решением или технологической реализацией.

# 24. Тайм-ауты

Интеграционные вызовы должны иметь контролируемые ограничения времени ожидания.

Отсутствие ответа внешней системы не должно приводить к бесконечному ожиданию серверной операции.

Количественные значения тайм-аутов определяются технологической реализацией и требованиями соответствующей интеграции.

# 25. Безопасность интеграций

Интеграционные взаимодействия должны обеспечивать:

- аутентификацию;
    
- авторизацию;
    
- защиту передаваемых данных;
    
- безопасное хранение секретов;
    
- контроль доступа;
    
- проверку входящих данных.
    

Конкретные механизмы безопасности определяются **AMD-070 — Моделью безопасности SmEl**.

# 26. Входящие интеграции

Входящие сообщения от внешних систем должны:

1. быть приняты через установленный интерфейс;
    
2. пройти проверку подлинности;
    
3. пройти валидацию;
    
4. быть сопоставлены с внутренним объектом;
    
5. пройти проверку бизнес-правил;
    
6. привести к контролируемому изменению состояния.
    

Внешняя система не должна считаться доверенным источником внутренних бизнес-данных без проверки.

# 27. Исходящие интеграции

Перед отправкой данных внешней системе Backend должен:

- сформировать необходимый набор данных;
    
- проверить его целостность;
    
- выполнить преобразование;
    
- выполнить аутентификацию;
    
- отправить запрос;
    
- обработать результат.
    

Результат должен быть связан с исходной внутренней операцией.

# 28. Трассируемость интеграций

Для значимых интеграционных операций должна обеспечиваться возможность определить:

- внутреннюю операцию;
    
- внешнюю систему;
    
- внешний идентификатор;
    
- время операции;
    
- результат;
    
- состояние;
    
- ошибку, если она произошла;
    
- факт повторного выполнения.
    

Это необходимо для диагностики и восстановления.

# 29. Независимость бизнес-логики

Бизнес-логика SmEl не должна зависеть от конкретной реализации внешней системы.

Замена внешнего поставщика должна по возможности ограничиваться интеграционным слоем и связанными архитектурными решениями.

Внутренние бизнес-сущности не должны напрямую использовать структуры внешнего API.

# 30. Отказ внешней системы

При недоступности внешней системы SmEl должен:

- сохранить внутреннее состояние в допустимом состоянии;
    
- зафиксировать ошибку;
    
- определить возможность повторной операции;
    
- не создавать дублирующие операции;
    
- предоставить информацию для последующей обработки.
    

Если операция является критической и не может быть завершена без внешней системы, Backend должен предотвратить некорректное завершение бизнес-процесса.

# 31. Версионирование интеграций

Интеграционные интерфейсы должны иметь контролируемые версии.

Изменение внешнего API не должно неконтролируемо нарушать работу SmEl.

При несовместимых изменениях должна использоваться отдельная версия интеграции либо иной механизм совместимости.

# 32. Мониторинг интеграций

Для интеграционного контура должны контролироваться:

- доступность внешней системы;
    
- количество операций;
    
- ошибки;
    
- задержки;
    
- повторные операции;
    
- состояние очередей, если они используются;
    
- состояние последних успешных операций.
    

# 33. Связь с компонентной моделью

AMD-060 реализует интеграционный компонент, определённый **AMD-040**.

Основной контур:

**Backend → Integration Layer → External System**

Integration Layer является технологической границей между внутренними компонентами SmEl и внешними системами.

# 34. Связь с моделью взаимодействий

AMD-060 детализирует интеграционные взаимодействия AMD-041:

**Order → Payment → Payment System**

**Order → Delivery → Delivery Service**

**Product / Catalog → Product Source**

**Stock → Stock System**

**Backend → Notification Service**

# 35. Связь с моделью развёртывания

AMD-060 соответствует интеграционному контуру AMD-051:

**Backend → Integration Layer → External Systems**

Внешние системы располагаются за пределами развёртывания SmEl.

Конкретное сетевое размещение и средства защиты определяются инфраструктурными и безопасностными решениями.

# 36. Связь с требованиями

AMD-060 основан на:

- **REQ-040 — Интеграционные требования SmEl**;
    
- **REQ-030 — Нефункциональные требования SmEl**;
    
- **REQ-050 — Ограничения и бизнес-правила SmEl**.
    

Также учитываются:

- **REQ-001 — Бизнес-требования SmEl**;
    
- **REQ-010 — Функциональные требования SmEl**;
    
- **REQ-020 — Информационные требования SmEl**.
    

# 37. Связь с архитектурными решениями

AMD-060 должен соответствовать:

- **STD-001 — Технологический стек SmEl**;
    
- **ADR-001–ADR-020 — Архитектурные решения SmEl**.
    

Конкретные внешние поставщики, протоколы и механизмы интеграции должны фиксироваться соответствующими ADR при необходимости.

# 38. Граница интеграционной модели

AMD-060 определяет логические интеграции и правила взаимодействия с внешними системами.

Документ не фиксирует конкретных поставщиков платёжных систем, служб доставки или иных сервисов, если они ещё не выбраны.

Также документ не определяет:

- конкретные API URL;
    
- ключи и секреты;
    
- конкретные форматы каждого внешнего API;
    
- инфраструктурные параметры;
    
- конкретные механизмы очередей.
    

# 39. Основание для последующих моделей

AMD-060 используется как основание для:

- архитектурных решений по отдельным интеграциям;
    
- технологической реализации внешних интерфейсов;
    
- модели безопасности;
    
- последующих технических спецификаций интеграций.
    

# 40. Заключительные положения

AMD-060 определяет интеграционную модель SmEl и устанавливает границу между внутренней системой и внешними сервисами.

Ключевым принципом является изоляция внутренней бизнес-логики от конкретных внешних систем:

**SmEl Backend → Integration Layer → External System**

Платежи, доставка, товарные данные, наличие и уведомления рассматриваются как отдельные интеграционные направления с контролируемым обменом данными, обработкой ошибок и обеспечением трассируемости.

Следующим специализированным уровнем является **AMD-070 — Модель безопасности SmEl**, определяющая защиту пользователей, API, данных, административного доступа и интеграционных взаимодействий.
