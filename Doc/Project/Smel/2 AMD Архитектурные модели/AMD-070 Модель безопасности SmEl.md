# 1. Назначение

Модель безопасности SmEl определяет архитектурные границы, основные механизмы и принципы обеспечения безопасности системы.

Модель описывает распределение ответственности за безопасность между клиентским приложением, API, серверной частью, данными и внешними системами.

Документ определяет архитектурный уровень безопасности и не заменяет конкретные технологические решения, которые при необходимости фиксируются в ADR.

# 2. Область применения

Модель применяется ко всем основным компонентам SmEl:

- клиентскому приложению;
    
- API;
    
- серверной части;
    
- данным;
    
- административному интерфейсу;
    
- интеграционному слою;
    
- внешним системам;
    
- операциям каталога, ценообразования, корзины, Checkout, заказа, оплаты и доставки.
    

# 3. Архитектурная граница безопасности

Основная граница безопасности проходит между внешним клиентским окружением и серверной частью SmEl.

Основная схема:

**Client → API → Backend → Data**

Внешние системы взаимодействуют с SmEl через интеграционный слой:

**Backend → Integration Layer → External System**

Клиентское приложение не является доверенной средой для выполнения критических бизнес-операций.

# 4. Принцип доверия

Серверная часть является доверенной архитектурной границей для выполнения критических бизнес-операций.

Клиентская часть считается недоверенной с точки зрения:

- передаваемых значений;
    
- идентификаторов объектов;
    
- цен;
    
- количества товаров;
    
- состояния заказа;
    
- параметров оплаты;
    
- параметров доставки;
    
- результатов локальных вычислений.
    

Все критические данные должны проверяться серверной частью.

# 5. Аутентификация

Аутентификация используется для идентификации авторизованного клиента и администратора.

Система должна различать:

- гостевого пользователя;
    
- авторизованного клиента;
    
- администратора.
    

Аутентификация не должна передавать клиентскому приложению полномочия, превышающие права соответствующего пользователя.

# 6. Авторизация

После идентификации пользователя система определяет допустимые операции на основании его роли и контекста доступа.

Авторизация должна выполняться на серверной стороне.

Клиентское приложение не может самостоятельно определять наличие права на выполнение критической операции.

# 7. Гостевой доступ

Гостевой пользователь может выполнять разрешённые операции каталога и формирования корзины без обязательной регистрации.

Гостевой доступ не должен предоставлять возможность:

- получать чужие данные;
    
- изменять чужую корзину;
    
- получать чужие заказы;
    
- выполнять административные операции;
    
- изменять защищённые бизнес-данные.
    

# 8. Авторизованный клиент

Авторизованный клиент получает доступ только к собственным данным и разрешённым операциям.

К собственным данным относятся, в частности:

- профиль клиента;
    
- корзина;
    
- оформленные заказы;
    
- данные доставки, если они связаны с клиентом.
    

Сервер должен проверять принадлежность запрашиваемого объекта текущему клиенту.

# 9. Административный доступ

Административный доступ является отдельным контуром доступа.

Основная схема:

**Administrator → Admin Interface → Backend → Data**

Администратор получает только те возможности, которые соответствуют его административным полномочиям.

Административные операции не должны быть доступны обычному клиенту.

# 10. Безопасность API

API является контролируемой границей взаимодействия между клиентом и серверной частью.

API должно обеспечивать:

- аутентификацию;
    
- авторизацию;
    
- проверку входных данных;
    
- контроль доступа к объектам;
    
- обработку ошибок;
    
- защиту критических операций;
    
- контроль повторных операций.
    

API не должно доверять данным только потому, что они были сформированы клиентским приложением.

# 11. Безопасность клиентского приложения

Frontend отвечает за безопасное представление интерфейса и корректное взаимодействие с API.

Frontend не является источником истины для:

- цен;
    
- скидок;
    
- акций;
    
- остатков;
    
- прав доступа;
    
- итоговой стоимости;
    
- состояния заказа;
    
- результатов проверки актуальности.
    

Защита интерфейсными ограничениями не заменяет серверную авторизацию и валидацию.

# 12. Безопасность серверной части

Backend является основным контуром реализации бизнес-правил и безопасности.

Сервер должен контролировать:

- идентичность пользователя;
    
- права доступа;
    
- корректность входных данных;
    
- допустимость бизнес-операций;
    
- актуальность критических данных;
    
- изменение состояний;
    
- создание заказа;
    
- операции оплаты;
    
- операции доставки;
    
- взаимодействие с внешними системами.
    

# 13. Защита данных

Доступ к данным должен предоставляться только компонентам и пользователям, которым он необходим для выполнения соответствующих функций.

Система должна предотвращать:

- несанкционированное чтение;
    
- несанкционированное изменение;
    
- несанкционированное удаление;
    
- раскрытие данных через API.
    

# 14. Защита персональных данных

Персональные данные клиента должны обрабатываться только в рамках разрешённых бизнес-операций.

Доступ к персональным данным должен ограничиваться принципом минимально необходимого доступа.

API не должно возвращать клиенту персональные данные других пользователей.

# 15. Безопасность корзины

Корзина должна быть связана с соответствующим пользовательским контекстом.

Для авторизованного клиента корзина сохраняется между сеансами.

Для гостя корзина существует только в рамках текущей сессии.

Сервер должен предотвращать доступ одного пользователя к корзине другого пользователя.

# 16. Безопасность Cart Item

Каждый Cart Item должен обрабатываться в контексте конкретной корзины.

Перед изменением или удалением Cart Item сервер должен проверить принадлежность элемента доступной пользователю корзине.

Клиент не должен иметь возможности изменить принадлежность Cart Item другой корзине посредством подмены идентификатора.

# 17. Проверка актуальности

Проверка актуальности является серверной операцией.

Перед переходом к оформлению заказа сервер должен повторно проверить критические данные, включая:

- наличие товара;
    
- актуальную стоимость;
    
- скидки;
    
- акции;
    
- доступность выбранных условий;
    
- другие существенные ограничения.
    

Результат локальной проверки на клиенте не считается доверенным.

# 18. Безопасность Checkout

Checkout является контролируемым сервером промежуточным состоянием между корзиной и заказом.

Система должна исключать возможность создания заказа на основании:

- устаревшей цены;
    
- недоступного товара;
    
- некорректного количества;
    
- неактуальной скидки;
    
- неактуальной акции;
    
- изменённых клиентом критических параметров.
    

# 19. Безопасность заказа

Создание заказа должно выполняться только серверной частью после успешной проверки необходимых условий.

После создания заказа данные, необходимые для сохранения истории операции, должны быть зафиксированы независимо от последующих изменений каталога и коммерческих условий.

Клиент не должен иметь возможности произвольно изменить исторические данные заказа.

# 20. Безопасность оплаты

Платёжные операции должны выполняться через контролируемый серверный контур.

Основная схема:

**Client → Backend → Payment Component → Integration Layer → Payment System**

Клиент не должен самостоятельно определять успешность оплаты.

Результат оплаты должен подтверждаться сервером на основании доверенного взаимодействия с платёжной системой.

# 21. Безопасность доставки

Операции доставки должны выполняться через серверный контур.

Основная схема:

**Order → Delivery Component → Integration Layer → Delivery System**

Клиент не должен иметь возможности самостоятельно установить недействительный статус доставки.

# 22. Безопасность интеграций

Взаимодействие с внешними системами выполняется через Integration Layer.

Внешняя система не должна получать доступ непосредственно к внутренним компонентам или базе данных SmEl.

Для каждой интеграции должны контролироваться:

- источник запроса;
    
- формат данных;
    
- допустимость операции;
    
- ошибки;
    
- повторные запросы;
    
- результаты обработки.
    

# 23. Защита транспортного взаимодействия

Передача данных между компонентами и внешними системами должна выполняться по защищённым каналам в соответствии с требованиями среды эксплуатации.

Особенно должна защищаться передача:

- учётных данных;
    
- токенов доступа;
    
- персональных данных;
    
- платёжных данных;
    
- данных административного доступа;
    
- конфиденциальных интеграционных данных.
    

Конкретные протоколы и параметры защиты определяются на технологическом уровне и при необходимости фиксируются отдельным ADR.

# 24. Секреты и конфигурационные данные

Секретные значения не должны храниться в исходном коде клиентского или серверного приложения.

К секретным данным относятся, в частности:

- ключи доступа;
    
- пароли;
    
- токены;
    
- секреты интеграций;
    
- параметры, позволяющие получить несанкционированный доступ к системам.
    

Способ хранения секретов определяется инфраструктурными и технологическими решениями.

# 25. Валидация входных данных

Все внешние входные данные должны считаться недоверенными.

Сервер должен выполнять проверку:

- типа;
    
- формата;
    
- диапазона;
    
- обязательности;
    
- допустимости значения;
    
- взаимной согласованности параметров.
    

Валидация должна выполняться до выполнения критической бизнес-операции.

# 26. Защита от повторных операций

Критические операции должны быть защищены от неконтролируемого повторного выполнения.

Особое значение это имеет для:

- создания заказа;
    
- платежных операций;
    
- подтверждения оплаты;
    
- операций доставки;
    
- интеграционных запросов.
    

Повторный запрос не должен приводить к неконтролируемому созданию дубликатов или повторному выполнению необратимой операции.

# 27. Управление ошибками

Ошибки не должны приводить к раскрытию внутренних сведений системы.

Внешнему клиенту предоставляется только необходимая информация о результате операции.

Внутренние технические детали должны обрабатываться сервером и журналироваться в соответствии с политикой наблюдаемости и аудита.

# 28. Аудит и журналирование

Для значимых операций должна обеспечиваться возможность установить:

- кто выполнил операцию;
    
- какую операцию выполнили;
    
- когда она была выполнена;
    
- над каким объектом;
    
- какой был результат.
    

Особое внимание должно уделяться:

- административным действиям;
    
- изменению критических данных;
    
- созданию заказа;
    
- операциям оплаты;
    
- операциям доставки;
    
- изменениям прав доступа;
    
- критическим интеграционным операциям.
    

# 29. Принцип минимальных полномочий

Каждый пользователь, компонент и внешний интеграционный участник должен обладать только теми полномочиями, которые необходимы для выполнения его функций.

Минимизация полномочий применяется к:

- пользователям;
    
- администраторам;
    
- API;
    
- внутренним компонентам;
    
- базе данных;
    
- интеграциям;
    
- техническим учётным данным.
    

# 30. Разделение сред

Среды разработки, тестирования и эксплуатации должны рассматриваться как отдельные контуры.

Доступы, конфигурации и секреты одной среды не должны автоматически предоставлять доступ к другой.

Рабочие данные и секреты Production не должны использоваться в Development или Test без специально определённого безопасного механизма.

# 31. Безопасность резервного копирования и восстановления

Резервные копии должны защищаться от несанкционированного доступа и изменения.

Доступ к резервным копиям должен предоставляться ограниченному кругу технических операций.

Процедуры восстановления должны учитывать сохранность:

- заказов;
    
- исторических данных;
    
- клиентских данных;
    
- критических бизнес-состояний.
    

# 32. Безопасность внешних интеграций

При отказе или компрометации внешней системы SmEl не должен автоматически предоставлять ей расширенный доступ к внутренним данным.

Интеграционный слой должен ограничивать:

- доступные операции;
    
- передаваемые данные;
    
- направление обмена;
    
- область действия полномочий.
    

# 33. Контроль критических бизнес-состояний

Изменение критических состояний должно выполняться только через разрешённые серверные операции.

Критическими являются, в частности:

- состояние Checkout;
    
- состояние заказа;
    
- состояние оплаты;
    
- состояние доставки.
    

Клиент не должен иметь возможности напрямую устанавливать такие состояния произвольными значениями.

# 34. Безопасность данных и исторической целостности

Исторические данные заказа должны быть защищены от изменения вследствие последующих изменений текущих данных.

Изменение:

- товара;
    
- цены;
    
- скидки;
    
- акции;
    
- характеристик;
    
- условий доставки
    

не должно произвольно изменять исторически зафиксированный заказ.

# 35. Безопасность и наблюдаемость

Механизмы безопасности должны быть связаны с системой мониторинга и журналирования.

Система должна обеспечивать возможность выявления:

- неуспешных попыток доступа;
    
- повторяющихся ошибок авторизации;
    
- подозрительных повторных операций;
    
- ошибок интеграций;
    
- нарушений бизнес-ограничений;
    
- критических административных действий.
    

# 36. Безопасность при отказах

Отказ отдельного компонента или внешней системы не должен автоматически приводить к обходу механизмов безопасности.

При невозможности безопасно выполнить критическую операцию система должна отказаться от её выполнения либо перевести её в контролируемое состояние.

Принцип:

**Fail Secure**

# 37. Тестирование безопасности

Безопасность должна проверяться на уровнях:

- API;
    
- авторизации;
    
- контроля доступа;
    
- валидации входных данных;
    
- бизнес-правил;
    
- интеграций;
    
- административного интерфейса;
    
- защиты данных;
    
- критических операций.
    

Конкретный набор тестов и инструментов определяется на последующих этапах реализации и в соответствующих технических решениях.

# 38. Связь с другими архитектурными моделями

AMD-070 использует и уточняет решения следующих моделей:

- AMD-001 — контекст SmEl;
    
- AMD-020 — функциональная модель SmEl;
    
- AMD-030 — информационная модель SmEl;
    
- AMD-040 — компонентная модель SmEl;
    
- AMD-041 — модель взаимодействий SmEl;
    
- AMD-050 — технологическая модель SmEl;
    
- AMD-051 — модель развёртывания SmEl;
    
- AMD-060 — интеграционная модель SmEl.
    

AMD-070 определяет безопасность их взаимодействия, не заменяя соответствующие модели.

# 39. Связь с требованиями и ADR

Модель безопасности реализует соответствующие требования REQ, прежде всего:

- REQ-030 — Нефункциональные требования SmEl;
    
- REQ-040 — Интеграционные требования SmEl;
    
- REQ-050 — Ограничения и бизнес-правила SmEl.
    

Конкретные архитектурные решения в области:

- аутентификации;
    
- управления сессиями;
    
- авторизации;
    
- хранения секретов;
    
- защиты API;
    
- аудита;
    
- интеграционной безопасности
    

при необходимости должны фиксироваться отдельными ADR.

# 40. Архитектурные границы модели

AMD-070 не определяет:

- конкретный механизм аутентификации;
    
- конкретный формат токенов;
    
- конкретные алгоритмы шифрования;
    
- конкретное средство хранения секретов;
    
- конкретный WAF;
    
- конкретную систему SIEM;
    
- конкретный антивирус;
    
- конкретную инфраструктуру безопасности.
    

Эти решения относятся к технологическому и архитектурному уровню реализации и принимаются отдельно.

# 41. Основной принцип безопасности SmEl

Безопасность SmEl строится вокруг серверной доверенной границы:

**Client → API → Backend → Data**

и контролируемого взаимодействия:

**Backend → Integration Layer → External System**

При этом:

**Клиент не является источником доверия для критических данных и операций.**

Серверная часть отвечает за аутентификацию, авторизацию, валидацию, выполнение бизнес-правил, защиту данных и контроль критических состояний.

# 42. Заключительные положения

AMD-070 фиксирует целевую архитектурную модель безопасности SmEl на уровне архитектурных принципов и границ ответственности.

Документ является основой для последующей детализации механизмов безопасности, соответствующих ADR и технологических решений.

Модель должна рассматриваться совместно с функциональной, информационной, компонентной, технологической, развёртывающей и интеграционной моделями SmEl.
