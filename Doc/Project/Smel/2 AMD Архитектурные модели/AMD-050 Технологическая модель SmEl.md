# 1. Назначение

Настоящий документ определяет технологическую модель системы **SmEl (Smart Electric)**.

Документ устанавливает соответствие между логическими архитектурными компонентами SmEl и технологиями, используемыми для их реализации.

AMD-050 развивает компонентную модель **AMD-040** и модель взаимодействий **AMD-041**.

# 2. Область применения

Технологическая модель распространяется на:

- клиентскую часть;
    
- серверную часть;
    
- API;
    
- бизнес-логику;
    
- информационное хранение;
    
- административную часть;
    
- интеграционные механизмы.
    

Документ не определяет конкретную инфраструктуру развёртывания. Она определяется последующими архитектурными моделями.

# 3. Технологическая основа

Технологическая основа SmEl определяется документом **STD-001 — Технологический стек SmEl**.

Основные технологии:

- **Frontend:** Vue 3;
    
- **язык Frontend:** TypeScript;
    
- **управление состоянием:** Pinia;
    
- **маршрутизация:** Vue Router;
    
- **стилизация:** Tailwind CSS;
    
- **Backend:** Django;
    
- **API:** Django REST Framework;
    
- **административная часть:** Django Admin;
    
- **СУБД:** PostgreSQL;
    
- **архитектурный интерфейс:** REST API.
    

# 4. Технологическая структура

Технологическая структура SmEl разделяется на следующие основные области:

**Frontend → REST API → Backend → PostgreSQL**

Дополнительный контур:

**Backend → Integration Layer → External Systems**

Административный контур:

**Administrator → Django Admin → Backend / Data**

# 5. Frontend

Frontend реализуется на базе **Vue 3**.

Frontend отвечает за:

- пользовательский интерфейс;
    
- отображение каталога;
    
- навигацию;
    
- карточки товаров;
    
- работу с корзиной;
    
- Checkout;
    
- отображение заказа;
    
- взаимодействие с API.
    

Frontend не является источником бизнес-истины.

# 6. TypeScript

TypeScript используется как основной язык разработки Frontend.

TypeScript обеспечивает:

- типизацию данных;
    
- описание API-моделей;
    
- типизацию состояния;
    
- контроль интерфейсов компонентов;
    
- снижение количества ошибок при взаимодействии между компонентами.
    

Типы Frontend не должны рассматриваться как замена серверной валидации.

# 7. Pinia

**Pinia** используется для управления состоянием Frontend.

Состояние может включать:

- состояние каталога;
    
- фильтры;
    
- состояние текущей корзины;
    
- состояние Checkout;
    
- пользовательское состояние;
    
- состояние UI.
    

Pinia не должна использоваться как источник окончательных значений цены, наличия, скидок или иных критических бизнес-данных.

# 8. Vue Router

**Vue Router** используется для организации навигации Frontend.

Маршрутизация должна обеспечивать переходы между основными пользовательскими областями:

- каталог;
    
- категория;
    
- товар;
    
- корзина;
    
- Checkout;
    
- заказ;
    
- клиентская область.
    

Проверка прав доступа должна выполняться серверной частью независимо от клиентской маршрутизации.

# 9. Tailwind CSS

**Tailwind CSS** используется для реализации визуального слоя Frontend.

Технология отвечает за представление интерфейса и не содержит бизнес-логики системы.

# 10. Backend

Backend реализуется на базе **Django**.

Backend является центральным серверным компонентом SmEl.

Он отвечает за:

- выполнение бизнес-логики;
    
- управление данными;
    
- валидацию;
    
- контроль доступа;
    
- выполнение бизнес-правил;
    
- обработку заказов;
    
- взаимодействие с внешними системами.
    

# 11. Django REST Framework

**Django REST Framework** используется для реализации REST API.

API обеспечивает взаимодействие Frontend и Backend.

Через API выполняются операции:

- получения каталога;
    
- получения товаров;
    
- работы с корзиной;
    
- Checkout;
    
- создания заказа;
    
- получения заказов;
    
- операций оплаты;
    
- операций доставки;
    
- работы клиента.
    

# 12. Backend как источник истины

Backend является единственным источником истины для критических бизнес-данных и бизнес-правил.

На Backend должны контролироваться:

- цены;
    
- скидки;
    
- акции;
    
- наличие;
    
- количество товара;
    
- состояние корзины;
    
- актуальность корзины;
    
- Checkout;
    
- создание заказа;
    
- состояние заказа;
    
- состояние оплаты;
    
- состояние доставки.
    

Frontend может отображать предварительные значения, но окончательное решение принимает Backend.

# 13. Django Admin

**Django Admin** используется для административного управления системой.

Административный интерфейс обеспечивает управление:

- категориями;
    
- товарами;
    
- характеристиками;
    
- изображениями;
    
- ценами;
    
- скидками;
    
- акциями;
    
- наличием;
    
- клиентами;
    
- заказами;
    
- доставкой;
    
- оплатой.
    

Административные операции должны использовать те же правила целостности данных, что и остальные серверные операции.

# 14. PostgreSQL

**PostgreSQL** используется как основная система управления базами данных SmEl.

База данных обеспечивает хранение:

- каталога;
    
- цен;
    
- коммерческих условий;
    
- наличия;
    
- клиентов;
    
- корзин;
    
- Checkout-данных;
    
- заказов;
    
- доставки;
    
- оплаты.
    

Физическая структура таблиц определяется на уровне реализации и не является предметом AMD-050.

# 15. Технологическое соответствие компонентов

Логические компоненты AMD-040 реализуются следующим образом:

|Логический компонент|Технологическая реализация|
|---|---|
|Клиентское приложение|Vue 3 + TypeScript|
|Управление состоянием|Pinia|
|Навигация|Vue Router|
|Визуальный слой|Tailwind CSS|
|API|Django REST Framework|
|Серверная бизнес-логика|Django|
|Каталог|Django + DRF|
|Ценообразование|Django|
|Корзина|Django + DRF|
|Checkout|Django + DRF|
|Заказы|Django + DRF|
|Оплата|Django + DRF + Integration Layer|
|Доставка|Django + DRF + Integration Layer|
|Клиенты|Django + DRF|
|Администрирование|Django Admin|
|Хранение данных|PostgreSQL|
|Внешние интеграции|Backend Integration Layer|

# 16. Технологическая реализация каталога

Каталог реализуется серверной частью Django и предоставляется Frontend через REST API.

Frontend отвечает за:

- отображение;
    
- навигацию;
    
- фильтрацию интерфейса;
    
- пользовательский ввод.
    

Backend отвечает за:

- получение данных;
    
- правила выборки;
    
- доступность;
    
- актуальность данных;
    
- формирование ответа API.
    

# 17. Технологическая реализация ценообразования

Ценообразование реализуется на Backend.

Backend получает необходимые данные из PostgreSQL и определяет:

- базовую цену;
    
- действующую цену;
    
- скидки;
    
- акции;
    
- итоговую стоимость.
    

Frontend получает результат через API.

Frontend не должен самостоятельно определять окончательную цену заказа.

# 18. Технологическая реализация корзины

Корзина реализуется на Backend с предоставлением операций через REST API.

Frontend использует Pinia для хранения текущего клиентского состояния корзины.

Backend хранит и контролирует:

- Cart;
    
- Cart Item;
    
- количество;
    
- принадлежность корзины;
    
- даты создания и изменения;
    
- актуальность позиции;
    
- правила жизненного цикла.
    

Для авторизованного клиента данные корзины сохраняются между сеансами.

Для гостя корзина ограничена текущей сессией.

# 19. Технологическая реализация Checkout

Checkout реализуется серверной частью.

Frontend предоставляет пользовательские данные и выбранные параметры.

Backend:

- проверяет корзину;
    
- повторно рассчитывает коммерческие условия;
    
- проверяет доставку;
    
- проверяет оплату;
    
- формирует данные для создания заказа.
    

Клиентское состояние Checkout не является окончательным источником данных.

# 20. Технологическая реализация заказа

Создание заказа выполняется Backend.

Backend формирует:

- Order;
    
- Order Item;
    
- исторические значения товара;
    
- цены;
    
- скидки;
    
- акции;
    
- стоимость доставки;
    
- итоговую стоимость;
    
- данные клиента;
    
- способ оплаты;
    
- способ доставки.
    

После сохранения заказа его исторические данные не должны зависеть от последующих изменений каталога.

# 21. Технологическая реализация оплаты

Оплата реализуется серверным компонентом оплаты.

Взаимодействие с внешней платёжной системой выполняется через интеграционный слой.

Основной технологический поток:

**Frontend → DRF API → Payment Component → Integration Layer → Payment System**

Результат операции передаётся обратно Backend, где фиксируется состояние оплаты.

# 22. Технологическая реализация доставки

Доставка реализуется серверным компонентом доставки.

При необходимости взаимодействия с внешней службой используется интеграционный слой.

Основной поток:

**Frontend → DRF API → Delivery Component → Integration Layer → Delivery Service**

Полученные данные об операции доставки сохраняются Backend.

# 23. Технологическая реализация клиентов

Данные клиентов управляются Backend на базе Django.

Frontend получает необходимые данные через API.

Backend отвечает за:

- идентификацию;
    
- аутентификацию;
    
- авторизацию;
    
- управление данными клиента;
    
- связь клиента с корзиной;
    
- связь клиента с заказами.
    

# 24. Технологическая реализация интеграций

Интеграции с внешними системами должны быть изолированы от основной бизнес-логики.

Интеграционный слой Backend обеспечивает:

- вызов внешних сервисов;
    
- преобразование данных;
    
- обработку ошибок;
    
- контроль повторных операций;
    
- получение результатов;
    
- регистрацию значимых интеграционных операций.
    

Конкретные внешние системы и протоколы определяются в **AMD-060 — Интеграционной модели SmEl**.

# 25. API-граница

REST API является технологической границей между Frontend и Backend.

Основные правила:

- Frontend не обращается непосредственно к PostgreSQL;
    
- Frontend не обращается непосредственно к внешним бизнес-системам;
    
- критические операции выполняются через Backend;
    
- серверная валидация является обязательной;
    
- API обеспечивает контролируемый доступ к функциям Backend.
    

# 26. Поток данных

Основной поток данных:

**PostgreSQL → Django → DRF API → Vue 3 → Пользователь**

При изменении данных:

**Пользователь → Vue 3 → DRF API → Django → PostgreSQL**

При внешней интеграции:

**Django → Integration Layer → External System**

Результат внешней операции возвращается через Backend.

# 27. Технологическая ответственность

Ответственность технологий разделяется следующим образом:

- **Vue 3** — пользовательский интерфейс;
    
- **TypeScript** — типизация Frontend;
    
- **Pinia** — клиентское состояние;
    
- **Vue Router** — навигация;
    
- **Tailwind CSS** — представление;
    
- **Django** — серверная логика;
    
- **Django REST Framework** — API;
    
- **Django Admin** — административное управление;
    
- **PostgreSQL** — постоянное хранение данных.
    

Технология не должна подменять бизнес-ответственность архитектурного компонента.

# 28. Технологические ограничения

В рамках текущей архитектуры устанавливаются следующие ограничения:

1. Backend является источником истины для бизнес-логики.
    
2. Frontend не имеет прямого доступа к PostgreSQL.
    
3. Frontend взаимодействует с Backend через API.
    
4. Внешние системы не должны напрямую изменять внутренние данные SmEl.
    
5. Критические бизнес-операции должны контролироваться сервером.
    
6. Технологические компоненты должны соответствовать утверждённому стеку STD-001.
    

# 29. Связь с компонентной моделью

AMD-050 реализует компоненты, определённые **AMD-040**.

Соответствие основных уровней:

**AMD-040 → AMD-050**

**Клиентское приложение → Vue 3 / TypeScript**

**Состояние → Pinia**

**Навигация → Vue Router**

**API → Django REST Framework**

**Бизнес-логика → Django**

**Администрирование → Django Admin**

**Данные → PostgreSQL**

**Интеграции → Backend Integration Layer**

# 30. Связь с моделью взаимодействий

Технологическая модель реализует взаимодействия AMD-041.

Основной технологический поток:

**Vue 3 → REST API → Django → PostgreSQL**

Для внешних операций:

**Django → Integration Layer → External System**

Таким образом, технологическая реализация сохраняет установленные архитектурные границы.

# 31. Связь с требованиями

AMD-050 основан на:

- **REQ-001 — Бизнес-требования SmEl**;
    
- **REQ-010 — Функциональные требования SmEl**;
    
- **REQ-020 — Информационные требования SmEl**;
    
- **REQ-030 — Нефункциональные требования SmEl**;
    
- **REQ-040 — Интеграционные требования SmEl**;
    
- **REQ-050 — Ограничения и бизнес-правила SmEl**.
    

# 32. Связь с архитектурными решениями

AMD-050 должен соответствовать:

- **STD-001 — Технологический стек SmEl**;
    
- **ADR-001–ADR-020 — Архитектурные решения SmEl**.
    

При изменении технологического стека или архитектурных решений технологическая модель должна быть актуализирована.

# 33. Граница технологической модели

AMD-050 определяет логическое соответствие архитектурных компонентов конкретным технологиям.

Документ не определяет:

- физические серверы;
    
- контейнеры;
    
- сетевую инфраструктуру;
    
- параметры размещения;
    
- масштабирование инфраструктуры;
    
- резервное копирование;
    
- конкретные конфигурации production-среды.
    

Эти вопросы относятся к модели развёртывания и последующим архитектурным документам.

# 34. Основание для последующих моделей

AMD-050 является основанием для разработки:

- **AMD-051 — Модель развёртывания SmEl**;
    
- **AMD-060 — Интеграционная модель SmEl**;
    
- **AMD-070 — Модель безопасности SmEl**.
    

# 35. Заключительные положения

AMD-050 определяет технологическую модель SmEl и связывает логические архитектурные компоненты с утверждённым технологическим стеком.

Модель сохраняет принцип разделения ответственности:

**Frontend отвечает за взаимодействие с пользователем, Backend — за бизнес-логику и данные, PostgreSQL — за постоянное хранение, Integration Layer — за взаимодействие с внешними системами.**

На основании AMD-050 может быть разработана **AMD-051 — Модель развёртывания SmEl**, определяющая физическое и логическое размещение компонентов системы.
