# 1. Назначение

Настоящий документ определяет компонентную модель системы **SmEl (Smart Electric)**.

Документ устанавливает основные программные компоненты системы, их ответственность, границы и взаимодействие.

AMD-040 является развитием функциональной модели **AMD-020** и информационной модели **AMD-030**.

# 2. Область применения

Компонентная модель распространяется на программную систему интернет-магазина SmEl и охватывает клиентскую часть, серверную часть, компоненты бизнес-логики, работу с данными, интеграции и административные функции.

Документ не определяет конкретную технологию реализации компонентов.

# 3. Основные компоненты системы

Компонентная модель SmEl включает следующие основные компоненты:

- клиентское приложение;
    
- API;
    
- компонент каталога;
    
- компонент поиска и навигации;
    
- компонент товара;
    
- компонент ценообразования;
    
- компонент корзины;
    
- компонент проверки актуальности;
    
- компонент Checkout;
    
- компонент заказов;
    
- компонент оплаты;
    
- компонент доставки;
    
- компонент клиентов;
    
- административный компонент;
    
- компонент интеграций;
    
- компонент данных.
    

Компонентная модель может расширяться при появлении новых функциональных областей.

# 4. Клиентское приложение

Клиентское приложение обеспечивает пользовательское взаимодействие с интернет-магазином.

Основные функции:

- отображение каталога;
    
- поиск и навигация;
    
- отображение карточки товара;
    
- управление корзиной;
    
- выполнение Checkout;
    
- отображение заказа;
    
- взаимодействие с функциями доставки и оплаты;
    
- отображение состояния операций.
    

Клиентское приложение не является источником истины для бизнес-правил и критических коммерческих данных.

# 5. API

API является интерфейсом взаимодействия клиентского приложения с серверной частью.

API обеспечивает:

- передачу запросов;
    
- передачу данных;
    
- выполнение предусмотренных операций;
    
- передачу результатов;
    
- обработку ошибок;
    
- контроль доступа.
    

API не должен содержать самостоятельную альтернативную реализацию бизнес-правил, противоречащую серверной бизнес-логике.

# 6. Компонент каталога

Компонент каталога отвечает за предоставление данных каталога.

Основные функции:

- получение списка товаров;
    
- получение категорий;
    
- получение структуры категорий;
    
- получение данных товара;
    
- предоставление характеристик;
    
- предоставление изображений;
    
- предоставление информации о доступности товара.
    

Компонент каталога использует актуальные данные из компонента данных.

# 7. Компонент поиска и навигации

Компонент поиска и навигации обеспечивает поиск и навигацию по каталогу.

Основные функции:

- поиск товаров;
    
- фильтрация;
    
- сортировка;
    
- навигация по категориям;
    
- формирование результатов поиска.
    

Компонент не должен самостоятельно изменять исходные данные каталога.

# 8. Компонент товара

Компонент товара отвечает за получение и представление информации о конкретном товаре.

Компонент обеспечивает:

- идентификацию товара;
    
- получение описания;
    
- получение характеристик;
    
- получение изображений;
    
- получение информации о доступности;
    
- получение актуальных коммерческих данных.
    

# 9. Компонент ценообразования

Компонент ценообразования отвечает за определение актуальной стоимости товара.

Компонент работает с:

- базовой стоимостью;
    
- ценами;
    
- скидками;
    
- акциями;
    
- периодами их действия;
    
- итоговой стоимостью.
    

Расчёт коммерческих условий должен выполняться на серверной стороне.

Цена, скидка или акция, отображённые клиентом, не считаются окончательно зафиксированными до соответствующей серверной проверки.

# 10. Компонент корзины

Компонент корзины отвечает за управление текущей корзиной клиента.

Основные функции:

- создание корзины;
    
- получение корзины;
    
- добавление товара;
    
- изменение количества;
    
- удаление позиции;
    
- получение текущего состояния корзины;
    
- управление сроком жизни корзины и её позиций.
    

Для авторизованного клиента компонент должен обеспечивать сохранение корзины между сеансами.

Для гостя корзина должна существовать только в рамках текущей сессии.

# 11. Компонент проверки актуальности

Компонент проверки актуальности отвечает за проверку возможности использования содержимого корзины для оформления заказа.

Проверяются:

- существование товара;
    
- доступность товара;
    
- допустимое количество;
    
- актуальная цена;
    
- скидки;
    
- акции;
    
- срок нахождения позиции в корзине;
    
- другие условия продажи.
    

Результат проверки должен определять, может ли корзина перейти к Checkout.

# 12. Компонент Checkout

Компонент Checkout отвечает за подготовку данных к созданию заказа.

Компонент обеспечивает:

- получение актуального состава корзины;
    
- повторную проверку данных;
    
- получение данных клиента;
    
- выбор доставки;
    
- выбор оплаты;
    
- расчёт итоговой стоимости;
    
- подготовку данных заказа.
    

Checkout является промежуточным состоянием процесса и не заменяет компонент заказа.

# 13. Компонент заказов

Компонент заказов отвечает за создание и сопровождение заказов.

Основные функции:

- создание заказа;
    
- формирование позиций заказа;
    
- фиксация стоимости;
    
- сохранение применённых скидок и акций;
    
- сохранение данных клиента;
    
- сохранение доставки;
    
- сохранение оплаты;
    
- управление состоянием заказа;
    
- предоставление истории заказов.
    

После создания заказа компонент должен обеспечивать независимость исторических данных заказа от последующих изменений каталога.

# 14. Компонент оплаты

Компонент оплаты отвечает за управление информацией и операциями, связанными с оплатой заказа.

Основные функции:

- выбор способа оплаты;
    
- создание платёжной операции, если применимо;
    
- получение состояния оплаты;
    
- обработка результата оплаты;
    
- связывание оплаты с заказом.
    

Внешние платёжные системы подключаются через компонент интеграций.

# 15. Компонент доставки

Компонент доставки отвечает за выбор и обработку способа получения заказа.

Основные функции:

- предоставление доступных способов доставки;
    
- определение стоимости доставки;
    
- получение данных получения;
    
- проверка доступности доставки;
    
- сохранение данных доставки;
    
- сопровождение состояния доставки.
    

Внешние службы доставки подключаются через компонент интеграций.

# 16. Компонент клиентов

Компонент клиентов отвечает за данные и операции, связанные с клиентами.

Основные функции:

- идентификация клиента;
    
- управление учётными данными;
    
- управление контактными данными;
    
- получение заказов клиента;
    
- связь клиента с корзиной;
    
- предоставление данных, необходимых для оформления заказа.
    

# 17. Административный компонент

Административный компонент обеспечивает управление системой сотрудниками интернет-магазина.

Основные области управления:

- категории;
    
- товары;
    
- характеристики;
    
- изображения;
    
- цены;
    
- скидки;
    
- акции;
    
- наличие;
    
- клиенты;
    
- заказы;
    
- доставка;
    
- оплата.
    

Административный компонент должен использовать серверные механизмы управления данными и бизнес-правилами.

# 18. Компонент интеграций

Компонент интеграций обеспечивает взаимодействие SmEl с внешними системами.

Возможные направления:

- платёжные системы;
    
- службы доставки;
    
- источники товарных данных;
    
- системы учёта наличия;
    
- внешние сервисы.
    

Компонент должен изолировать внутреннюю бизнес-логику SmEl от конкретных внешних интерфейсов.

# 19. Компонент данных

Компонент данных отвечает за доступ к информационным объектам системы.

Компонент обеспечивает работу с:

- Product;
    
- Category;
    
- Product Characteristic;
    
- Product Image;
    
- Price;
    
- Discount;
    
- Promotion;
    
- Stock;
    
- Customer;
    
- Cart;
    
- Cart Item;
    
- Checkout;
    
- Order;
    
- Order Item;
    
- Delivery;
    
- Payment.
    

Компонент данных не должен нарушать бизнес-правила, определённые серверной частью системы.

# 20. Серверная граница

Серверная часть SmEl является центральной границей выполнения бизнес-логики.

На серверной стороне должны контролироваться:

- бизнес-правила;
    
- ценообразование;
    
- скидки и акции;
    
- наличие;
    
- проверка корзины;
    
- Checkout;
    
- создание заказа;
    
- состояние заказа;
    
- состояние оплаты;
    
- состояние доставки;
    
- критические изменения данных.
    

Клиентская часть не должна считаться доверенным источником этих данных.

# 21. Взаимодействие компонентов

Основное взаимодействие компонентов соответствует функциональному потоку:

**Клиентское приложение → API → Каталог → Товар → Ценообразование**

Для процесса покупки:

**Клиентское приложение → API → Корзина → Проверка актуальности → Checkout → Заказ**

Для завершения заказа:

**Заказ → Оплата**

**Заказ → Доставка**

Внешние операции выполняются через:

**Компонент интеграций → Внешняя система**

# 22. Компонентная ответственность

Каждый компонент должен иметь определённую ответственность и не должен дублировать ответственность другого компонента.

Основные границы ответственности:

- **Каталог** — представление ассортимента;
    
- **Товар** — данные конкретного товара;
    
- **Ценообразование** — коммерческие условия;
    
- **Корзина** — текущее выбранное содержимое;
    
- **Проверка актуальности** — проверка возможности продолжения покупки;
    
- **Checkout** — подготовка оформления;
    
- **Заказ** — исторически зафиксированная покупка;
    
- **Оплата** — платёжное состояние;
    
- **Доставка** — состояние получения;
    
- **Интеграции** — взаимодействие с внешними системами;
    
- **Данные** — доступ к информационным объектам.
    

# 23. Граница текущих и исторических данных

Компоненты каталога, ценообразования, наличия и корзины работают преимущественно с текущими данными.

Компонент заказов формирует историческую фиксацию данных.

После создания заказа изменение данных текущего каталога не должно изменять сохранённые данные заказа.

# 24. Жизненный цикл покупки

Компоненты должны поддерживать следующий жизненный цикл:

**Каталог → Выбор товара → Корзина → Проверка актуальности → Checkout → Заказ → Оплата → Доставка → Получение товара**

Каждый переход должен выполняться только при выполнении соответствующих бизнес-правил.

# 25. Компонентные зависимости

Основные зависимости определяются следующим образом:

- клиентское приложение зависит от API;
    
- API зависит от серверных функциональных компонентов;
    
- функциональные компоненты используют компонент данных;
    
- Checkout зависит от корзины, проверки актуальности, ценообразования, клиента, доставки и оплаты;
    
- заказ зависит от результатов Checkout;
    
- оплата и доставка связаны с заказом;
    
- внешние системы доступны через компонент интеграций.
    

Зависимости не должны приводить к обходу установленных бизнес-границ.

# 26. Связь с информационной моделью

Компонентная модель реализует информационные объекты AMD-030.

Основное соответствие:

**Каталог → Product / Category / Characteristic / Image**

**Ценообразование → Price / Discount / Promotion**

**Корзина → Cart / Cart Item**

**Checkout → Checkout**

**Заказ → Order / Order Item**

**Доставка → Delivery / Delivery Method**

**Оплата → Payment / Payment Method**

**Клиент → Customer**

# 27. Связь с требованиями и архитектурными решениями

AMD-040 реализует функциональные и информационные требования, определённые документами серии REQ.

Основными основаниями являются:

- **REQ-001 — Бизнес-требования SmEl**;
    
- **REQ-010 — Функциональные требования SmEl**;
    
- **REQ-020 — Информационные требования SmEl**;
    
- **REQ-030 — Нефункциональные требования SmEl**;
    
- **REQ-040 — Интеграционные требования SmEl**;
    
- **REQ-050 — Ограничения и бизнес-правила SmEl**.
    

Компонентная модель также должна соответствовать принятым архитектурным решениям **ADR-001–ADR-020**.

# 28. Граница компонентной модели

AMD-040 определяет логические программные компоненты и их ответственность.

Документ не определяет:

- конкретные классы;
    
- структуру исходного кода;
    
- физические модули проекта;
    
- структуру базы данных;
    
- серверную инфраструктуру;
    
- параметры развёртывания.
    

Эти вопросы определяются последующими архитектурными моделями и техническими решениями.

# 29. Основание для последующих моделей

AMD-040 является основанием для разработки:

- **AMD-041 — Модель взаимодействий SmEl**;
    
- **AMD-050 — Технологическая модель SmEl**;
    
- последующих архитектурных моделей, определяющих развёртывание, интеграции и безопасность.
    

AMD-041 должна детализировать взаимодействие компонентов, определённых настоящим документом.

# 30. Заключительные положения

AMD-040 определяет компонентную модель SmEl и устанавливает логические границы основных программных компонентов системы.

Компоненты должны обеспечивать реализацию функциональной модели AMD-020 и работу с информационными объектами AMD-030 при соблюдении требований серии REQ и принятых архитектурных решений ADR.

На основании AMD-040 должна быть разработана **AMD-041 — Модель взаимодействий SmEl**, определяющая последовательность и правила взаимодействия компонентов системы.
