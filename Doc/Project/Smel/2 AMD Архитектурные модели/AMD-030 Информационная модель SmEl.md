# 1. Назначение

Настоящий документ определяет информационную модель проекта **SmEl (Smart Electric)**.

Документ устанавливает основные информационные сущности системы, их назначение, взаимосвязи, жизненный цикл и правила преобразования данных между основными состояниями бизнес-процесса.

AMD-030 разработан на основании требований серии **REQ** и функциональной модели **AMD-020**.

# 2. Область применения

Информационная модель охватывает данные, используемые в основных функциональных областях SmEl:

- каталог;
    
- товары;
    
- характеристики;
    
- ценообразование;
    
- наличие;
    
- клиенты;
    
- корзина;
    
- Checkout;
    
- заказы;
    
- оплата;
    
- доставка;
    
- административное управление;
    
- интеграции.
    

Модель не определяет физическую структуру базы данных, конкретные таблицы, индексы и механизмы хранения.

# 3. Основные информационные сущности

Информационная модель SmEl включает следующие основные сущности:

- **Product** — товар;
    
- **Category** — категория;
    
- **Product Characteristic** — характеристика товара;
    
- **Product Image** — изображение товара;
    
- **Price** — цена;
    
- **Discount** — скидка;
    
- **Promotion** — акция;
    
- **Stock** — наличие;
    
- **Customer** — клиент;
    
- **Cart** — корзина;
    
- **Cart Item** — позиция корзины;
    
- **Checkout** — оформление заказа;
    
- **Order** — заказ;
    
- **Order Item** — позиция заказа;
    
- **Delivery** — доставка;
    
- **Delivery Method** — способ доставки;
    
- **Payment** — оплата;
    
- **Payment Method** — способ оплаты.
    

Состав информационных сущностей может расширяться при дальнейшем архитектурном проектировании.

# 4. Каталог

Каталог представляет функционально организованную совокупность данных о товарах.

Основные информационные сущности каталога:

**Category → Product → Product Characteristic / Product Image**

Каталог предоставляет текущие данные, используемые для выбора товара.

Исторические данные оформленных заказов не должны зависеть от последующих изменений каталога.

# 5. Product

**Product** является основной информационной сущностью товара.

Product должен обеспечивать идентификацию товара и связь с его текущими данными.

Основные атрибуты:

- идентификатор;
    
- артикул;
    
- наименование;
    
- описание;
    
- категория;
    
- характеристики;
    
- изображения;
    
- состояние доступности;
    
- данные, необходимые для ценообразования.
    

Product является источником данных для формирования **Cart Item**.

# 6. Category

**Category** обеспечивает классификацию товаров.

Category может иметь связь:

**Category → Product**

Для поддержки сложной структуры каталога допускается иерархическая связь категорий:

**Category → Category**

Конкретная глубина и правила иерархии определяются требованиями каталога.

# 7. Product Characteristic

**Product Characteristic** представляет техническую характеристику товара.

Основные данные:

- идентификатор;
    
- наименование;
    
- значение;
    
- единица измерения;
    
- связь с Product.
    

Набор характеристик может различаться в зависимости от категории товара.

Информационная модель должна допускать расширение набора характеристик без изменения базовой сущности Product.

# 8. Product Image

**Product Image** представляет изображение товара.

Изображение должно быть связано с соответствующим Product.

Модель должна допускать наличие нескольких изображений одного товара.

# 9. Ценообразование

Ценообразование представляет отдельную информационную область.

Основные сущности:

**Product → Price**

и связанные с ними:

**Discount**

**Promotion**

Ценообразование должно позволять определить актуальные коммерческие условия для товара.

# 10. Price

**Price** представляет стоимость товара в определённом коммерческом контексте.

Price должен позволять определить:

- товар;
    
- стоимость;
    
- период действия;
    
- состояние актуальности;
    
- другие необходимые условия применения.
    

Текущая цена может изменяться без изменения исторических данных уже созданного заказа.

# 11. Discount и Promotion

**Discount** представляет условие предоставления скидки.

**Promotion** представляет акционное или иное коммерческое предложение.

Они должны иметь возможность быть связаны с:

- товаром;
    
- категорией;
    
- периодом действия;
    
- условиями применения.
    

Конкретные правила расчёта скидок и акций относятся к функциональной и бизнес-логике системы.

# 12. Stock

**Stock** представляет информацию о доступности товара.

Stock связан с Product и должен позволять определить:

- доступность;
    
- доступное количество, если оно учитывается;
    
- состояние наличия;
    
- время актуальности данных.
    

Stock используется при:

- работе с корзиной;
    
- проверке актуальности;
    
- Checkout;
    
- создании заказа.
    

# 13. Customer

**Customer** представляет зарегистрированного клиента SmEl.

Основные данные:

- идентификатор;
    
- учётные данные;
    
- контактные данные;
    
- данные, необходимые для оформления заказа;
    
- связанные заказы;
    
- связанная корзина.
    

Customer должен иметь возможность быть связанным с одной или несколькими сущностями бизнес-процесса покупки.

# 14. Cart

**Cart** представляет текущее состояние выбранных клиентом товаров.

Cart содержит:

- идентификатор;
    
- владельца или идентификатор сессии;
    
- дату создания;
    
- дату изменения;
    
- состояние;
    
- позиции Cart Item.
    

Правила хранения:

- авторизованная корзина связана с Customer и сохраняется между сеансами;
    
- гостевая корзина связана с текущей сессией.
    

# 15. Cart Item

**Cart Item** представляет выбранный товар в корзине.

Основные данные:

- идентификатор;
    
- ссылка на Product;
    
- количество;
    
- дата добавления;
    
- дата изменения;
    
- данные, необходимые для проверки актуальности.
    

Основная связь:

**Product → Cart Item**

Цена товара не считается окончательно зафиксированной в Cart Item.

# 16. Актуальность Cart Item

Для Cart Item должна существовать возможность определить состояние актуальности.

Проверяются:

- существование Product;
    
- Stock;
    
- количество;
    
- Price;
    
- Discount;
    
- Promotion;
    
- срок нахождения позиции в корзине;
    
- другие условия продажи.
    

Результатом проверки является возможность либо невозможность дальнейшего использования позиции в Checkout.

# 17. Checkout

**Checkout** представляет состояние процесса подготовки заказа.

Checkout использует данные:

**Cart → Checkout**

и дополнительно включает:

- Customer;
    
- Delivery Method;
    
- данные получения;
    
- Payment Method;
    
- актуальные коммерческие условия;
    
- итоговую стоимость.
    

Checkout не заменяет Order и не является его историческим эквивалентом.

# 18. Order

**Order** представляет исторически зафиксированный результат оформления покупки.

Основные связи:

**Customer → Order**

**Checkout → Order**

Order содержит:

- идентификатор;
    
- дату и время создания;
    
- покупателя;
    
- Order Item;
    
- стоимость товаров;
    
- скидки и акции;
    
- стоимость доставки;
    
- итоговую стоимость;
    
- Delivery;
    
- Payment;
    
- состояние заказа.
    

После создания Order становится самостоятельной исторической сущностью.

# 19. Order Item

**Order Item** представляет исторически зафиксированную позицию заказа.

Основная связь:

**Product → Order Item**

При этом Order Item должен содержать собственные исторические значения:

- идентификатор исходного товара;
    
- наименование;
    
- количество;
    
- цену;
    
- применённую скидку;
    
- итоговую стоимость;
    
- необходимые данные идентификации товара.
    

Изменение Product после создания Order не должно изменять Order Item.

# 20. Delivery

**Delivery** представляет состояние выполнения доставки конкретного заказа.

Delivery связан с Order и Delivery Method.

Основные данные:

- идентификатор;
    
- способ доставки;
    
- данные получения;
    
- стоимость;
    
- состояние;
    
- данные внешней доставки, если применимо.
    

# 21. Delivery Method

**Delivery Method** представляет доступный способ доставки.

Способ доставки может содержать:

- идентификатор;
    
- наименование;
    
- описание;
    
- условия применения;
    
- стоимость или правила её определения;
    
- состояние доступности.
    

Конкретные способы доставки определяются требованиями и архитектурой SmEl.

# 22. Payment

**Payment** представляет платёжную операцию, связанную с Order.

Основные данные:

- идентификатор;
    
- заказ;
    
- способ оплаты;
    
- сумма;
    
- дата и время;
    
- состояние;
    
- идентификатор внешней платёжной операции, если применимо.
    

Одна операция не должна неконтролируемо приводить к повторному изменению финансового состояния заказа.

# 23. Payment Method

**Payment Method** представляет доступный способ оплаты.

Может содержать:

- идентификатор;
    
- наименование;
    
- описание;
    
- состояние доступности;
    
- условия применения;
    
- данные, необходимые для выбора способа оплаты.
    

Конкретная реализация платёжных механизмов определяется архитектурой интеграций.

# 24. Основные информационные связи

Основная цепочка преобразования данных:

**Product → Cart Item → Checkout → Order Item**

Связанный бизнес-процесс:

**Cart → Проверка актуальности → Checkout → Order → Payment / Delivery**

Связи каталога:

**Category → Product → Characteristic / Image**

Связи ценообразования:

**Product → Price / Discount / Promotion**

Связи клиента:

**Customer → Cart**

**Customer → Order**

# 25. Преобразование данных

Основным архитектурным преобразованием является переход от текущего состояния данных к исторически зафиксированному состоянию заказа.

Последовательность:

**Product**  
↓  
**Cart Item**  
↓  
**Checkout**  
↓  
**Order Item**  
↓  
**Order**

При переходе к Order должны фиксироваться значения, необходимые для восстановления исторического содержания покупки.

# 26. Разделение текущих и исторических данных

Информационная модель разделяет:

**текущие данные**

- Product;
    
- Price;
    
- Discount;
    
- Promotion;
    
- Stock;
    

и

**операционные данные**

- Cart;
    
- Cart Item;
    
- Checkout;
    

и

**исторические данные**

- Order;
    
- Order Item;
    
- зафиксированные данные Delivery;
    
- зафиксированные данные Payment.
    

Такое разделение обеспечивает независимость истории заказов от последующих изменений каталога.

# 27. Жизненный цикл информационных данных

Основной жизненный цикл покупки:

**Product → Cart Item → Checkout → Order Item**

При этом:

- Product существует независимо от конкретной покупки;
    
- Cart Item существует в рамках корзины;
    
- Checkout существует в процессе оформления;
    
- Order Item создаётся при формировании заказа;
    
- Order сохраняет результат завершённого оформления.
    

Оплата и доставка сопровождают Order в соответствии с их собственными жизненными циклами.

# 28. Целостность информационной модели

Информационная модель должна обеспечивать:

- уникальность идентификаторов;
    
- корректность обязательных связей;
    
- невозможность создания некорректного Order;
    
- сохранение исторических значений Order Item;
    
- согласованность Order, Payment и Delivery;
    
- корректное разделение текущих и исторических данных;
    
- невозможность использования неактуальной корзины для создания заказа.
    

# 29. Локализация

Информационная модель должна поддерживать локализуемые данные.

Минимальный набор языков:

- украинский;
    
- русский;
    
- английский.
    

Локализация должна применяться прежде всего к данным, отображаемым пользователю, включая наименования, описания и характеристики, для которых предусмотрена мультиязычность.

# 30. Интеграционные данные

Для внешних интеграций модель должна обеспечивать хранение данных, необходимых для сопоставления объектов SmEl и внешних систем.

В частности:

- идентификатор внешней системы;
    
- идентификатор внешнего объекта;
    
- состояние обмена;
    
- дата и время обмена;
    
- результат операции;
    
- данные, необходимые для повторной обработки.
    

Конкретный состав определяется соответствующими интеграционными решениями.

# 31. Информационная ответственность

За актуальные бизнес-данные SmEl должна отвечать серверная часть системы.

Клиентская часть не является источником истины для:

- цены;
    
- скидок;
    
- акций;
    
- наличия;
    
- состояния корзины;
    
- итоговой стоимости;
    
- состава создаваемого заказа.
    

Исторические данные заказа должны определяться серверной частью в момент создания Order.

# 32. Связь с функциональной моделью

AMD-030 непосредственно связан с **AMD-020 — Функциональная модель SmEl**.

Функциональные блоки используют следующие основные информационные сущности:

|Функциональный блок|Основные информационные сущности|
|---|---|
|Каталог|Category, Product, Characteristic, Image|
|Ценообразование|Price, Discount, Promotion|
|Наличие|Stock|
|Корзина|Cart, Cart Item|
|Проверка актуальности|Product, Stock, Price, Discount, Promotion, Cart Item|
|Checkout|Cart, Cart Item, Customer, Delivery Method, Payment Method|
|Заказ|Order, Order Item|
|Оплата|Payment, Payment Method|
|Доставка|Delivery, Delivery Method|
|Клиент|Customer, Cart, Order|
|Администрирование|основные сущности системы|

# 33. Связь с требованиями

AMD-030 разработан на основании:

- **REQ-000 — Требования к проекту SmEl**;
    
- **REQ-001 — Бизнес-требования SmEl**;
    
- **REQ-010 — Функциональные требования SmEl**;
    
- **REQ-020 — Информационные требования SmEl**;
    
- **REQ-030 — Нефункциональные требования SmEl**;
    
- **REQ-040 — Интеграционные требования SmEl**;
    
- **REQ-050 — Ограничения и бизнес-правила SmEl**.
    

# 34. Связь с архитектурными решениями

Информационная модель должна учитывать:

- **STD-001 — Технологический стек SmEl**;
    
- **ADR-001–ADR-020 — Архитектурные решения SmEl**.
    

Конкретная физическая реализация информационной модели должна определяться на последующих архитектурных уровнях.

# 35. Основание для последующих моделей

AMD-030 является основанием для разработки:

- **AMD-040 — Компонентная модель SmEl**;
    
- **AMD-041 — Модель взаимодействий SmEl**;
    
- **AMD-050 — Технологическая модель SmEl**;
    
- последующих моделей, связанных с интеграцией, развёртыванием и безопасностью.
    

# 36. Заключительные положения

AMD-030 определяет информационную структуру SmEl на архитектурном уровне.

Модель фиксирует основные информационные сущности, их связи и преобразование данных от товара до исторически зафиксированного заказа.

Документ не определяет конкретную физическую структуру базы данных и не заменяет технологическую модель или реализацию.

На основании AMD-030 должна быть разработана **AMD-040 — Компонентная модель SmEl**, определяющая программные компоненты, реализующие функциональные и информационные области системы.
