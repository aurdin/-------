Для проекта интернет-магазина **SmEl** я бы зафиксировал последовательность разработки архитектурной документации так, чтобы каждый следующий документ опирался на уже принятые решения.

### Последовательность

| Этап   | Идентификатор | Документ                                            | Назначение                                                             |
| ------ | ------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| **1**  | **STD**       | **STD — Standards / Стандарты проекта**             | Фиксирует правила, принципы, технологии и порядок разработки           |
| **2**  | **AMD**       | **AMD — Architecture Model / Архитектурная модель** | Описывает систему в целом: границы, контекст, основные части и связи   |
| **3**  | **REQ**       | **Requirements — Требования**                       | Фиксирует, **что** система должна делать                               |
| **4**  | **ADR**       | **ADR — Architecture Decision Record**              | Фиксирует, **почему** приняты конкретные архитектурные решения         |
| **5**  | **AMS**       | **Architecture Models — Архитектурные модели**      | Детализирует структуру системы, компоненты, взаимодействия и процессы  |
| **6**  | **API**       | **API / Contracts**                                 | Фиксирует контракты взаимодействия frontend ↔ backend и внешних систем |
| **7**  | **DAT**       | **Data Model / DB Architecture**                    | Детализирует сущности, связи, ограничения и хранение данных            |
| **8**  | **DEP**       | **Deployment Architecture**                         | Описывает Docker, окружения, инфраструктуру и развёртывание            |
| **9**  | SEC           | **Security Architecture**                           | Авторизация, права доступа, защита данных, безопасность API            |
| **10** | TST           | **Test Architecture / QA**                          | Определяет стратегию тестирования и связь требований с тестами         |

### Для SmEl сейчас логическая цепочка выглядит так

**STD-001**  
Технологический стек  
↓  
**AMD-001**  
Контекст SmEl  
↓  
**STD-002**  
Порядок разработки и оформления документов  
↓  
**Requirements SmEl**  
Функциональные и нефункциональные требования  
↓  
**AMD-020**  
Архитектурная модель после уточнения требований  
↓  
**ADR-001 … ADR-020**  
Уже принятые архитектурные решения  
↓  
**ADR-021 и далее**  
Новые решения, которые появляются из требований и детализации архитектуры  
↓  
**Architecture Models**  
Контекстная, контейнерная, компонентная, процессная и другие модели  
↓  
**API Contracts**  
Например, Checkout API  
↓  
**Data Model**  
↓  
**Deployment / Security / Test Architecture**

### Важный принцип

Последовательность лучше понимать не как строго линейную:

**Требования → архитектура → решения → модели → контракты → реализация**

Но при появлении нового существенного решения цикл повторяется:

**Требование → анализ → ADR → изменение архитектурной модели → контракт → реализация → тесты.**

То есть **ADR не должен заменять архитектурную модель**, а архитектурная модель не должна превращаться в набор отдельных ADR.

Для нашего SmEl я бы сейчас продолжил именно с **Requirements SmEl**, а затем уже сформировал **AMD-020** на основании согласованных требований.

Что такое контракт

**Контракт** в архитектуре программного проекта — это формальное соглашение о том, **как одна часть системы взаимодействует с другой**.

Проще:

> **Контракт отвечает на вопрос: «Что одна сторона может запросить у другой и что она получит в ответ?»**

### Пример для SmEl

Допустим, Frontend хочет получить корзину пользователя.

Контракт API может определить:

```
GET /api/cart/
```

Запрос:

```
GET /api/cart/
Authorization: ...
```

Ответ:

```
{
  "id": 15,
  "status": "busy",
  "items": [
    {
      "product": 123,
      "article": "LEGRAND-123",
      "quantity": 2,
      "unit_price": "150.00",
      "total": "300.00"
    }
  ],
  "subtotal": "300.00",
  "discount_total": "20.00",
  "total": "280.00"
}
```

Это и есть часть **контракта**.

Он определяет:

- URL;
- HTTP-метод;
- параметры запроса;
- формат данных;
- обязательные и необязательные поля;
- типы данных;
- возможные ответы;
- коды ошибок;
- правила авторизации;
- ограничения и бизнес-правила.

### Почему это важно

Frontend и Backend могут разрабатываться независимо.

Например:

```
             КОНТРАКТ
                │
       ┌────────┴────────┐
       ↓                 ↓
   Frontend            Backend
       │                 │
       └──── API ────────┘
```

Frontend знает:

> «Если я отправлю такой запрос, Backend должен вернуть данные вот в таком формате».

Backend знает:

> «Я обязан принимать такой запрос и возвращать согласованный формат».

Поэтому изменение API — это не просто изменение кода. Если изменение нарушает контракт, нужно учитывать обе стороны.

### В SmEl

У нас особенно важен **Checkout API Contract**, который мы уже начали разрабатывать.

Он определяет взаимодействие примерно такого вида:

```
Корзина
   ↓
Checkout API
   ↓
Проверка данных
   ↓
Расчёт стоимости
   ↓
Создание заказа
   ↓
Order
```

Например, контракт может определить:

```
POST /api/checkout/
```

**Вход:**

```
товары корзины
данные покупателя
адрес доставки
способ доставки
контактные данные
```

**Выход:**

```
номер заказа
состав заказа
стоимость товаров
скидка
итого
статус заказа
```

### Контракт ≠ реализация

Это очень важно.

**Контракт:**

> `POST /api/checkout/` принимает X и возвращает Y.

**Реализация:**

> Django View + Serializer + Service + модели Order делают это внутри Backend.

То есть контракт описывает **границу между системами**, а не то, как эта функция реализована внутри.

Для SmEl поэтому разумно выделять отдельный раздел архитектурной документации:

**API Contracts → Cart API → Checkout API → Order API → Auth API → Product API → Price API → Stock API**

И уже на основании этих контрактов реализовывать Frontend и Backend.

т.е. По русски это взаимодействие

Да, **в упрощённом виде — это взаимодействие**.

Но точнее:

- **Взаимодействие** — это сам процесс обмена между частями системы.
- **Контракт взаимодействия** — это **заранее согласованные правила этого обмена**.

Например, для SmEl:

> **Frontend ↔ Backend**

Взаимодействие:

> Frontend отправляет запрос → Backend его обрабатывает → Backend возвращает ответ.

Контракт:

> Какой URL, какой метод, какие данные передаются, какие данные возвращаются и какие ошибки возможны.

Поэтому в документации можно использовать понятное русское название:

**«Контракт взаимодействия»**

или, если хочется проще:

**«Правила взаимодействия»**.

Для архитектуры **SmEl** я бы использовал термин **«Контракт взаимодействия»**, а в скобках при первом употреблении — **API Contract**.
