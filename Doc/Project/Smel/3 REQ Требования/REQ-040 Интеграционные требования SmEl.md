# 1. Назначение

Настоящий документ определяет интеграционные требования проекта **SmEl (Smart Electric)**.

Документ устанавливает требования к взаимодействию SmEl с внешними системами, сервисами и внутренними программными компонентами, участвующими в реализации бизнес-процессов интернет-магазина.

# 2. Область применения

Интеграционные требования распространяются на:

- взаимодействие пользовательской и серверной частей SmEl;
    
- взаимодействие серверной части с внешними сервисами;
    
- интеграции, связанные с оплатой;
    
- интеграции, связанные с доставкой;
    
- передачу данных о товарах и наличии;
    
- обмен данными, необходимыми для выполнения бизнес-процессов;
    
- административные и служебные интеграции.
    

Конкретные технологии и протоколы интеграции определяются на архитектурном уровне.

# 3. Общие требования к интеграциям

Интеграции SmEl должны обеспечивать:

- корректную передачу данных;
    
- целостность передаваемой информации;
    
- однозначное определение участников обмена;
    
- контроль доступности внешней системы;
    
- обработку ошибок взаимодействия;
    
- контроль результатов операций;
    
- защиту передаваемых данных;
    
- возможность диагностики проблем интеграции.
    

Интеграция не должна приводить к нарушению целостности основных бизнес-операций SmEl.

# 4. Внутренняя интеграция клиентской и серверной частей

Пользовательская часть SmEl должна взаимодействовать с серверной частью посредством согласованного программного интерфейса.

Через данный интерфейс должны выполняться операции, связанные с:

- каталогом;
    
- товарами;
    
- ценообразованием;
    
- корзиной;
    
- проверкой актуальности;
    
- Checkout;
    
- заказами;
    
- клиентскими данными;
    
- доставкой;
    
- оплатой.
    

Серверная часть должна оставаться источником достоверных бизнес-данных и результатов критических операций.

# 5. Интеграция с платёжными системами

SmEl должен обеспечивать возможность взаимодействия с внешними платёжными системами, если соответствующий способ оплаты предусматривает внешнюю обработку платежа.

Интеграция должна обеспечивать:

- передачу необходимых данных для инициирования платежа;
    
- получение результата платёжной операции;
    
- идентификацию платёжной операции;
    
- обработку успешного платежа;
    
- обработку отказа или ошибки;
    
- получение информации об изменении состояния платежа.
    

Данные платежа должны быть связаны с соответствующим заказом.

# 6. Интеграция с системами доставки

SmEl должен обеспечивать возможность взаимодействия с внешними системами доставки, если выбранный способ доставки требует такой интеграции.

Интеграция может обеспечивать:

- передачу данных заказа;
    
- передачу данных получателя;
    
- передачу данных доставки;
    
- получение стоимости доставки;
    
- получение доступных вариантов доставки;
    
- получение идентификатора отправления;
    
- получение состояния доставки.
    

Результаты взаимодействия должны быть связаны с соответствующим заказом.

# 7. Интеграция с источниками товарных данных

При наличии внешних источников товарной информации SmEl должен обеспечивать возможность получения:

- данных о товарах;
    
- артикулов;
    
- характеристик;
    
- изображений;
    
- категорий;
    
- цен;
    
- информации о наличии.
    

Полученные данные должны проходить проверку перед использованием в каталоге.

Конкретные внешние источники определяются требованиями проекта и архитектурными решениями.

# 8. Интеграция с системами учёта наличия

При использовании внешней системы учёта SmEl должен иметь возможность получать информацию о доступности товаров.

Интеграция должна учитывать:

- идентификатор товара;
    
- доступное количество;
    
- состояние доступности;
    
- время получения информации;
    
- результат обмена.
    

Актуальность данных о наличии должна учитываться при проверке корзины и оформлении заказа.

# 9. Интеграция с внешними сервисами

SmEl может взаимодействовать с внешними сервисами, необходимыми для функционирования интернет-магазина.

К таким сервисам могут относиться:

- платёжные системы;
    
- службы доставки;
    
- сервисы уведомлений;
    
- источники товарных данных;
    
- системы учёта;
    
- сервисы идентификации;
    
- иные специализированные сервисы.
    

Каждая внешняя интеграция должна иметь определённое назначение и контролируемый интерфейс взаимодействия.

# 10. Форматы и структура данных

Передаваемые между системами данные должны иметь согласованную структуру.

Для каждой интеграции должны быть определены:

- состав данных;
    
- обязательные и необязательные поля;
    
- типы данных;
    
- правила валидации;
    
- правила преобразования;
    
- правила обработки отсутствующих данных;
    
- правила обработки некорректных данных.
    

Изменение формата обмена не должно приводить к неконтролируемому нарушению существующих интеграций.

# 11. Идентификация объектов

При интеграционном обмене информационные объекты должны иметь однозначные идентификаторы.

Для объектов, передаваемых между SmEl и внешней системой, должна обеспечиваться возможность сопоставления:

**объект SmEl ↔ объект внешней системы**

Особое внимание должно уделяться идентификации:

- товаров;
    
- заказов;
    
- платежей;
    
- отправлений;
    
- клиентов, если они передаются во внешнюю систему.
    

# 12. Обработка ошибок интеграции

SmEl должен корректно обрабатывать:

- недоступность внешней системы;
    
- тайм-аут;
    
- некорректный ответ;
    
- нарушение формата данных;
    
- отказ внешней системы;
    
- повторный запрос;
    
- частичное выполнение операции.
    

Ошибка внешней системы не должна приводить к неконтролируемому изменению состояния заказа.

# 13. Повторное выполнение операций

Для критически значимых интеграционных операций должна быть предусмотрена защита от неконтролируемого повторного выполнения.

Особенно это относится к:

- созданию платежа;
    
- подтверждению платежа;
    
- передаче заказа в службу доставки;
    
- изменению состояния заказа.
    

Повторная обработка одного и того же внешнего события не должна приводить к созданию дублирующих бизнес-операций.

# 14. Асинхронное взаимодействие

Для операций, выполнение которых не требует немедленного ответа пользователю, должна допускаться возможность асинхронного взаимодействия.

Асинхронный обмен может применяться для:

- уведомлений;
    
- обновления состояния доставки;
    
- обработки платёжных событий;
    
- синхронизации товарных данных;
    
- обновления информации о наличии.
    

Конкретный способ асинхронного взаимодействия определяется архитектурой SmEl.

# 15. Синхронизация данных

При обмене данными с внешними системами SmEl должен обеспечивать контроль актуальности полученной информации.

Должны учитываться:

- время получения данных;
    
- источник данных;
    
- состояние синхронизации;
    
- результат последней операции;
    
- ошибки обмена.
    

Критические данные должны проходить повторную проверку перед использованием в бизнес-операции, если существует риск их устаревания.

# 16. Безопасность интеграций

Интеграции должны обеспечивать защиту передаваемых данных.

Должны быть предусмотрены:

- аутентификация участников взаимодействия;
    
- авторизация операций;
    
- защита каналов передачи;
    
- контроль доступа к интеграционным интерфейсам;
    
- защита секретов и ключей доступа;
    
- контроль входящих данных.
    

Секретные данные интеграций не должны храниться или передаваться способом, создающим необоснованный риск их раскрытия.

# 17. Надёжность интеграций

Интеграции должны обеспечивать устойчивость к временным сбоям внешних систем.

В зависимости от характера операции могут применяться:

- повторные попытки;
    
- контроль времени ожидания;
    
- отложенная обработка;
    
- фиксация ошибки;
    
- ручная повторная обработка.
    

Механизм восстановления не должен нарушать целостность заказа и платежных данных.

# 18. Мониторинг интеграций

Для интеграций должна обеспечиваться возможность определить:

- состояние взаимодействия;
    
- время выполнения операции;
    
- результат операции;
    
- источник или получателя данных;
    
- возникшие ошибки;
    
- количество повторных попыток.
    

Информация должна быть достаточной для диагностики проблем интеграции.

# 19. Уведомления

При необходимости SmEl должен обеспечивать интеграцию с сервисами уведомлений.

Уведомления могут использоваться для информирования клиента о:

- создании заказа;
    
- изменении состояния заказа;
    
- успешной или неуспешной оплате;
    
- изменении состояния доставки;
    
- иных значимых событиях.
    

Факт отправки уведомления не должен определять состояние основной бизнес-операции, если иное специально не установлено требованиями.

# 20. Независимость бизнес-процессов от внешних систем

Недоступность внешней системы не должна приводить к потере уже сохранённых данных SmEl.

Для операций, допускающих отложенное выполнение, система должна обеспечивать сохранение информации до восстановления возможности взаимодействия.

Критические данные заказа должны сохраняться независимо от текущей доступности внешних сервисов.

# 21. Версионирование интеграций

Интеграционные интерфейсы должны иметь контролируемую версию.

Изменение интерфейса должно выполняться таким образом, чтобы обеспечить совместимость с существующими потребителями в течение установленного периода.

Несовместимые изменения должны быть явно идентифицированы и контролируемо введены в эксплуатацию.

# 22. Трассируемость интеграционных операций

Для критических интеграционных операций должна обеспечиваться возможность проследить цепочку:

**Бизнес-операция → запрос → внешний сервис → ответ → изменение состояния SmEl**

Особенно это относится к:

- платежам;
    
- доставке;
    
- синхронизации товаров;
    
- изменению наличия;
    
- уведомлениям.
    

# 23. Требования к отказоустойчивости

Система должна сохранять корректное состояние при отказе внешней системы.

При невозможности завершить интеграционную операцию SmEl должен:

- зафиксировать факт ошибки;
    
- сохранить необходимые данные;
    
- определить состояние операции;
    
- исключить неконтролируемое повторное выполнение;
    
- обеспечить возможность восстановления или повторной обработки.
    

# 24. Расширяемость интеграций

Архитектура SmEl должна допускать добавление новых внешних систем без необоснованного изменения существующих бизнес-процессов.

В частности, должна быть предусмотрена возможность добавления:

- нового платёжного провайдера;
    
- нового способа доставки;
    
- нового сервиса уведомлений;
    
- нового источника товарных данных;
    
- нового внешнего сервиса.
    

# 25. Количественные показатели

На текущем этапе конкретные количественные параметры интеграций не фиксируются.

В последующих версиях могут быть определены:

- максимальное время ожидания ответа;
    
- количество повторных попыток;
    
- интервалы синхронизации;
    
- допустимая задержка обновления данных;
    
- время восстановления интеграции;
    
- допустимое количество ошибок;
    
- другие эксплуатационные показатели.

# 28. Заключительные положения

REQ-040 определяет интеграционные требования SmEl и устанавливает общие требования к взаимодействию системы с внутренними и внешними участниками информационного обмена.

На основании REQ-040 должны быть определены соответствующие интеграционные компоненты и взаимодействия в последующих архитектурных моделях и архитектурных решениях SmEl.
