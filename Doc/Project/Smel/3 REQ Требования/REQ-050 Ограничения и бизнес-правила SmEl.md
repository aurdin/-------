# 1. Назначение

Настоящий документ определяет ограничения и бизнес-правила проекта **SmEl (Smart Electric)**.

Документ устанавливает обязательные условия функционирования системы, ограничения бизнес-процессов и правила, которым должны соответствовать пользовательские, информационные и административные операции.

# 2. Область применения

Требования распространяются на основные бизнес-процессы SmEl, включая:

- каталог;
    
- ценообразование;
    
- корзину;
    
- Checkout;
    
- оформление заказа;
    
- оплату;
    
- доставку;
    
- управление клиентами;
    
- административное управление.
    

# 3. Общие принципы

SmEl должен обеспечивать выполнение бизнес-операций в соответствии с установленными правилами.

Бизнес-правила должны применяться независимо от способа обращения к системе, включая пользовательский интерфейс, API и административные операции, если для соответствующей операции не установлено иное правило.

Критические бизнес-правила не должны зависеть исключительно от клиентской части системы.

# 4. Ограничения каталога

Товар может быть представлен в каталоге только при наличии обязательных данных, необходимых для его идентификации и отображения.

Товар должен иметь уникальный идентификатор.

Товар должен быть связан с соответствующей категорией, если такая связь обязательна для данного типа товара.

Данные каталога должны оставаться отделёнными от исторических данных уже оформленных заказов.

# 5. Правила ценообразования

Актуальная стоимость товара определяется действующими коммерческими условиями.

К коммерческим условиям относятся:

- базовая стоимость;
    
- скидки;
    
- акции;
    
- иные условия, влияющие на стоимость.
    

Стоимость товара в корзине не считается окончательно зафиксированной до оформления заказа.

Перед созданием заказа стоимость должна быть повторно проверена.

# 6. Правила применения скидок и акций

Скидка или акция может применяться только при выполнении установленных для неё условий.

Система должна учитывать период действия соответствующего коммерческого условия.

После создания заказа применённые скидки и акции должны сохраняться как часть исторических данных заказа.

Последующее изменение или прекращение действия скидки или акции не должно изменять уже созданный заказ.

# 7. Правила наличия товара

Товар может быть включён в заказ только при наличии необходимого количества или подтверждённой возможности его предоставления в соответствии с правилами продажи.

Перед созданием заказа наличие товара должно быть повторно проверено.

Информация о наличии, использованная при создании заказа, не должна изменять исторический состав уже созданного заказа.

# 8. Правила корзины

Корзина является промежуточным состоянием перед оформлением заказа.

Для каждой позиции корзины должны контролироваться:

- существование товара;
    
- доступность товара;
    
- количество;
    
- актуальность цены;
    
- скидки;
    
- акции;
    
- срок нахождения позиции в корзине;
    
- иные ограничения продажи.
    

Для авторизованного клиента корзина должна сохраняться между сеансами.

Для гостя корзина должна существовать только в рамках текущей сессии.

# 9. Срок нахождения товара в корзине

Система должна обеспечивать возможность контролировать срок нахождения позиции в корзине.

По истечении установленного срока позиция должна быть признана неактуальной либо повторно проверена в соответствии с правилами проекта.

Конкретное значение срока нахождения позиции в корзине на текущем этапе не фиксируется и должно быть определено отдельным бизнес-решением.

Истечение срока нахождения товара в корзине не должно приводить к изменению уже созданного заказа.

# 10. Правила Checkout

Checkout представляет собой промежуточный этап подготовки заказа.

Переход к созданию заказа допускается только после успешной проверки актуальности необходимых данных.

Checkout должен учитывать:

- состав корзины;
    
- количество товаров;
    
- актуальные цены;
    
- скидки и акции;
    
- данные клиента;
    
- способ доставки;
    
- данные получения;
    
- способ оплаты;
    
- итоговую стоимость.
    

Checkout не является самостоятельным историческим заказом.

# 11. Правила создания заказа

Заказ создаётся только после успешного завершения необходимых проверок.

При создании заказа должны быть зафиксированы:

- состав заказа;
    
- количество;
    
- стоимость товаров;
    
- применённые скидки и акции;
    
- стоимость доставки;
    
- итоговая стоимость;
    
- данные покупателя;
    
- способ доставки;
    
- данные получения;
    
- способ оплаты.
    

После создания заказа его историческое содержание не должно зависеть от текущего состояния корзины или каталога.

# 12. Историчность заказа

Заказ является самостоятельной исторической сущностью.

Изменение:

- товара;
    
- наименования;
    
- характеристик;
    
- цены;
    
- скидки;
    
- акции;
    
- наличия;
    
- условий доставки
    

не должно изменять соответствующие исторические данные уже созданного заказа.

Позиции заказа должны сохранять значения, действовавшие на момент оформления.

# 13. Правила изменения заказа

Возможность изменения заказа после создания определяется его текущим состоянием и установленными бизнес-правилами.

Недопустимые изменения должны быть отклонены системой.

Изменение заказа не должно нарушать:

- историческую целостность;
    
- финансовую целостность;
    
- состояние оплаты;
    
- состояние доставки.
    

# 14. Правила оплаты

Для заказа должен быть определён способ оплаты, если он обязателен для выбранного сценария.

Состояние оплаты должно быть связано с соответствующим заказом.

Платёжная операция должна быть однозначно идентифицируема.

Повторная обработка одного платежного события не должна приводить к неконтролируемому повторному зачислению или изменению состояния заказа.

# 15. Правила доставки

Для заказа должен быть определён способ доставки, если доставка предусмотрена выбранным сценарием.

Данные получения должны соответствовать выбранному способу доставки.

Стоимость доставки должна учитываться при формировании итоговой стоимости заказа.

Состояние доставки должно быть связано с соответствующим заказом.

# 16. Правила клиента

Авторизованный клиент должен иметь доступ только к своим пользовательским данным и заказам.

Гостю должна быть доступна покупка без обязательной регистрации, если соответствующий сценарий разрешён правилами SmEl.

Данные клиента, необходимые для выполнения заказа, должны обрабатываться в соответствии с установленными требованиями безопасности и защиты персональных данных.

# 17. Правила административного управления

Административные операции должны выполняться только пользователями, имеющими соответствующие полномочия.

Изменение административных данных не должно приводить к неконтролируемому изменению исторических данных заказов.

Критические административные операции должны быть доступны для аудита.

# 18. Правила идентификации

Основные информационные объекты SmEl должны иметь уникальные идентификаторы.

Идентификаторы не должны неоднозначно соответствовать нескольким объектам одного типа.

При интеграционном взаимодействии должна обеспечиваться возможность сопоставления объектов SmEl с объектами внешних систем.

# 19. Правила целостности

Система не должна допускать:

- создание заказа без обязательных данных;
    
- создание заказа из неактуальной корзины;
    
- использование недействующих коммерческих условий;
    
- нарушение обязательных связей между информационными объектами;
    
- потерю исторических данных заказа;
    
- неконтролируемое дублирование критических операций.
    

# 20. Правила работы с состояниями

Основные бизнес-объекты, имеющие жизненный цикл, должны иметь определённое состояние.

Состояния должны изменяться только посредством допустимых переходов.

Недопустимый переход состояния должен быть отклонён системой.

Особенно это относится к:

- заказу;
    
- оплате;
    
- доставке;
    
- корзине.
    

# 21. Правила повторного выполнения операций

Критические операции должны быть защищены от неконтролируемого повторного выполнения.

К таким операциям относятся:

- создание заказа;
    
- проведение платежа;
    
- подтверждение платежа;
    
- передача заказа в доставку;
    
- изменение критического состояния заказа.
    

Повторное получение одинакового внешнего события не должно создавать дублирующий бизнес-результат.

# 22. Правила внешних интеграций

Внешняя система не должна считаться источником истины для бизнес-данных SmEl без соответствующего архитектурного решения.

Полученные от внешней системы данные должны проходить необходимые проверки.

Недоступность внешней системы не должна приводить к потере уже сохранённых данных SmEl.

Для операций, допускающих отложенное выполнение, должна обеспечиваться возможность повторной обработки.

# 23. Ограничения безопасности

Доступ к данным и операциям должен предоставляться в соответствии с полномочиями пользователя.

Критические данные не должны быть доступны неавторизованным пользователям.

Секреты, ключи доступа и иные чувствительные данные интеграций не должны предоставляться клиентской части без необходимости.

# 24. Ограничения API

API должен принимать только корректные и допустимые данные.

Серверная часть должна самостоятельно выполнять необходимые проверки бизнес-правил.

Клиентская часть не должна иметь возможности обойти критические бизнес-ограничения посредством прямого обращения к API.

Результат критической операции должен определяться серверной частью.

# 25. Ограничения архитектурного характера

Настоящий документ не определяет конкретные технологии реализации бизнес-правил.

При этом архитектура SmEl должна обеспечивать:

- централизованное применение критических бизнес-правил;
    
- сохранение целостности данных;
    
- независимость исторических заказов от текущих данных каталога;
    
- контролируемое взаимодействие с внешними системами;
    
- возможность расширения бизнес-функций.
    

Конкретные архитектурные механизмы определяются документами серии AMD и ADR.

# 26. Приоритет бизнес-правил

Приоритет имеют правила, обеспечивающие:

1. целостность данных;
    
2. корректность финансовых операций;
    
3. корректность оформления заказа;
    
4. безопасность;
    
5. сохранение исторических данных;
    
6. корректность доставки;
    
7. выполнение дополнительных бизнес-функций.
    

При возникновении конфликта требований приоритет определяется на основании утверждённых требований проекта и соответствующих архитектурных решений.
