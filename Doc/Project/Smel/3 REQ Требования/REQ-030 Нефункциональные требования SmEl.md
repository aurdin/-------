# 1. Назначение

Настоящий документ определяет нефункциональные требования проекта **SmEl (Smart Electric)**.

Документ устанавливает требования к качественным характеристикам системы, её надёжности, производительности, безопасности, масштабируемости, сопровождаемости и другим эксплуатационным свойствам.

# 2. Область применения

Нефункциональные требования распространяются на программную систему SmEl в целом и учитываются при разработке пользовательской части, серверной части, информационного обеспечения, интеграций и административной части.

# 3. Производительность

SmEl должен обеспечивать приемлемое время отклика пользовательских операций.

В первую очередь требования производительности распространяются на:

- открытие каталога;
    
- переход между категориями;
    
- поиск;
    
- фильтрацию;
    
- открытие карточки товара;
    
- работу с корзиной;
    
- проверку корзины;
    
- оформление заказа;
    
- просмотр заказов.
    

Количественные показатели производительности должны быть определены после оценки целевой нагрузки и могут быть уточнены в последующих версиях документа.

# 4. Масштабируемость

Система должна обеспечивать возможность увеличения:

- количества товаров;
    
- количества категорий;
    
- количества клиентов;
    
- количества заказов;
    
- количества одновременно работающих пользователей;
    
- объёма хранимых данных.
    

Увеличение нагрузки не должно требовать изменения бизнес-требований системы.

# 5. Надёжность

SmEl должен обеспечивать корректное выполнение основных бизнес-операций.

Особое внимание должно уделяться операциям:

- изменения корзины;
    
- проверки актуальности корзины;
    
- оформления заказа;
    
- создания заказа;
    
- фиксации оплаты;
    
- изменения состояния заказа.
    

Система не должна создавать частично сформированный или неконсистентный заказ в результате сбоя операции.

# 6. Целостность данных

Система должна обеспечивать целостность данных между связанными информационными объектами.

Особенно должна обеспечиваться согласованность:

**Product → Cart Item → Checkout → Order Item**

и связанных с ними цен, скидок, акций, доставки и оплаты.

Исторические данные оформленного заказа должны сохраняться независимо от последующих изменений текущих данных каталога.

# 7. Безопасность

SmEl должен обеспечивать защиту:

- учётных записей;
    
- персональных данных клиентов;
    
- данных заказов;
    
- данных корзин;
    
- платёжной информации;
    
- административных функций.
    

Доступ к данным и функциям должен предоставляться в соответствии с полномочиями пользователя.

# 8. Аутентификация и авторизация

Система должна обеспечивать:

- идентификацию пользователей;
    
- аутентификацию;
    
- управление сессиями или иным механизмом состояния пользователя;
    
- разграничение доступа;
    
- защиту административных функций.
    

Авторизованный клиент должен иметь доступ только к своим пользовательским данным и заказам.

# 9. Защита персональных данных

Система должна обеспечивать обработку персональных данных в соответствии с применимыми требованиями законодательства и установленными правилами проекта.

Персональные данные не должны предоставляться пользователям, не имеющим соответствующих полномочий.

# 10. Доступность

SmEl должен обеспечивать доступность основных функций интернет-магазина в течение установленного периода эксплуатации.

Основными критическими функциями являются:

- каталог;
    
- просмотр товара;
    
- корзина;
    
- оформление заказа;
    
- заказ.
    

Конкретный показатель доступности должен быть определён после установления эксплуатационных требований проекта.

# 11. Восстановление

Система должна обеспечивать возможность восстановления работоспособности и данных после отказов.

Должны быть предусмотрены механизмы:

- резервного копирования;
    
- восстановления данных;
    
- контроля целостности восстановленных данных.
    

Параметры RPO и RTO определяются отдельными эксплуатационными требованиями.

# 12. Сопровождаемость

Система должна быть организована таким образом, чтобы обеспечивать:

- понятность структуры;
    
- локализацию изменений;
    
- тестируемость;
    
- возможность расширения функций;
    
- возможность исправления ошибок без необоснованного воздействия на другие части системы.
    

Изменения бизнес-правил не должны требовать изменения клиентской части, если соответствующее правило относится к серверной бизнес-логике.

# 13. Расширяемость

SmEl должен обеспечивать возможность расширения:

- ассортимента;
    
- категорий;
    
- характеристик;
    
- способов доставки;
    
- способов оплаты;
    
- механизмов ценообразования;
    
- интеграций;
    
- пользовательских функций.
    

Расширение системы не должно нарушать существующие бизнес-процессы.

# 14. Локализация

Система должна поддерживать мультиязычное представление пользовательской информации.

Минимальный набор языков:

- украинский;
    
- русский;
    
- английский.
    

Добавление нового языка не должно требовать изменения бизнес-логики существующих функций.

# 15. Совместимость

Пользовательская часть SmEl должна корректно работать в поддерживаемых современных веб-браузерах.

Система должна обеспечивать взаимодействие между клиентской и серверной частями посредством согласованного API.

# 16. Наблюдаемость

Система должна обеспечивать возможность контроля состояния основных компонентов и бизнес-операций.

Должна обеспечиваться регистрация значимых событий, ошибок и отказов, необходимых для:

- диагностики;
    
- анализа инцидентов;
    
- контроля работоспособности;
    
- сопровождения системы.
    

# 17. Аудит

Для критически значимых операций должна обеспечиваться возможность установить:

- что произошло;
    
- когда произошло;
    
- с каким объектом произошло;
    
- какой пользователь или процесс инициировал операцию.
    

Особое внимание должно уделяться операциям, связанным с заказами, оплатой, административным изменением данных и изменением коммерческих условий.

# 18. Безопасность бизнес-операций

Система должна защищать критические операции от некорректного или повторного выполнения.

В частности, создание заказа, изменение его состояния и обработка оплаты должны обеспечивать защиту от появления противоречивых состояний.

# 19. API

Взаимодействие пользовательской части с серверной частью должно осуществляться через определённый программный интерфейс.

API должен обеспечивать:

- предсказуемость взаимодействия;
    
- контроль доступа;
    
- валидацию входных данных;
    
- корректную обработку ошибок;
    
- согласованное представление данных.
    

Конкретная технология API определяется `STD-001` и соответствующими архитектурными решениями.

# 20. Независимость бизнес-логики

Критически важные бизнес-правила должны быть реализованы на стороне серверной части системы.

Клиентская часть не должна являться единственным источником:

- расчёта стоимости;
    
- проверки цены;
    
- проверки скидок и акций;
    
- проверки наличия;
    
- проверки корзины;
    
- создания заказа.
    

# 21. Тестируемость

Система должна обеспечивать возможность проверки:

- бизнес-правил;
    
- функциональных требований;
    
- API;
    
- операций с корзиной;
    
- оформления заказа;
    
- расчёта стоимости;
    
- управления заказами;
    
- механизмов авторизации.
    

# 22. Конфиденциальность

Доступ к информации должен предоставляться только субъектам, имеющим соответствующие права.

Особенно должны защищаться:

- персональные данные;
    
- данные авторизации;
    
- данные заказов;
    
- административные данные;
    
- платёжные данные.
    

# 23. Требования к ошибкам

Система должна:

- обнаруживать некорректные входные данные;
    
- предотвращать выполнение недопустимых операций;
    
- возвращать понятный результат ошибки;
    
- не раскрывать пользователю внутренние технические данные, не предназначенные для него;
    
- сохранять диагностическую информацию для сопровождения.
    

# 24. Трассируемость

Нефункциональные требования должны быть связаны с соответствующими функциональными и архитектурными требованиями.

Для критических требований должна быть обеспечена возможность проследить цепочку:

**REQ → AMD → ADR → Реализация → Верификация**

# 25. Количественные показатели

На текущем этапе часть нефункциональных требований сформулирована качественно.

Конкретные значения для:

- времени отклика;
    
- производительности;
    
- доступности;
    
- RPO;
    
- RTO;
    
- максимальной нагрузки;
    
- количества одновременно работающих пользователей;
    
- других эксплуатационных характеристик
    

должны быть определены после уточнения целевых эксплуатационных параметров SmEl.

# 26. Связь с другими требованиями

REQ-030 детализирует нефункциональную составляющую требований REQ-000 и учитывает функциональные и информационные требования REQ-001, REQ-010 и REQ-020.

Документ является основанием для соответствующих архитектурных моделей и архитектурных решений SmEl.

# 27. Связанные документы

- **REQ-000 — Требования к проекту SmEl**
    
- **REQ-001 — Бизнес-требования SmEl**
    
- **REQ-010 — Функциональные требования SmEl**
    
- **REQ-020 — Информационные требования SmEl**
    
- **STD-001 — Технологический стек SmEl**
    
- **AMD-001 — Контекст SmEl**
    
- **ADR-001–ADR-020 — Архитектурные решения SmEl**
    

# 28. Заключительные положения

REQ-030 определяет нефункциональные требования SmEl.

Документ устанавливает целевые качественные характеристики системы, но не определяет конкретные архитектурные механизмы их реализации.

Количественные показатели могут уточняться по мере развития проекта и должны фиксироваться в новых версиях требований.
